# FINeprint

> AI가 금융 상품을 설명할 때 **빼먹는 조건**을 잡아내는 프로젝트.

이름은 영어 표현 "read the fine print"(약관의 깨알글씨까지 읽어라)에서 왔다.
**FIN**ance(금융) · **fine**-grained condition(잘게 쪼갠 조건) ·
printed disclosure(공시 문서) — 세 뜻이 겹친다.

## 무엇이 문제인가

실제 사례 하나로 시작하는 게 빠르다. 금융감독원 공시에 올라온 정기예금
**e-그린세이브예금**의 우대조건 원문은 이렇게 되어 있다.

```
만기일에 아래 조건을 "모두" 충족하는 경우 보너스이율 0.1%
  - 6~12개월제로 5천만원 이상 가입
  - 만기일 기준 전전월 말에 펀드 3천만원 이상 보유
```

AI가 내놓은 답변은 이랬다.

```
"5천만원 이상 가입하면 보너스이율 0.1%를 받을 수 있다"     ← 펀드 조건이 빠졌다
```

이 답변이 맞는지 검사하는 프로그램(이하 **검증기**)은 이걸 **통과시켰다.**
"5천만원 이상 가입"은 공시 원문에 정말 있으니까 맞다고 본 것이다. 하지만 답변은
틀렸다 — 조건 하나를 빼먹었으니 그대로 따라 해도 보너스이율을 못 받는다.

**틀린 답을 맞다고 통과시키는 이 실수를 이 프로젝트에서 `condition_omission`
(필수조건 누락)이라고 부른다.** 이게 첫 번째 타깃이다.

<details>
<summary>검증기가 내리는 판정 세 가지 (용어 정리)</summary>

| 판정 | 뜻 |
|---|---|
| `SUPPORTED` | 답변이 공시 내용으로 뒷받침된다 |
| `UNSUPPORTED` | 답변이 공시 내용과 어긋난다 |
| `INSUFFICIENT` | 맞는지 틀린지 판단할 정보가 공시에 없다 |

위 예시의 정답은 `UNSUPPORTED`인데 검증기는 `SUPPORTED`를 냈다.
</details>

## 왜 어려운가 — 모델을 키워도 안 됐다

선행 프로젝트 [finance_verifier](https://github.com/hyos0415/finance_verifier)에서
같은 문제를 세 모델에 물어봤고, 결과는 이랬다.

| 모델 | 크기 | 이 실수를 잡았나 |
|---|---|---|
| Qwen3.5-4B | 4B(작음) | 0/2 |
| Claude Haiku 4.5 | — | 1/2 |
| Nemotron Ultra | 550B(위의 약 130배) | 0/2 |

**130배 큰 모델이 같은 지점에서 같은 실수를 했다.** 모델을 키워서 해결되는 문제가
아니라는 뜻이다. 게다가 이건 "필요한 문서를 못 찾아서" 생긴 실수도 아니다 —
finance_verifier에는 검색 단계가 아예 없고, 공시 원문을 그대로 넣어준 상태에서
실패했다.

정리하면, 지금 검증기는 **답변에 적힌 것이 맞는지는 잘 보지만, 답변에 안 적힌
필수조건을 공시 전체에서 찾아내지는 못한다.**

## 세우려는 가설

> 조건을 **구조로 적어두면** — 특히 **어느 혜택에 어떤 조건이 걸리는지**를
> 혜택 단위로 묶어두면 — 빠진 조건을 계산으로 잡을 수 있다.

"혜택 단위로 묶는다"는 게 왜 중요한지는 다른 상품이 잘 보여준다. 한 예금 상품은
우대금리 갈래가 셋이고, 각 갈래마다 붙는 조건이 다르다.

```
① 거래기간 5년 이상 + 마케팅 동의   →  0.20%
② 급여·연금 입금                    →  0.10%
③ 카드 결제실적                     →  0.10%
```

AI가 "거래기간 5년 이상이면 0.20%"라고 답했다면, 빠진 것은 ①에 같이 걸린
**마케팅 동의**다. ②③은 이 답변과 아무 상관이 없다. 즉 조건을 한 줄로 늘어놓은
목록만으로는 판단이 안 되고, **"이 답변이 말하는 혜택 → 그 혜택에 걸린 조건들"**
순서로 좁혀야 답이 나온다.

같은 구조로 두 번째 실수도 겨냥한다: **`INSUFFICIENT`와 `UNSUPPORTED`를 헷갈리는
것**("정보가 없음"과 "명시적으로 틀림"의 구분). 답변이 가리키는 항목이 구조 안에
있는지 없는지만 조회하면 되는 문제로 바뀐다.

## 이 프로젝트가 하지 않는 것

**"그래프를 써보는 프로젝트"가 아니다.** 위 가설이 맞더라도 그래프까지 갈 필요는
없을 수 있고, 심지어 **조건을 정리해서 그냥 LLM에게 넘겨주는 것만으로 해결될
수도 있다.**

그래서 그래프를 만들기 **전에**, 더 싼 방법들로 되는지부터 순서대로 확인한다.
이 확인 절차를 **반증 게이트**라고 부르고, 내용은 `docs/handoff/v2.md` §3에 있다.

게이트에서 "그래프 필요 없음"이 나오면 **거기서 끝내고, 그게 이 프로젝트의
결론이다.** 실패가 아니라 측정으로 얻은 발견이다.

이 게이트가 답하는 것은 **상품 하나 안에서의** 조건 누락까지다. 조건이 **다른 상품을
가리키는** 경우(예: "우리 은행 적금에 같이 가입해야 함")는 정보가 한 레코드 안에 없어서
따로 물어야 했고, 그래서 "사슬을 따라가야 잡히는 누락이 있는가"를 2단계 질문으로 세웠다.

**그 질문은 측정한 뒤 폐기했다.** 적금을 넣으면 사슬이 몇 건까지 늘어날지 예측을 먼저
커밋하고(임계: 6건 미만이면 폐기) 적금 전수 59건을 수집해 세어 보니 **4건**이었다.
참조 자체는 예측보다 많았지만(적금 조건의 51.8%), 대상이 대부분 입출금통장·주택청약·
카드이고 금융감독원 API에는 그 상품군이 **없다**. 기록: `docs/decisions/0002-drop-chain-traversal.md`.

측정으로 방향을 닫은 것도 결과다. 남은 것은 `START-HERE.md` §5에 있다.

## 지금 상태

```
문서·계획 확정.   구현 0줄.   실험 0건.
```

착수 전에 사람이 정해야 할 것이 3개 남아 있다 (표본 크기, 게이트 통과 기준,
조건 판정 규칙). → **[`START-HERE.md`](./START-HERE.md)** 부터 읽는다.

## 계보

이 프로젝트는 앞선 두 프로젝트에서 배운 걸 이어받는다.

```
KAG_LlamaIndex     그래프부터 만들고 평가는 나중에 → 한계 발견
        ↓
finance_verifier   평가부터 만들기 → 필수조건 누락 실패를 실제로 발견 (사례 3건)
        ↓
FINeprint          "구조가 정말 필요한가"부터 확인 → 필요한 만큼만 만들고 효과를 측정
```
