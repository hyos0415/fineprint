# 0042 · 로컬 추론은 R2 하나에만 둔다 — 엔진은 llama.cpp, 비교는 R3 무대에서

> 날짜: 2026-09-01 · 상태: 유효

로드맵 D8(R2) · B7(E2) · C1(R3) · 앞선 결정 `0041`(사용자 한 명) · `0026`(개인정보
최소수집) · `0013`(추출 개선 중단) · `0038`(의존성 예외는 사유를 적는다) ·
`design.md` R2 절(*"개인정보 이유로 로컬 SLM을 1순위로 둔다"*)

**사전등록이 없다.** 자원 배분과 도구 선택이다. **실험을 하게 되면 그때 사전등록한다**
(아래 D5).

## Decision

**GPU 에 상주할 모델은 하나뿐이므로, 그 자리를 대안이 없는 과업에 준다.**

```
D1  **로컬 모델은 R2(사용자 자연어 → 스코프) 하나에만 둔다.** 개인정보가 닿는
    유일한 추론 자리이고, API 로 보내면 그 순간 외부로 나간다 — **대안이 없다**

D2  **R2 의 엔진은 llama.cpp 다.** 온디맨드 적재(필요할 때 올리고 놓는다) ·
    양자화로 크기 선택 · CPU 오프로드 · GBNF 로 임의 문법 강제

D3  **자유 입력의 출력은 화이트리스트 스키마다** — 기관 · 상품군 · 기간 · 금액 넷.
    **원문은 구조화 직후 버리고 로그에도 남기지 않는다.** 로컬만으로는 절반이다 —
    우리가 원문을 적으면 그건 여전히 개인정보 보관이다

D4  **R1(추출)·R3(분해 검증)은 API 로 남긴다.** 개인정보가 없고(공시 원문뿐)
    품질이 측정 대상이다. **B7(E2 — 로컬 vs Haiku · 비용 축)은 우선순위를 내린다**

D5  **엔진 비교 실험은 R3 무대에서 한다.** 지표·임계를 측정 전에 커밋한다
    (`CLAUDE.md` 3번). 지금은 하지 않는다 — F4-2 를 먼저 닫는다

D6  **자연어로 조건 답을 확정하지 않는다.** `design.md` R2 절이 이미 정한 것을 다시
    못 박는다 — 조건은 사용자가 예/아니오/모름으로 확인한다
```

## Evidence

### 제약이 "요청 동시성" 이 아니라 "모델 상주" 다

```
RTX 4070 Laptop 8GB · 사람이 보기에 R2 모델 하나가 7GB 가까이 먹는다
→ 상주 가능한 모델이 **하나**다
→ R3·B7 배치가 VRAM 을 잡고 있으면 **사용자가 문장을 입력하는 순간 R2 가 못 뜬다**
```

**처음에 이 충돌을 안 셌다.** "엔진 하나로 셋(R2·R3·B7)을 감당한다" 는 말은 워크로드가
겹치지 않을 때만 성립한다.

### 그래서 배분 기준은 "대안이 있는가" 다

```
R2   로컬이 **필수** — API 로 보내면 개인정보가 나간다. 대안이 없다
B7   로컬이 **선택** — 대안(Haiku)이 완전히 괜찮다. 데이터가 공개 공시다
R3   같음 — 공시 원문과 우리 분해뿐이다
```

**희소 자원은 대안이 없는 쪽에 간다.** 그리고 B7 의 보상 자체가 작다 — 추출 호출이
**월 460쌍**(은행권 234 + 저축은행 228)이고 `0013` 이 이미 추출 개선을 멈춘 상태다.
비용 축의 절대값이 크지 않다.

**B7 을 옹호할 수 있는 논리 하나**는 *"로컬 SLM 이 이 프로젝트 과업에서 얼마나 하는지를
R2 전에 안다"* 인데, **과업이 다르다** — R1 은 긴 조건문을 17종으로 분류하고 R2 는 짧은
문장에서 4칸을 뽑는다. 전이가 약하다.

### 개인정보가 닿는 자리는 자유 입력이다 — 그리고 위험은 "안 물은 것" 이다

```
지금 (F4-2 폼)   기관·상품군·기간·금액을 선택·숫자 필드로 받는다 → **LLM 이 안 닿는다**
R2 를 켜면       사용자가 문장을 쓴다 → **LLM 이 첫 수신자다**

우리가 필요한 것   스코프 축 넷
사용자가 쓸 것     "우리은행 주거래고 목돈 3천만 정도, 6개월~1년 짧게"
                → 거래 은행 · 보유 금액 · 자금 성격이 한 문장에 다 들어온다.
                  자유 입력이라 직장·가족·잔액이 섞여도 우리가 못 막는다
```

**구조화된 답보다 자유 텍스트가 질적으로 더 위험하다** — 경계가 없고, 첫 접촉이고,
사용자가 스스로 더 말한다. 그래서 D3 의 화이트리스트가 로컬 못지않게 중요하다.
`problem.md` §7 이 *"LLM 이 숫자를 만들지 못하게 한다"* 로 막은 것과 같은 모양이고,
여기서는 **LLM 이 뽑을 수 있는 칸을 미리 제한하는 것**이다.

### 엔진 셋의 차이 — 구조적으로 아는 것

```
llama.cpp   GGUF 양자화 + CPU/GPU 하이브리드. **VRAM 보다 큰 모델을 오프로드로 돌린다**
            GBNF = 임의의 문맥자유문법 제약 (JSON 스키마보다 넓다)
            프로세스 하나 · Docker·WSL 불필요 · **올리고 놓기가 쉽다**
            약점 — 동시성·긴 프롬프트 prefill
vLLM        PagedAttention · 연속 배치 · CUDA graph · 접두 캐시 · guided decoding
            모델이 VRAM 에 들어가야 한다 · **VRAM 풀을 미리 크게 잡는다**(기본 0.9)
            이 저장소에 **검증된 설정이 이미 있다**(`CLAUDE.md` · `scripts/run_vllm.sh`)
SGLang      **RadixAttention** — 요청 간 접두를 자동 재사용한다
            **jump-forward 제약 디코딩** — 문법이 강제하는 토큰을 건너뛴다
            **다단 호출 DSL** — 오케스트레이션을 런타임이 함께 최적화한다
            약점 — 생태계가 작고 Linux 우선 · 상주 서버로 VRAM 을 잡는다
```

**R2 워크로드가 이 차이를 구분하지 않는다** — 사용자 1명 · 짧은 문장 · 4칸 · 세션 중에만.
배치가 없고 재사용할 접두가 없고 제약 디코딩은 셋 다 된다. **셋 다 "충분히 빠르다" 로
끝난다.** 그래서 R2 에서는 온디맨드 적재가 되는 쪽(llama.cpp)이 성질에 맞는다 —
세션 밖에서 VRAM 을 붙들 이유가 없다.

### 엔진 차이가 드러나는 무대는 이 프로젝트 안에 이미 있다

```
R1 추출     월 460쌍 · **같은 system 블록 고정 + 조건문만 바뀜**(`extract_llm.py` 주석 100줄)
           → 접두 재사용이 정확히 겨냥하는 모양
R3 분해 검증  원문 고정 + 분해만 바뀜 · 출력이 셋 중 하나(SUPPORTED/UNSUPPORTED/INSUFFICIENT)
           → 접두 재사용 + jump-forward **둘 다** 먹는다
```

**R3 는 품질은 막혀 있고 엔진은 열려 있다.** C1 이 gold 라벨을 선행으로 두는 것은
*판정이 맞았나*를 재기 위한 것이고, **엔진 측정에는 라벨이 필요 없다** — 실제
(원문, 분해) 쌍으로 처리량·지연·VRAM 을 잰다. 출력을 채택할 유혹이 없어서 오히려 깔끔하다.

### 관찰 도구 — 층이 넷이고 새로 도입할 것이 없다

```
A. 앱·프롬프트   **Langfuse** — 호출 단위 프롬프트·출력·지연·토큰수, `engine` 태그로 나란히.
                다단 호출은 중첩 span. `.env.example` 에 키 자리가 **이미 있다**
B. 엔진 내부     각 엔진이 낸다 — vLLM `/metrics` · SGLang `--enable-metrics`(로그에
                **캐시 히트율**이 찍힌다) · llama.cpp `/metrics` + 응답 `timings`
                (**prefill 과 decode 를 갈라 준다**)
C. GPU·시스템    `nvidia-smi (dmon)` — VRAM 실사용 · SM 활용률. "정말 7GB 먹나" 가 여기서 답난다
D. 커널·프로파일  Nsight Systems · PyTorch profiler — 우리 목적에는 과하다
```

**Grafana 를 세울 필요가 없다** — 스크립트가 `/metrics` 를 찍고 `nvidia-smi` 를 폴링해
CSV 로 떨구면 된다. `CLAUDE.md` 가 선행 프로젝트 근거로 가리키는 것도 `results/latency/`
라는 **파일**이다.

**공정 비교의 함정** — 엔진마다 지표 정의가 다르다(TTFT 를 어디서 재나, 캐시 히트율을
무엇으로 나누나). 대시보드 숫자를 나란히 놓으면 사람을 속인다. **직접 잰 것**(총 시간,
토큰 수, VRAM 최대값)이 비교에 안전하다.

## Alternative

- **A. R2 에 SGLang 을 쓴다** — 사람이 써 보고 싶다고 했다
- **B. 엔진 하나로 R2·R3·B7 을 다 감당한다** (vLLM 또는 SGLang 상주)
- **C. B7(로컬 vs Haiku)을 먼저 한다** — 선행 조건이 채워져 있고 vLLM 환경이 검증됐다
- **D. Ollama** — 운영이 가장 쉽다
- **E. R2 도 API 로 보낸다** — 개인정보 처리 고지를 하고
- **F. 엔진 비교를 지금 한다** (F4-2 보다 먼저)

## Why rejected

- **A** — **강점이 R2 에서 하나도 안 살아난다.** 접두 재사용할 요청이 없고 배치가 없다.
  게다가 상주 서버라 세션 밖에서도 VRAM 을 붙든다. **학습 목적에도 손해다** —
  어느 엔진을 써도 "잘 돌던데요" 로 끝나 엔진을 평가할 근거가 안 나온다. 그래서
  D5 로 **무대를 R3 로 옮겼다**(강점이 결과로 드러나는 자리)
- **B** — 위 Evidence 첫 항목. 8GB 에서 상주 모델이 하나라 **배치가 R2 를 밀어낸다**
- **C** — 보상이 작고(월 460쌍 · `0013` 이 추출 개선을 멈췄다) **GPU 우선순위를 개인정보가
  아닌 비용 축에 준다.** 선행 조건이 채워졌다는 것은 *할 수 있다*는 뜻이고 *먼저 해야
  한다*는 뜻이 아니다
- **D** — llama.cpp 를 감싼 것이다. 얻는 것이 운영 편의뿐이고 **감춰지는 것이 정확히
  배우고 싶은 부분**이다(양자화·오프로드·GBNF). 사람이 제외했다
- **E** — `design.md` R2 절이 *"개인정보 이유로 로컬 SLM 을 1순위로 둔다"* 로 이미 정했고,
  `0026`(개인정보 최소수집)과 정면으로 어긋난다. 고지는 전송을 되돌리지 못한다
- **F** — F4-2 가 크리티컬 패스의 마지막이고, **끝까지 도는 화면이 있으면 R2 의 요구가
  구체적으로 보인다**(사용자가 실제로 무엇을 자유롭게 쓰려 하는지). 엔진 실험은 늦어도
  잃는 것이 없다

## 반증 조건

- **3B Q4(~2GB)로 4칸 추출이 되면** — VRAM 제약 자체가 자작이었던 것이다. 그러면 상주
  모델이 둘 이상 가능해지고 B 안(엔진 하나로 여럿)이 다시 살아난다. **`design.md` 가
  R2 측정을 "필드별 추출 정확도" 로 이미 적어 뒀으니 그 측정이 곧 모델 크기 결정이다**
- **llama.cpp 로 R2 를 만들었더니 지연이 사용자에게 걸리면** — 짧은 문장 하나라 괜찮다고
  봤다. prefill 이 느려 체감되면 GPU 최적화 엔진(vLLM·SGLang)으로 옮긴다 —
  그때는 상주 비용을 받아들이는 것이다
- **화이트리스트로 뽑았는데 원문이 어딘가에 남으면** — D3 가 깨진 것이다. `ask_session_*.json`
  이 답을 기록하므로 **자유 입력을 켜는 순간 그 로그를 먼저 본다**
- **엔진 비교를 R3 에서 했더니 차이가 안 나오면** — 무대 선택이 틀린 것이다. 그러면
  차이가 나는 조건(더 긴 프롬프트 · 더 많은 호출 · 더 강한 문법 제약)을 찾거나,
  **"우리 규모에서는 엔진이 구분되지 않는다" 를 결론으로 적는다** — 그것도 실증사례다
- **R2 를 만들었더니 질문 수가 줄지 않으면** — 자유 입력이 **개인정보 위험만 늘리고 얻는
  게 없는 부품**이다. `0028` 이 스코프로 39→7 을 실측한 방식으로 재고, 안 줄면 R2 를 뺀다
