# 0032 · 세율은 조문 좌표에 핀을 박고, 바뀌었는지만 기계가 본다

> 날짜: 2026-08-31 · 상태: 유효

이슈 [#28](https://github.com/hyos0415/fineprint/issues/28) · 로드맵 E3·A6·H1 ·
앞선 결정 `0010`(공시는 월 1회) · `0030`(선호 가중치 — 전부 세후 %p) ·
`problem.md` §4(세율표를 코드에 안 박는다) · §7(AI가 숫자를 만들지 못하게 한다)

**사전등록이 없다.** 이건 측정이 아니라 **사실 확인**이라 예측할 것이 없다 —
조문에 뭐라고 적혀 있는지는 읽으면 나온다.

## Decision

**세율의 근거 조문 좌표를 커밋하고, 그것이 바뀌었는지만 기계가 본다.**

```
config/tax-sources.json   법령ID · 조문번호 · 조문가지번호 · 시행일자 · 공포번호
                          · 본문 해시 · 인용 원문
src/ingest/fetch_law.py   --check 로 대조 · --snapshot 으로 갱신 · --show 로 원문 읽기
```

정한 것 넷.

1. **핀은 `법령ID` 에 박는다.** `MST`(법령일련번호)는 개정마다 새로 생기므로 매번
   검색으로 얻고, **그 변화 자체가 "바뀌었다" 신호다**
2. **2단으로 확인한다.** 목록 조회(2.5KB)로 판정하고, 바뀐 법령만 본문(1.3MB)을 긁는다
3. **조문에서 세율을 자동으로 읽지 않는다.** 기계는 *"바뀌었다"* 까지만 말하고
   *"무엇으로 바뀌었나"* 는 사람이 읽어 `config/tax-2026.json` 에 반영한다
4. **별도 DAG 를 만들지 않는다.** 세율이 쓰이는 자리는 월 1회 공시 수집 뒤의 계산
   하나뿐이므로, **월간 파이프라인의 첫 태스크**로 넣는다 (로드맵 H1)

## Evidence

### 첫 확인에서 틀린 값이 나왔다 — 그리고 그게 3번의 근거다

```
조특법 §89의3   조합등예탁금

  우리 config     "세율 0.014 — 농특세만 부과"
  조문 실제        2025-12-31 까지 가입분은 **비과세**
                 **2026-01-01 ~ 2026-12-31 가입분 100분의 5**
                 2027-01-01 이후 가입분 100분의 9
```

**우리 값은 2025년까지의 상태였다.** 일몰이 지나 저율과세가 시작된 것을 몰랐다.
**가입 시기로 세율이 갈리고 대상자 조건(§88조의5②1)으로 또 갈린다** — 조문에서 세율을
정규식으로 뽑았다면 어느 숫자를 집었을지 알 수 없고, 정확히 **이런 종류의 틀린 값을
조용히** 만들었을 것이다.

`problem.md` §7 이 *"LLM 이 숫자를 만들지 못하게 한다 — 숫자 칸은 코드가 채운다"* 로
막은 것과 같은 자리다. 여기서는 **정규식이 그 자리에 있었을 뻔했다.**

**화면 영향은 0이다** — 이 상품군은 우리 데이터에 없다고 config 에 이미 적혀 있었다.
값이 틀렸을 뿐이다.

### 빠진 값도 하나 있었다

```
조특법 §88의2   비과세종합저축에 **2028년 12월 31일까지** 가입하는 경우
우리 config     일몰이 아예 안 적혀 있었다
```

**2028-12-31 까지 살아 있으므로 2층 세금 계산은 무사하다.** 다만 그것을 모르고 있었다.

### 맞은 값 넷도 조문으로 확인했다

| config | 조문 |
|---|---|
| 이자소득세 14% | 소득세법 §129①1**라** — "그 밖의 이자소득에 대해서는 100분의 14" |
| 지방소득세 1.4% | 지방세법 §103의13① — "원천징수하는 소득세의 **100분의 10**" |
| 비과세종합저축 한도 5천만원 | 조특법 §88의2① |
| 종합과세 기준 2천만원 | 소득세법 §14③6 — "이자소득등의 종합과세기준금액" |

**지방소득세 1.4% 는 조문에 없다.** 14% × 10% 로 유도한 값이다. 그래서 감시하는
문구를 `"1.4%"` 가 아니라 **`"100분의 10에 해당하는 금액"`** 으로 잡았다 — 조문이
말하는 것을 감시해야지 우리가 계산한 것을 감시하면 안 된다.

### 2단 확인의 근거는 실측 크기 차이다

```
lawSearch.do    2,505 bytes      법령일련번호·시행일자·공포번호   <- 이것만으로 판정된다
lawService.do   1,288,895 bytes  본문 (소득세법)                 ~515배
```

**동작을 확인했다** — 스냅샷의 공포번호를 개정된 것처럼 바꿔 놓고 돌리니 그 법령만
2단으로 내려가 조문 2개를 대조하고 종료코드 1을 냈다. 나머지 두 법령은 본문을
안 긁었다.

### 조문 단위로도 잡힌다

`조문시행일자` 가 따로 있다. 소득세법이 2026-07-01 시행 버전인데 §129 의
`조문시행일자` 는 `20260101` 이다 — **그 조문은 1월 이후 안 바뀌었다**는 뜻이다.

### 함정 하나 — `조문여부='전문'`

편·장 헤더가 **같은 조문번호로** 조문 목록에 섞여 있다. 안 걸렀다가 소득세법 §14 와
지방세법 §103의13 을 못 찾았다. 좌표는 `(조문번호, 조문가지번호)` 이고
`조문여부 == '조문'` 을 함께 봐야 한다.

## Alternative

- **A. 조문에서 세율을 정규식으로 뽑아 config 를 자동 갱신한다** — 사람 손이 아예 없다
- **B. 매일 조문을 긁는다** — 개정을 가장 빨리 안다
- **C. 세율 감시용 Airflow DAG 를 따로 세운다** — 관심사가 분리된다
- **D. 지금처럼 사람이 한 번 확인하고 끝낸다** — 스냅샷도 스크립트도 안 만든다
- **E. 12월~1월에만 조밀하게 본다** — 세법 개정 시점이 예측 가능하다

## Why rejected

- **A** — §89의3 이 반례다. 가입 시기별로 5%/9% 로 갈리고 대상자 조건이 붙는다.
  정규식이 어느 숫자를 집을지 알 수 없고, **틀려도 조용하다.** 오늘 찾은 오류가
  정확히 그 모양이다
- **B** — 명분이 없다. 세율은 매일 쓰는 값이 아니고 쓰이는 자리는 월 1회 계산
  하나뿐이다. 364일의 "안 바뀌었다" 는 정보가 아니다
- **C** — 저장소에 `dags/` 가 0개이고 H1 은 9월 공시 대기다. 이것 하나 때문에
  인프라를 먼저 세우면 `CLAUDE.md` 1번이 막는 모양(**구조 먼저, 쓸 곳은 나중**)이 된다.
  스크립트가 DAG task 의 몸통이고 cron·Actions·Airflow 어디에나 붙는다
- **D** — 세법은 매년 바뀐다. 한 번 확인하고 끝내면 **내년 이맘때 오늘과 똑같은
  상태**가 된다. 오늘 찾은 오류가 그 증거다 — 누군가 2025년에 맞게 적어 뒀고 아무도
  다시 안 봤다
- **E** — 지연을 20일에서 며칠로 줄이는 대신 지킬 규칙이 하나 늘어난다. **지연이
  실제로 문제가 됐을 때 만든다** — 그때는 근거가 생긴다. 지금은 근거 없는 최적화다

## 반증 조건

- **`--check` 가 개정을 놓치면** — 목록 조회의 시행일자·공포번호가 개정 신호로
  충분하지 않은 것이다. 그러면 조문 해시를 매번 보는 쪽으로 바꾼다(비용이 515배 든다)
- **개정 20일 지연이 실제로 사용자에게 틀린 숫자를 보여주면** — 대안 E(12~1월 창)를
  다시 본다. 지금은 근거가 없어서 안 만들었다
- **`--check` 가 자주 발동하는데 세율이 안 바뀌면** — 조문 전체를 해시로 잡는 것이
  너무 민감한 것이다(자구 수정·다른 항의 개정에도 걸린다). 그러면 감시 범위를
  `볼 문구` 주변으로 좁힌다
- **`OC=test` 가 막히면** — 공용 샘플 키에 기댄 것이 틀린 것이다. `.env` 의
  `LAW_OC` 로 실키를 받는다 (자리는 이미 만들어 뒀다)
- **사람이 `--check` 결과를 보고도 config 를 안 고치면** — 알림만 있고 강제가 없는
  것이다. 그때는 월간 파이프라인이 **계산 전에 멈추게** 한다 (지금은 종료코드만 낸다)
