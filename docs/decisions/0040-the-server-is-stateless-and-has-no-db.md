# 0040 · 서버는 무상태다 — 답을 저장하지 않고, 그래서 DB 가 없다

> 날짜: 2026-09-01 · 상태: 유효

로드맵 F4-1 · 이슈 [#38](https://github.com/hyos0415/fineprint/issues/38) ·
계획 [`ui-plan.md`](../spec/ui-plan.md) · 앞선 결정 `0038`(FastAPI+Jinja2) ·
`0039`(계약 두 겹) · `0026`(개인정보 최소수집) · `0037`(수익화 없음) · `0010`(공시는 월 1회)

**사전등록이 없다.** 설계 결정이고, 완료 조건은 회귀다(CLI 무변동 · A1~A13 · 서버·CLI 대조).

## Decision

**서버가 아무것도 저장하지 않는다.**

```
D1  **답(state)을 서버에 저장하지 않는다.** 클라이언트가 매 요청에 실어 보낸다
D2  **DB 를 두지 않는다.** 읽는 것은 읽기 전용 스냅샷이고 쓰는 것이 없다
D3  **엔드포인트는 사실상 하나다** — `POST /api/screen`.
    무상태에서는 *"답 하나를 더 받는다"* 가 *"답이 하나 더 들어간 state 로 다시
    그린다"* 와 같은 일이다
D4  **스냅샷은 프로세스 안에서 캐시한다** — `(스냅샷, 권역, 기간)` 하나당 한 번.
    월 1회만 갱신되므로(`0010`) 캐시가 틀릴 자리가 없다
D5  **클라이언트 입력을 믿지 않는다** — 답에 모르는 조건 유형이 오면 400 으로 거른다.
    이것이 무상태의 대가다
D6  **127.0.0.1 에만 묶는다** — 로컬 전용 (`0037` 의 전제)
```

## Evidence

### 무상태가 가능한 이유는 상태가 작아서다 — 실측

```
질문 15개를 다 답한 state          466B
스코프·기간·선호까지 합쳐도         1KB 아래
```

**답을 요청에 실어 보내는 것이 부담이 아니다.** 반대로 서버에 두면 세션 저장소·만료·
재시작 대비가 따라온다.

### 얻는 것 셋

```
개인정보   `0026` 의 반증 조건이 **발동하지 않는다** — "우대조건 답을 저장하면 수집
          최소화와 충돌할 수 있다. **저장·계정 기능을 만드는 순간 이 결정을 다시
          본다**". 저장하지 않으면 다시 볼 일이 없다
이어하기   D9 가 **공짜다** — 클라이언트가 자기 state 를 보관하면 서버 재시작과 무관하다.
          서버 세션이면 재시작에 날아간다
되돌리기   나중에 세션 저장을 얹는 건 쉽고, 걷어내는 건 어렵다
```

### DB 가 없는 이유는 "서버가 없어서" 가 아니다

DB 가 필요해지는 조건은 **서버의 존재**가 아니라 **상태의 성질**이다.

```
① 사용자가 만든 상태가 프로세스보다 오래 살아야 한다
② 그 상태를 여러 요청·여러 사용자가 공유한다
③ 동시에 쓴다
```

셋 다 없다. 읽는 것은 월 1회 갱신되는 읽기 전용 스냅샷이고, 쓰는 것은 D1 로 없앴다.
**보통 웹앱이 DB 를 갖는 이유는 계정·주문·게시물처럼 사용자가 만든 상태인데, 우리는
그걸 안 만들기로 정했다**(`0037` 가입 안 받음·수익화 없음 · `0026` 개인정보).
**DB 가 없는 건 생략이 아니라 제품 결정의 결과다.**

### 규모가 DB 의 강점이 의미를 갖는 구간이 아니다 — 실측

```
전 기간·전 권역 행 1,081개 · 293KB      (+ 추출 결과 한 벌 ~500KB)
서버가 시작할 때 드는 것   은행권 311KB / 47ms · 저축은행 288KB / 94ms
요청 하나                score_all 16ms · view.build 0.0ms · 리포트 10개 0.0ms
응답                     상위 10개 33~36KB · 전체 153KB
```

**전체가 1MB 아래다.** 인덱스·조인·쿼리 최적화가 이길 자리가 없다. 그리고 요청마다
스냅샷을 다시 읽으면 **50~94ms 가 계산 16ms 보다 커진다** — 그래서 D4 로 캐시한다.

### 서버가 존재하는 이유는 계산기가 파이썬에 있어서다

정적 페이지로 가려면 둘 중 하나인데 둘 다 막힌다.

```
JS 로 계산기 재구현     계산이 두 군데 → 두 답 (`problem.md` §7)
미리 계산해 굽는다      은행권 12개월 질문 15개 × 예/아니오/모름 = 3^15 = 1,435만 상태.
                     응답 33KB 이니 약 475GB. 문구 단위로 세면 39개라 3^39 이고
                     스코프·선호·기간 조합이 여기에 **곱해진다**
```

즉 서버는 **"이미 있는 계산 함수를 HTTP 로 감싼 것"** 이다. 감싼다고 저장할 것이
생기지는 않는다.

### 같은 뷰 모델을 내는지 대조했다 — 원리상 같다는 것과 실제로 같다는 것은 다르다

`src/web/check_api_parity.py` 를 만들어 두 경로를 같은 입력으로 돌렸다.

```
케이스 6개   미응답 · 답 둘 · 모름 섞임 · 저축은행 · 스코프+선호 · 전체 목록(67개)
             → **전부 동일** (JSON 왕복의 튜플→리스트만 정규화)
에러 계약 6개  없는 스냅샷 400 · 없는 기간 400 · 모르는 조건 400 · 빈 스코프 400 ·
             잘못된 선호 400 · 모르는 필드 422 → **전부 기대대로**
```

**에러 계약을 따로 검사하는 이유**는 CLI 와 서버의 요구가 다르기 때문이다 — CLI 는
`SystemExit` 로 죽어도 되지만 서버는 4xx 로 답해야 한다. `AB.load()` 가 던지는
`SystemExit` 을 서버가 잡아 400 으로 바꾼다.

### 뷰 모델에 질문 칸이 없었다 — `0039` 가 예고한 자리다

웹이 *"다음 질문이 무엇인가"* 를 물으니 뷰 모델에 **질문 수만 있고 질문이 없었다.**
`0039` 반증 조건이 이 경우를 미리 적어 뒀다 — *"뷰 모델에 없는 값이 필요하면 칸을
늘리되 **CLI 렌더러도 그 칸을 쓰게** 한다. 한쪽만 쓰는 칸이 생기면 D1 이 무너진다."*

그대로 했다 — `view.next_question()` 을 만들고 **CLI 루프도 그것을 쓴다**(전에는
루프가 자기 자리에서 `rank_questions` 를 불러 첫 항목을 집었다). 순서 규칙이 두
군데가 될 자리를 막았다.

**`outside_best()` 도 옮겼다** — 스코프 밖 최고 금리(A7)를 만드는 함수가 렌더러
(`ask_loop`)에 있었다. 그건 **그리는 것이 아니라 사실을 만드는 것**이고, 렌더러에
두면 서버가 CLI 모듈을 import 해야 한다. `view.py` 로 옮겼다.

### 실행 환경을 `.venv` 로 옮겼다

전례가 갈려 있었다 — `pdfplumber` 는 **전역**에 깔려 있는데 `.gitignore` 에는
`.venv/`·`venv/` 자리가 이미 있었다. 사람이 `.venv` 를 골랐다.

```
python -m venv .venv
source .venv/Scripts/activate      # Git Bash. PowerShell 은 .venv\Scripts\Activate.ps1
pip install -r requirements.txt    # pdfplumber 까지 전부 — 반쪽 venv 를 만들지 않는다
```

**활성화하면 기존 명령이 그대로 돈다** — 문서의 `python src/...` 를 고치지 않았다.
전역에 깔지 않은 이유는 `0038` 의 반증 조건이다 — *"의존성 때문에 실행이 번거로워지면
CLI 경로가 방치되기 시작하는 것이 신호다."* 전역에 깔면 그 신호를 관측할 기회가 사라진다.

## Alternative

- **A. 서버 세션 (메모리 dict + 세션 id)** — 요청이 작아지고 클라이언트가 단순해진다
- **B. 세션을 파일이나 SQLite 에 저장한다** — 재시작에도 살아남고 이어하기가 서버 쪽에서 된다
- **C. 지금 DB 를 넣는다** — 나중에 옮기는 비용을 미리 없앤다
- **D. 스냅샷을 캐시하지 않고 요청마다 읽는다** — 파일을 갈아끼우면 즉시 반영된다
- **E. 엔드포인트를 둘로 나눈다** (`/api/session` · `/api/answer`) — 흐름이 드러난다

## Why rejected

- **A** — 얻는 것이 요청 1KB 절약뿐이고, **`0026` 의 반증 조건을 건드린다.** 세션에
  답이 들어가는 순간 "서버가 우대조건 답을 들고 있다" 가 되고, 재시작·만료·정리를
  다뤄야 한다. 이어하기도 서버 수명에 묶인다
- **B** — A 의 문제에 **저장까지 더한다.** `0026` 이 *"저장·계정 기능을 만드는 순간
  이 결정을 다시 본다"* 로 못 박은 그 자리다. 이어하기는 클라이언트 보관으로 이미 된다
- **C** — 위 Evidence. 데이터가 1MB 아래이고 쓰기가 없다. 그리고 **스냅샷의 정직성을
  갉는다** — `collection-pipeline.md` 가 *"스냅샷은 그때 API 가 뭐라고 했는지의
  기록이므로 우리가 고치면 안 된다"* 고 적어 뒀는데 DB 는 upsert·마이그레이션을
  유혹한다. `CLAUDE.md` 1번(**구조 먼저, 쓸 곳은 나중**)이 막는 모양이다.
  **DB 가 정당해지는 조건은 넷이고 지금 하나도 안 걸린다** — 답 저장 · 스냅샷 여러 달치
  질의(지금 2개월치뿐이라 물어볼 게 없다. 그때도 DuckDB/SQLite 다) · A2 코퍼스 검색
  (그때도 RDB 가 아니라 벡터 인덱스다) · 멀티유저 세션(안 하기로 한 것)
- **D** — 50~94ms 가 계산 16ms 보다 크다. 스냅샷 교체는 **재시작으로 반영한다** —
  월 1회짜리에 매 요청 비용을 내지 않는다
- **E** — 무상태에서는 두 엔드포인트가 **같은 일**을 한다. 나누면 "답 하나만 받는"
  엔드포인트가 실제로는 state 전체를 받아야 해서 이름이 거짓이 된다

## 반증 조건

- **요청이 커져서 문제가 되면** — 지금 466B 다. 질문이 늘거나(문구 단위로 39개) 스코프가
  복잡해져 **10KB 를 넘으면** A 안(서버 세션)을 다시 본다
- **클라이언트가 보낸 state 가 서버를 깨뜨리면** — D5 의 검증이 모자란 것이다. 지금은
  조건 유형만 본다. **값의 형태**(수치 자리에 문자열 등)로 깨지면 검증을 값까지 넓힌다
- **이어하기를 만들었더니 사용자가 state 를 잃으면** — 클라이언트 보관이 실제로는
  안 되는 것이다(브라우저 저장소 삭제 등). 그때는 **사용자가 파일로 내려받는** 쪽을
  먼저 보고, 그래도 안 되면 B 안을 본다
- **스냅샷 캐시 때문에 옛 데이터를 보여주면** — 월 갱신 뒤 재시작을 잊은 경우다.
  `/api/health` 가 무엇을 들고 있는지 내므로 그것으로 확인한다. 자주 겪으면
  파일 mtime 을 보고 자동으로 버리는 쪽으로 바꾼다
- **서버·CLI 대조가 통과하는데 화면이 다르면** — 대조는 뷰 모델까지만 본다. 렌더가
  다르면 잡지 못한다. **그래서 F4-2 에서 웹 렌더러에도 렌더 겹을 건다**(`0039` D3)
