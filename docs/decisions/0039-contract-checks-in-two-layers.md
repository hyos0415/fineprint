# 0039 · 화면 계약을 두 겹으로 건다 — 그리고 A1 은 계약을 안 보고 있었다

> 날짜: 2026-09-01 · 상태: 유효

로드맵 F4-0 · 이슈 [#36](https://github.com/hyos0415/fineprint/issues/36) ·
계획 [`ui-plan.md`](../spec/ui-plan.md) · 앞선 결정 `0035`(A12·A13) · `0036`(리포트도
계약을 진다) · `0026`(화면 계약을 assert 로 박는다)

**사전등록이 없다.** 구현이고, 완료 조건은 **회귀**다 — CLI 출력 무변동 + A1~A13 통과.

## Decision

**화면 계약을 두 겹으로 가른다.**

```
모델 겹   view.check_model(vm)      뷰 모델에 **사실이 담겼나**
                                   렌더러가 무엇이든 같다. 위반에 `[모델]` 이 붙는다
렌더 겹   check_screen_contract     그 사실을 **실제로 출력했나**
                                   렌더러마다 건다 (CLI 화면 · 리포트, 나중에 웹)
```

정한 것 넷.

```
D1  화면이 내놓을 것을 `src/analysis/view.py` 의 **뷰 모델 하나**로 모으고,
    `render_final_screen()` 이 **그것을 거쳐** 그린다. 웹 렌더러도 같은 것을 받는다

D2  **상품 dict 를 복사하지 않는다.** `vm["products"]` 는 `evaluate()` 가 낸 그 객체다.
    복사하면 뷰 모델과 화면이 서로 다른 값을 들 수 있다

D3  **문자열 검사를 없애지 않는다.** 두 겹이 잡는 것이 다르다 — 아래 Evidence 가
    실측이다

D4  `status_lines()` 를 **사실(`status_facts`) + 렌더**로 가른다. 상태바는 이미
    `st` 를 돌려주고 있었고(A4·A6 이 그것을 읽는다), 나머지만 문자열이었다
```

## Evidence

### 두 겹이 정말 다른 것을 잡는지 음성 검사로 확인했다

**둘을 따로 망가뜨렸다.**

```
(가) 렌더만 망가뜨린다   product_line 이 최대값 하나만 출력하게 한다
(나) 모델만 망가뜨린다   vm 의 사유 문장을 비운다
                       (렌더러는 C.CAVEAT 에서 직접 꺼내므로 화면은 멀쩡하다)
```

```
                        모델 겹    렌더 겹
고치기 전                  0건       0건
(가) 렌더만 망가뜨림        0건    **61건**   ← A1
(나) 모델만 망가뜨림     **4건**      0건     ← A3
```

**둘 다 필요하다는 것이 이 표다.** 모델 겹만 있으면 (가)를 놓치고, 렌더 겹만 있으면
(나)를 놓친다. 웹 렌더러가 붙으면 (가)의 자리가 하나 더 늘어난다.

### 그런데 (가)가 처음에는 **양쪽 다 0건**이었다 — A1 이 계약을 안 보고 있었다

```python
# 고치기 전 (check_screen_contract.check_state)
line = L.product_line(i, s)
width = s["net_hi"] - s["net_lo"]
if width > EPS and "~" not in L.span(s):        # <- line 이 아니라 span(s) 를 본다
    bad.append({"assert": "A1", "product": s["name"], "detail": line})
```

**`L.span(s)` 는 헬퍼의 출력이다.** 이 검사는 *"span() 이 범위를 만드나"* 를 볼 뿐
**화면이 그 값을 실제로 썼는지는 보지 않았다.** `line` 은 위반 메시지에만 쓰였다.

그래서 렌더러를 최대값만 출력하도록 바꿔도 **A1 이 통과했다.** 화면 계약 검사의
1번 항목이 화면을 안 보고 있었던 것이다.

```python
# 고친 뒤
if width > EPS and "~" not in line:
```

**이 결함은 `0035` 가 찾은 것과 같은 종류다** — 그때는 데이터가 있는데 한 화면에만
라벨이 없었고, 이번에는 검사가 렌더 대신 헬퍼를 보고 있었다. 둘 다 *"어디를 보고
있나"* 를 안 물어서 생겼다.

**리포트 쪽 A1 은 멀쩡했다**(`0036` 에서 만들 때 렌더된 블록을 봤다) — 나중에 만든
쪽이 맞았고 원래 것이 틀렸다.

### 회귀 — CLI 출력이 한 글자도 안 바뀌었다

권역 2 × 상태 5(+스코프 1)에서 화면·상태·리포트를 전부 떠서 대조했다.

```
status_facts 분리 뒤     화면 문자열 차이 0줄 (st dict 에 키 셋이 늘었다 — 추가만)
뷰 모델 경유 뒤           차이 0줄
A1 수정 뒤               차이 0줄
```

## Alternative

- **A. 문자열 검사를 전부 모델 검사로 바꾼다** — 렌더러가 늘어도 검사가 하나다
- **B. 뷰 모델을 만들되 렌더러는 그대로 두고, 검사만 뷰 모델을 본다**
- **C. F4-2(웹)까지 간 뒤에 그때 계약을 옮긴다**
- **D. Pydantic 모델로 뷰 모델을 정의한다** (`0038` 이 FastAPI 를 정했으므로)
- **E. `st` 를 그대로 뷰 모델로 쓴다** — 새 파일을 만들지 않는다

## Why rejected

- **A** — 위 표 (가) 열이 반례다. **데이터가 있어도 안 그릴 수 있다.** 모델 검사만
  남기면 `0035` 가 찾은 실패(한 화면에만 라벨이 없었다)를 다시 못 잡는다
- **B** — **뷰 모델이 화면과 드리프트한다.** 렌더러가 안 쓰는 모델은 "화면이 무엇을
  보여주는가" 의 기록이 아니라 별도의 사본이 되고, 둘이 갈라져도 아무도 모른다.
  그래서 D1 에서 **렌더러가 거쳐 가게** 했다
- **C** — 그 순간 검사를 **HTML 문자열에 대고 다시 써야 한다.** `ui-plan.md` 가
  F4-0 을 첫 작업으로 둔 이유이고, 실제로 이번에 **옮기는 과정에서 A1 의 결함이
  드러났다** — 웹을 먼저 만들었으면 그 결함 위에 화면을 하나 더 얹었을 것이다
- **D** — 의존성 추가는 F4-1 의 일이다(`0038` — `requirements.txt` 에 사유를 적는 것이
  그 단계의 완료 조건이다). F4-0 을 표준 라이브러리로 끝내면 **회귀 검증이 끝난 뒤에**
  의존성을 얹을 수 있다. 순서를 바꾸면 둘이 섞여 무엇이 깼는지 모른다
- **E** — `st` 는 상태바의 사실이다. 상품 목록·사유 문장·스코프 밖·고지가 없다.
  넓히면 결국 뷰 모델이 되는데, 그러면 상태바 dict 라는 이름이 거짓이 된다

## 반증 조건

- **웹 렌더러(F4-2)를 붙였는데 뷰 모델에 없는 값이 필요하면** — 모델이 화면 요구를
  못 담은 것이다. 그때는 칸을 늘리되 **CLI 렌더러도 그 칸을 쓰게** 한다. 한쪽만 쓰는
  칸이 생기면 D1(렌더러가 거쳐 간다)이 무너진다
- **모델 겹이 통과하는데 웹 화면에서 계약이 깨지면** — 렌더 겹을 웹에 안 건 것이다.
  렌더러가 늘 때마다 렌더 겹을 하나 더 건다는 것이 D3 다
- **`[모델]` 위반이 한 번도 안 나오면** — 모델 검사가 아무것도 안 보고 있을 수 있다.
  **음성 검사를 회귀로 승격한다**(지금은 손으로 돌렸다). 이 결정에서 만든 스크립트가
  그 뼈대다
- **A1 처럼 "헬퍼를 보는" 검사가 또 있으면** — 이번에 A1 하나를 찾았지만 나머지를
  전수로 훑지는 않았다. A2·A5·A9 는 객체 검사라 해당이 없고, A7·A8·A10 은 `screen` 을
  직접 본다. **A3 는 `screen` 을 본다**(확인함). 그래도 렌더러가 늘면 다시 봐야 한다
