# 0060 · R2 는 스코프 네 칸까지다 — 조건 답 제안은 기각을 재확인하고, 은행 목록은 확인 없이 쓰지 않는다

2026-09-07 · 이슈 [#73](https://github.com/hyos0415/fineprint/issues/73) · `prereg-28` §5~§8 · 앞선 `0058`(1차 기각) · `0059`(2차 · 결정 재료) ·
`0057`(방향 · 확인 없이 들어가는 값 0) · `0042`(원안 — 화이트리스트 넷)

## Decision

**사람이 확정했다 (2026-09-07)** — *"사람이 수정하는 화면을 만드는 게 맞다고 보는데, 사실 100퍼센트로 성공을 했다고 하더라도 사람 수정본은
넣으려고 했음. 내가 관찰하지 못했지만 100퍼센트 신뢰할 수는 없어서"*. 즉 HITL(사람이 고치는 단계)은 정확도와 무관하게 **원래부터 들어갈
것**이었고, 이 실험이 정한 것은 그 화면에 무엇을 올리느냐(스코프 네 칸)다.

```
D1  **조건 답 제안은 기각을 재확인한다.** 어려운 표본(TEST2 · 부정문 · 보고 싶은 은행 ≠ 거래 은행)에서 4B 로컬 모델은 30문장 중 8문장에 화면까지
    갈 오답을 냈다(9건 · 뒤집힘 · 지어낸 추론 · 권역 혼동). 쉬운 표본(TEST)의 0 은 운이었다. 확인 화면을 붙여도 셋 중 하나가 틀린 제안이면
    확인이 형식이 된다 — 만들지 않는다
D2  **R2 의 범위는 `0042` 원안으로 돌아간다 — 스코프 네 칸**(권역 · 상품군 · 기간 · 금액). 이 넷은 세 표본 100문장에서 권역 97% ·
    상품군 100% · 기간 100% · 금액 80~100% 였고, 틀려도 "좁히지 못함" 이지 "금리를 과대 진술" 이 아니다. 폼에 **미리 채워진 값**으로 보이고
    사용자가 고쳐서 제출한다 — 이것이 확인이다
D3  **거래 은행 목록은 자연어에서 채우지 않는다.** 역할 스키마(v5)가 두 목록(v3)보다 낫지만(틀린 은행 3 → 0~1) 0 이 아니고, 이 목록은 F6 이
    다른 답을 유도하는 자리라 하나가 틀리면 조건 여럿이 같이 틀린다. 목록 질문은 지금처럼 사용자가 직접 고른다. **은행 역할 스키마는 남긴다** —
    "보고싶음" 은 스코프의 은행 칸 후보로만 쓸 수 있다(D2 의 다섯째 칸 · 틀려도 좁히기만 달라진다)
D4  재확인 호출(정답만 6개 뺌)과 근거 대조 필터(0건)는 **쓰지 않는다.** 코드는 실험 기록으로 남긴다
D5  `0057` 의 D1(조건 답 후보를 화이트리스트에 더한다)은 **철회**한다. D2(확인 없이 들어가는 값 0)·D3(로컬 · 원문 폐기)·D4(기각도 결론)는 그대로다
D6  화면 작업 — 0단계 폼에 "내 상황" 상자(선택) → 로컬 모델이 스코프 다섯 칸(권역·은행·상품군·기간·금액)을 **폼에 미리 채운다** → 사용자가
    고쳐서 "목록 보기". 서버는 원문을 응답 뒤 버린다. 상자를 비우면 지금과 같다. 지연 4초는 대기 표시 한 줄로 충분하다
```

## Evidence

`prereg-28` §5~§8. 세 표본에서의 조건 답 화면 오답 — DEV 2/40 · TEST 0/30 · TEST2 9/30. 오답의 모양 셋(뒤집힘 · 지어낸 추론 · 권역 혼동)이
1차부터 반복됐고, 그동안 화면 0 을 만들어 준 것은 **오답 키가 우연히 후보 집합 밖이었던 것**이다. TEST2 에서 그 우연이 사라지자 30% 가 됐다.

스코프 네 칸은 반대로 표본이 어려워져도 거의 안 흔들렸다(TEST2 권역 29/30 · 상품군 30/30 · 기간 30/30 · 금액 24/30 — 금액 6건은
"5천" 처럼 단위를 생략한 문장). 이 칸들은 폼의 값이라 **틀려도 사용자가 제출 전에 본다.**

**사람의 물음** — *"HITL 도입으로 LLM 이 잘못 추출한 걸 스스로 수정 조금 할 수 있게는 해두고 싶은데"*. D2·D6 이 그 모양이다 — 모델이 채우고
사람이 고친 뒤 제출한다. 다만 고칠 것이 **다섯 칸**이면 사람이 실제로 보고, 조건 답 스무 개면 보지 않는다. 그래서 범위가 다섯 칸이다.

## Alternative

- **A. 전부 제안·전부 확인** (`0059` 의 A) — TEST2 로 기각. 30% 오답을 확인 화면에 올리는 것은 사용자에게 검수를 시키는 것이다
- **B. 더 큰 모델** — 1차에서 9B·7.8B 가 4B 보다 낫지 않았고, 8GB 위로는 못 올린다. 클라우드는 `0042` D1 위반
- **C. 프롬프트·스키마를 더 고친다** — 다섯 판(v1~v5·hybrid)에서 조건 답 오답은 2~9 사이를 오갔고 수렴하지 않았다. 표본을 어렵게 하면 올라간다.
  이 방향은 "몇 번 더" 가 아니라 "모델이 바뀌어야" 하는 자리다
- **D. 미세조정(LoRA)** — 합성 문장으로 4B 를 학습시키는 길. 비용이 크고 데이터도 합성뿐이다. 사람 세션에서 자연어 수요가 관측된 뒤에 본다
- **E. R2 전부 닫기** — 스코프 네 칸은 값이 있고(폼 채우기가 30초 → 문장 하나) 위험이 없다. 닫을 이유가 없다

## Why rejected

위에 같이 적었다.

## 반증 조건

- **스코프 미리 채움에서 사용자가 고친 칸이 사람 세션 기준 20% 를 넘으면** — D2 의 정확도 가정이 실제 문장에서 안 서는 것이다. 상자를 뺀다
- **8GB 에 올라가는 모델이 TEST2 에서 조건 답 화면 오답 0 을 내면** — D1 을 다시 잰다(새 표본으로 · TEST2 는 이미 봤다)
- **사람 세션에서 "은행도 말로 넣고 싶다" 가 반복되면** — D3 의 은행 역할 스키마를 **제안 + 확인**으로 목록 질문에 붙이는 실험을 연다(그때 새 사전등록)
- **"5천" 처럼 단위 없는 금액을 모델이 잘못 읽어 화면에 큰 금액이 미리 채워지면** — 금액 칸은 미리 채우지 않고 비운다(TEST2 금액 6건 오답이 전부 이 모양)
