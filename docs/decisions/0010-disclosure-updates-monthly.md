# 0010 — 공시는 월 단위로 갱신된다. "4일 만에 바뀐다"를 정정하고 E8을 다시 정의한다

> 날짜: 2026-08-26 · 상태: 유효 · `../spec/prereg-01-savings-scope.md` §4.3 정정

## Decision

세 가지를 정한다.

1. **"공시가 4일 만에 바뀐다"는 해석을 정정한다.** 공시는 **매월 20일 전후에 한꺼번에
   갱신되고, 같은 달 안에서는 바뀌지 않는다.** `prereg-01` §4.3이 관측한 3건은
   4일간의 변화가 아니라 **월 갱신 경계를 넘은 것**이다
2. **수집 주기를 월 1회로 한다.** Airflow를 일간으로 돌리지 않는다
3. **E8(갱신 시 사람 손이 몇 건 필요한가)의 질문을 다시 정의한다.**
   "며칠마다 얼마나 바뀌나"가 아니라 **"월이 바뀌면 얼마나 바뀌나"**다.
   9월 공시가 올라와야 잴 수 있다

## Evidence

**직접 재봤다.** 은행 예적금 97상품을 2026-08-26에 다시 받아 `20260824`와 비교했다.

```
상품 수          97 → 97      추가 0 · 삭제 0
조건 문구 변경    0 / 97
금리 변경        0 / 97
```

**공시 메타데이터가 이유를 설명한다.**

| | 20260824 수집 | 20260826 수집 |
|---|---|---|
| 공시월 `dcls_month` | 202608 | 202608 (동일) |
| 공시 시작일 `dcls_strt_day` | 8/20 에 95건 · 8/21 에 2건 | 동일 |
| 회사 제출일 `fin_co_subm_day` | 8/20 에 91건 · 8/21 에 6건 | 동일 |

**8/20이 8월 공시가 올라온 날이다.** `prereg-01` §4.3이 비교한 8/20 데이터는 선행
프로젝트가 갱신 경계 근처에서 받은 것이고, 8/24 데이터는 확정된 8월 공시다.
그래서 3건이 달랐다. 같은 달 안에서 다시 재면 0건이다.

**저축은행은 며칠에 걸쳐 들어온다.**

```
저축은행 79곳 공시 시작일   8/20 318건 · 8/24 35건 · 8/22 20건 · 8/21 18건
은행 17곳                  8/20 95건 · 8/21 2건        거의 같은 날
```

## Alternative

- **(가) 기존 해석 유지** — "4일 만에 바뀐다"를 그대로 두고 일간 수집
- **(나) 정정하되 기록을 다시 쓴다** — `prereg-01` §4.3을 고쳐 쓴다
- **(다) 더 긴 간격으로 여러 번 재보고 정한다**

## Why rejected

- **(가) 유지**: 실측이 0건이다. 그리고 일간 수집은 API에 불필요한 부하를 주고,
  "매일 재추출해야 하니 AI가 필요하다"는 잘못된 근거를 만든다
- **(나) 기록 재작성**: `prereg-01` §4.3의 **관측은 사실이다** — 3건이 실제로 달랐다.
  틀린 것은 그 원인에 붙인 해석이다. 관측을 지우면 왜 그런 결론에 이르렀는지 추적할 수
  없다. **정정 배너를 붙이고 원문을 남긴다** (`0003`이 선행 결론을 정정할 때 쓴 방식)
- **(다) 더 재보기**: 공시 메타데이터(`dcls_month`·`dcls_strt_day`)가 이미 이유를
  설명한다. 추가 관측 없이도 왜 0건인지 안다. 다만 **월 경계 관측은 여전히 필요하고**,
  그게 E8이다

## 따라오는 결과

**(1) Airflow 설계가 바뀐다.**

```
바뀌기 전   매일 수집 → 매일 재추출
바뀐 뒤     월 1회 수집 (매월 20일 전후) + 갱신 감지
            "이번 달 것이 다 들어왔나" 판정이 필요하다 — 저축은행이 흩어져 들어온다
```

**(2) AI 재추출 비용이 거의 문제가 아니다.**

```
전체 재추출  월 1회 · 228쌍 · $1
폴백 구조면   39%만 호출
연간          약 $12
```

"매달 다시 만들어야 하니 AI가 필요하다"는 근거가 **약해진다.** 월 1회 $1이면
사람이 손보는 것과 비교할 값어치가 크지 않다. **E8이 답해야 할 것이 더 중요해졌다** —
월 경계에서 규칙 파서가 몇 건 깨지는가.

**(3) 기준 스냅샷을 확보했다.** `20260826`(은행 예적금 97상품). 9월 공시가 올라오면
이것과 비교한다.

## 반증 조건

- **9월 공시 전에 `20260826`과 다른 데이터가 관측되면** → "같은 달 안에서 안 바뀐다"가
  틀린 것이다. 월 단위 수집으로는 부족하다
- **저축은행에서 같은 달 안에 변화가 관측되면** → 권역마다 갱신 방식이 다르다는 뜻이고,
  수집 주기를 권역별로 나눠야 한다. 은행권에서만 확인했으므로 열려 있는 가능성이다
- **9월 경계에서 바뀐 상품이 5% 미만이면** → 규칙 파서를 손보는 비용이 매우 낮다는 뜻이고,
  R1에서 AI가 필요하다는 근거가 약해진다. `0004`의 첫 번째 반증 조건과 같은 방향이다
- **`dcls_strt_day`가 이번 달인 기관 수가 며칠이 지나도 100%에 안 닿으면** →
  "수집 완료"를 판정하는 기준을 다시 잡아야 한다
