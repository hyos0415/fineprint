# 0024 · 되묻기 흐름을 정의한다 — 전부 묻고, 남은 수는 줄어들기만 한다

2026-08-27 · 설계 [`../spec/design.md`](../spec/design.md) §되묻기 흐름 ·
앞선 결정 `0015`·`0016`·`0017`(되묻기 3종) · `0018`(질문 예산) · `0023`(규칙 대신 되묻기)

## Decision

**질문 수를 제한하지 않는다. 전부 묻는다.** 대신 언제 끝나는지 보여주고, 그 숫자가
**절대 늘어나지 않게** 만든다.

```
P1  질문에 공시 문구를 그대로 붙인다. 우리가 요약하지 않는다        (0016 유지)
P2  질문 수 제한 없음. `ASK_BUDGET = 12` 는 평가 지표로만 쓴다     ← 새로 정한 것
P3  되묻기는 편의가 아니라 이 시스템의 존재 이유다
P4  상태바에 숫자 둘을 나란히 놓는다 — 진행(남은 질문) · 성과(확정 상품)
P5  "모르겠다" 는 범위로 낸다. hi 를 내리지 않는다
```

**분모는 "모두 예" 를 가정한 최대치**다. 은행권 22개 · 저축은행 27개이고,
아무것도 안 물은 상태에서 추출 데이터만으로 미리 계산된다.

## Evidence

### P2 — 12개가 견딜 만한가는 애초에 질문이 아니었다

사람이 지적한 것이다.

> 질문이 12개가 견딜 만한가? 나는 이게 전혀 상관이 없을 거 같다고 보는게, 실제로
> 은행원이 업무를 할 때 전부 다 확인을 해야 하는 부분이잖아? 모른다고 임의로 체크하고
> 넘어가도 되는 부분이 절대 아니야. 실제 행원 세일즈 면접 때도 비슷한 경험을 했어.
> 다만 이 질문이 언제 끝나는지는 상태바로 알려주면 좋을 거 같아.

**`0018` 의 예산 12개는 원래 평가 지표였고**(질문 부풀리기 방지), 사용자 화면에 그
제한을 옮겨 붙일 이유가 없었다. 전부 물으면 `0023` 이 찾은 개선도 사용자에게 도달한다 —
그 개선은 13번째 질문 뒤에 있다.

전부 답하면 질문이 몇 개인지 실측했다. **행원 면담 한 번 분량이다.**

| | 전부 답하면 | 유형 질문 | 수치 후속 |
|---|---|---|---|
| 은행권 | 22개 | 15 | 7 |
| 저축은행 | 27개 | 13 | 14 |

### P1 — 공시 문구를 그대로 붙이는 것이 맞다

`"기존고객 경남은행 카드이용시(8회이상&10만원이상 카드대금 결제보유) 1.5%"` 같은 문구를
사용자가 읽을 수 있는지 걱정했는데, 사람이 기각했다.

> 경남은행 카드 이용시는 만약에 쓰는 사람이라면 나는 충분히 대답할 수 있을 거라고 보거든?

**그 상품을 쓸 사람에게 묻는 것**이므로 원문이 오히려 정확하다. `0016` 을 그대로 둔다.

### P4 — 남은 질문 수가 늘어나는 버그가 있었다

`rank_questions()` 는 **지금 물을 수 있는** 질문만 낸다. 유형에 "예" 라고 답하면 수치
후속 질문이 새로 생기므로 남은 수가 **늘어난다.**

```
은행권 15번째 질문 뒤   남은 5개
      16번째 질문 뒤   남은 6개   ← 늘었다. "급여이체 예" 가 금액 질문을 낳았다
줄지 않은 지점          은행권 6곳 · 저축은행 12곳
```

**해법은 사람이 냈다.**

> 예라고 했을 때를 상정하고 질문 수를 줄이는 식으로 보여주는게 더 맞을 거 같거든?
> 질문이 많았다가 줄어드는게 사용자 입장에서 체감 효과가 더 강하잖아

처음부터 "모두 예" 최대치를 분모로 쓰면 **구조적으로** 줄어들기만 한다. 그리고
"아니오"·"모르겠다" 는 그 유형의 수치 후속까지 같이 지우므로 **2~3개씩** 줄어든다 —
조건을 못 채우는 사용자일수록 빨리 끝나는데, 그게 실제로도 맞다(물을 게 정말 적다).

세 시나리오 전부 단조 감소를 실측으로 확인했다.

| 답한 질문 | 전부 "예" | 전부 "아니오" | 전부 "모르겠다" |
|---|---|---|---|
| 0 | 22 남음 · 확정 4/67 · 1위 5.92% | 22 · 4 · 5.92% | 22 · 4 · 5.92% |
| 5 | 17 · 16 · 5.92% | 14 · 17 · 5.12% | 14 · **4** · 5.92% |
| 10 | 12 · 38 · 5.92% | 8 · 48 · 4.06% | 8 · **4** · 5.92% |
| 끝 | 0 · **64**/67 · 5.92% (22개) | 0 · **65**/67 · 4.06% (15개) | 0 · **4**/67 · 5.92% (15개) |

### P4 의 둘째 숫자 — "모르겠다" 가 진전처럼 보이는 문제

남은 질문 수 **하나만** 보여주면 "모르겠다" 와 "아니오" 가 똑같이 진전으로 보인다.
둘 다 질문을 지우는데 "모르겠다" 는 금리를 하나도 좁히지 못한다.

**확정 상품 수가 그 차이를 정확히 가른다** — 끝까지 갔을 때 예 64 · 아니오 65 ·
모르겠다 **4**다. 실제 화면에서 4개를 답한 시점을 재보면 이렇다.

```
아니오 4개    진행 6/22    확정 17/67
모르겠다 4개   진행 6/22    확정  4/67     ← 진행은 같고 성과는 0
```

**나란히 놓으면 사용자가 대가를 스스로 본다.** 우리가 답을 강요하지는 않는다 —
P2 의 "임의로 체크하고 넘어가면 안 된다" 와 강요하지 않는 것을 둘 다 지키는 자리다.

### P5 — "모르겠다" 를 "아니오" 로 취급하면 반대 방향으로 거짓이 된다

사람이 방어적 표기를 위해 제안했다.

> 모르면 아니오랑 똑같게 보이는게 맞지 않을까 싶기도 한데. 왜냐면 방어적으로 표기를
> 해야지. 과장 광고 이슈를 니가 가져왔었잖아

**방어하려는 방향은 맞고, 그 방어는 이미 `lo` 에 있다.**

```
lo = group_totals(met)           충족 확인된 것만 더한다
                                 "모르겠다" 도 "아니오" 도 lo 에 한 푼도 안 들어간다
hi = group_totals(met + unknown) "모르겠다" 는 들어가고 "아니오" 는 안 들어간다
```

실측으로 확인했다 — `NH1934월복리적금` 은 4개를 "아니오" 로 답했을 때와 "모르겠다" 로
답했을 때 **lo 가 2.16% 로 동일**하다.

**hi 까지 내리면 방어를 넘어 단정이 된다.**

| 전부 "모르겠다" 로 답한 사용자 | 범위 유지 (채택) | 아니오로 취급 |
|---|---|---|
| 확정 상품 | 4/67 | **65/67** |
| 폭 평균 | 0.769%p | 0.039%p |
| 1위 | 5.92% | 4.06% |

**아무것도 모른다고 답한 사용자에게 "금리 확정 65개" 가 나온다.** 과대 진술을 막은
자리에 **"확정" 이라는 거짓 라벨**이 들어선다. 사용자는 정보를 하나도 안 줬는데 우리가
단정한 숫자를 내놓는 것이다.

그리고 **확인만 하면 받을 수 있는 좋은 상품을 순위에서 내린다.** 실측 — `카카오뱅크
우리아이적금` 은 "모르겠다" 에서 1위(2.54~5.92%)인데 "아니오" 로 취급하면 상위 3위 밖으로
밀린다. `0017` 이 *"최소 순으로 시작하면 좋은 상품이 묻힌다"* 로 막은 실패와 같은 모양이다.

**되묻기의 값어치도 숫자로 나왔다.** 아무것도 안 물으면 두 사용자에게 똑같이 5.92% 를
보여주는데, 조건을 못 채우는 사용자의 실제 최대는 4.06% 다 — **과대 진술 1.86%p.**
`ask_budget.py` 가 이미 이 칼럼을 찍고 있었다. 사람이 3번에서 말한 *"저게 없으면 이
서비스의 필요성이 없다"* 가 이 숫자다.

### 지금까지 모든 측정이 "예" 로만 답한 사용자였다

`condition_met()` 은 처음부터 `False` 를 처리했는데 **입력 경로가 없었다** —
`--state` 가 True·숫자·`모름` 만 만들었다. `--state '유형=아니오'` 를 채웠다.

**기준선은 안 움직였다** (은행권 확정 39/67 · 폭 0.176 · 커버리지 84.8% · 저축은행
88/106 · 0.277 · 35.7%). 평가 경로가 "아니오" 를 쓰지 않으므로 당연하지만 확인했다.

## Alternative

| | 방법 | 왜 안 골랐나 |
|---|---|---|
| A | 질문을 12개로 제한한다 | 행원은 전부 확인한다. 임의로 체크하고 넘어가는 것이 이 프로젝트가 막으려는 실패다 |
| B | 질문을 2단계로 나눈다 (유형 → 수치) | 분모가 안 늘어나게 하는 데는 되지만, "모두 예 최대치" 가 더 단순하고 체감도 낫다. Agent 제안이었고 사람 안이 이겼다 |
| C | 남은 질문 수만 보여준다 | "모르겠다" 가 진전으로 보인다. 실제 진전은 0 이다 |
| D | "모르겠다" 를 "아니오" 로 취급한다 | 확정 4 → 65. 방어가 아니라 단정이 된다. 위 실측 |

## 반증 조건

- **사용자가 22~27개 질문에서 중간에 그만두면** — P2 가 틀린 것이다. 그때는 어디서
  그만두는지를 재서, 상위 N개만 묻고 나머지는 `미응답` 사유로 내는 쪽을 본다
- **상태바 분모가 사용자에게 너무 커 보여 시작 자체를 막으면** — 22개를 처음부터
  보여주는 것이 역효과다. 그러면 B(2단계)로 돌아간다
- **"모르겠다" 비율이 절반을 넘으면** — 질문이 답할 수 없는 형태라는 뜻이다.
  P1(공시 문구 원문)을 다시 봐야 한다
- **확정 상품 수가 사용자에게 성과로 읽히지 않으면** — P4 의 둘째 숫자가 제 일을 못
  하는 것이다. 폭 평균이나 1위 금리 변화로 바꿔 본다
- **"아니오" 를 넣은 뒤 확정률이 오히려 떨어지면** — 예상과 반대다. 지금 실측은
  전부 아니오가 65/67 로 전부 예(64/67)보다 **높다** (판정이 다 끝나기 때문이다)

## 남은 것

- **R2 의 자리가 바뀌었다.** 자연어에서 조건 답을 채우는 것은 P2 위반이다 —
  추정을 사용자 확인 없이 쓰는 것이기 때문이다. R2 는 **0단계 폼(기간·납입액) 채우기와
  질문 순서 미세조정**으로만 쓴다. `design.md` §R2 의 계약을 그렇게 좁혀 적었다
- **UI 가 아직 없다.** 위 흐름은 CLI 로만 돌아간다. `design.md` §화면 계약이 그대로 적용된다
