# 0036 · 비교 리포트는 "이 숫자가 어디서 왔나" 를 적고, 합이 안 맞는 자리를 숨기지 않는다

> 날짜: 2026-08-31 · 상태: 유효

로드맵 F1 · 이슈 [#33](https://github.com/hyos0415/fineprint/issues/33) ·
앞선 결정 `0017`(범위로 쓴다) · `0022`(배타 그룹은 밴드) · `0027`(문구를 자르지 않는다) ·
`0030`(선호는 정렬만) · `0035`(화면 계약 A12·A13) · `problem.md` §3 · §7

**사전등록이 없다.** 측정이 아니라 구현이다 — 만들기 전에 **재고 조사**로 "무엇이
없나" 를 세고(아래 Evidence), 만든 뒤의 검증은 **화면 계약 assert** 다(`0026` 방식).

## Decision

**리포트를 객체와 렌더로 가르고, 계산은 하지 않는다.**

```
report.build(s, rank, prefs)   상품 하나 → 리포트 객체 (숫자는 전부 evaluate() 의 값)
report.render(rep)             객체 → 텍스트
calculate.py --report N        상위 N개
```

정한 것 다섯.

```
D1  **`evaluate()` 가 조건별 근거를 버리지 않게 한다.** `met`/`unmet`/`unknown` 은
    이름만 남기는 채로 **그대로 두고**(화면 계약 검사·질문 루프가 그 모양을 읽는다),
    `why` 를 더해 조건별 %p · 공시 문구 원문 · 배타 그룹 · 임계 여부를 담는다

D2  **리포트는 금리를 다시 계산하지 않는다.** 여기서 하는 산수는 이미 있는 값의 차
    두 개뿐이다(`raw_lo - base` · `raw_hi - raw_lo`). 리포트가 자기 산수를 하면
    화면과 계산기가 서로 다른 숫자를 말할 수 있다

D3  **합이 안 맞으면 그 차이를 적는다.** 조건별 단순 합 ≠ 계산에 들어간 값이 되는
    자리가 둘이다 — 배타 그룹(`0022`)과 상품 상한(`cap`). 맞춰 보이지 않는다

D4  **계단의 칸 이름을 계산이 실제로 하는 일에 맞춘다** — `채운 조건`/`안 답한 조건`
    이 아니라 **`확실히 받는 우대`/`불확실한 우대`** 다. 실측에서 후자가 틀린 이름임이
    드러났다(아래 Evidence)

D5  **리포트도 화면 계약을 진다** — A1(범위) · A3(사유 문장) · A12(세후 라벨) ·
    A13(고지). 렌더가 하나 늘면 계약도 하나 늘린다 (`0035` 가 배운 것)
```

## Evidence

### 재고 조사 — 약속한 칸 14개 중 4개가 없었다

`problem.md` §3 **내놓는 것**이 약속한 화면과 지금 화면을 나란히 놓고 셌다
(2026-08-31 · 은행권 12개월).

```
없는 칸                     지금 상태
채운 조건의 %p              met 이 condition_type **이름만** 남긴다
못 채운 조건의 %p           같음
못 채운 이유(공시 문구 원문)   evidence 를 버린다
배타 그룹이 왜 걸렸나         caveats 에 코드(`중복우대불명`)로만
```

**그런데 원천에는 다 있었다.**

```
추출 항목 242개 · rate 가 있는 항목 238개(98.3%) · evidence 가 있는 항목 242개(100%)
calculate.py:903-905   "met": [i["condition_type"] for i in rng["met"]]   <- 여기서 버린다
```

`rng["met"]` 는 추출된 조건 dict 전체를 들고 있다 — 그게 금리 계산의 근거이기 때문이다.
**화면이 못 보여주는 게 아니라 데이터가 화면까지 오지 않았다.**

화면 쪽 실측이 같은 말을 한다.

```
상위 10개 상품의 추출 항목 27개 중 공시 문구가 화면에 있는 것   0개
화면 1,590자에 '기본' 0회 · '+' 0회 · '%p' 0회
```

### 만들면서 칸 이름이 틀린 것을 찾았다 — D4 가 그것이다

처음 계단을 `채운 조건` / `아직 안 답한 조건` 으로 썼다. 실측에서 숫자가 이름과
안 맞았다.

```
NH1934월복리적금 · 급여이체를 "예" 로 답한 상태

  채운 조건        조건별 단순 합 +2.00%p   계산에 들어간 것 +1.00%p
  안 답한 조건      조건별 단순 합 +2.50%p   계산에 들어간 것 +3.50%p   ← 1.00%p 가 어디서?
```

**답한 조건인데 중복 적용 여부가 불명한 몫**이 거기 섞여 있었다. 계산기는 보수(`lo`)
쪽에서 배타 그룹의 최댓값만 세고 낙관(`hi`) 쪽에서는 다 더하므로(`0022`), 그 차이가
`hi - lo` 에 남는다 — 그리고 `hi - lo` 를 "안 답한 조건" 이라고 부르면 **거짓말이 된다.**

그래서 칸을 `확실히 받는 우대` / `불확실한 우대(안 답한 조건 · 중복 적용 불명분)` 로
바꾸고, 차이의 출처를 짚어 적는다 — 위 경우 *"위에서 깎인 중복 적용 불명분이 여기
들어온 것이다"* 가 화면에 나간다.

### 최대값이 어떤 가정 위에 서 있는지도 적어야 했다

```
웰뱅 라이킷(LIKIT) 적금 (저축은행 · 12개월)
  기본 2.00% + 불확실한 우대 +12.00%p = 세전 최대 14.00% → 세후 11.84%

  그 12.00%p 의 정체
    카드실적  +2.00%p  (배타그룹 g1)  "롯데카드 결제계좌를 당행 입출금통장으로 지정…"
    카드실적  +7.00%p  (배타그룹 g1)  "LOCA LIKIT 카드 누적 이용실적 50만원 이상"
    자동이체  +3.00%p  (배타그룹 g1)  "LOCA LIKIT 카드 자동이체 납부 실적 3개월 이상"
```

**세 조건이 모두 같은 그룹인데 낙관은 셋을 다 더한다.** 하나만 받게 되면 최대는
7.00%p 짜리이고, 세전 최대가 14.00%가 아니라 9.00% 다. 조건 줄에 `배타그룹 g1` 이
붙어 있어도 **최대값 자체가 그 가정 위에 있다는 말**이 없으면 사용자는 12%p 를 다
받는 것으로 읽는다. 그래서 밴드가 있는 상품에는 그 문장을 항상 붙인다.

이 자리가 `0017` 이 막으려던 것과 같다 — 광고 금리를 그냥 보여주지 않고 **어떤
조건들로 이루어졌는지 분해해 보여주는 것**이 원래 하려던 일이다.

### 검사가 실제로 잡는다

```
음성 검사 — 리포트에서만 헤더를 빼고 돌렸다
  A13  **불통과 4건**  "[리포트] 성격 고지가 화면에 없다"
  A12  통과            리포트 본문의 각 상품 줄에 "(세후)" 가 있다 — 통과가 맞다

복원 뒤 — 은행권 시드 200 · 저축은행 시드 200 · 선호 있음(시드 30)
  A1~A13 전부 통과 (리포트 패스 4상태 포함)
```

리포트 검사는 **전 세션에서 돌리지 않는다** — 여기서 잡는 것은 상태에 따라 변하는
값이 아니라 **렌더 구조**다. 아무것도 안 답한 상태와 페르소나 끝 상태 셋에서 본다.

## Alternative

- **A. `met`/`unmet`/`unknown` 을 이름 목록에서 dict 목록으로 바꾼다** — `why` 를 따로
  두지 않는다
- **B. 리포트가 조건별 %p 를 직접 합쳐 금리를 낸다** — 계산기를 안 건드린다
- **C. 합이 안 맞는 것을 맞춰 보인다** — 배타 그룹·상한을 반영한 %p 를 조건별로 배분한다
- **D. F4(UI)를 먼저 만들고 리포트는 HTML 로 바로 쓴다**
- **E. R4(LLM 서술 문단)를 먼저 만든다** — 사람이 읽기에는 그게 더 친절하다

## Why rejected

- **A** — 그 모양을 **화면 계약 검사(A11)와 질문 루프가 읽는다.** 바꾸면 `0031` 이
  겪은 것과 같은 종류의 연쇄 수정이 되고, 이번 작업의 목적(없는 칸 채우기)과 무관한
  위험을 진다. `why` 를 더하는 쪽은 **기존 독자를 하나도 안 건드린다**
- **B** — 배타 그룹과 상한 때문에 **단순 합이 실제와 다르다.** 리포트가 자기 산수를
  하면 목록과 리포트가 서로 다른 최대값을 말하게 된다. 실제로 이번 실측에서 그 차이가
  한 상품에서 `+2.00 vs +1.00`, 다른 상품에서 `+2.50 vs +3.50` 이었다
- **C** — 배분 규칙을 우리가 발명하는 것이다. 어느 조건이 잘렸는지는 **공시가 안
  알려준다**(`0022` 가 라벨을 절반쯤 못 믿는다고 적은 그 자리다). 배분하면 그 불확실성이
  숫자 안으로 숨는다 — `problem.md` §7 이 막는 모양이다
- **D** — 리포트 객체가 없으면 UI 가 렌더와 내용을 한 덩어리로 만든다. 그리고 화면
  계약 검사를 **HTML 문자열에 대고** 다시 써야 한다(`0035` 반증 조건 1이 그 자리다)
- **E** — `design.md` R4 의 계약이 *"입력: 코드가 이미 채운 리포트(숫자 칸 전부 확정)"*
  다. F1 이 R4 의 선행이고, 순서를 뒤집으면 LLM 이 숫자 칸을 채우게 된다

## 반증 조건

- **리포트를 읽고도 사용자가 "왜 이 금리인가" 를 못 말하면** — 칸을 채운 것이 답이
  아니었던 것이다. 사람 세션으로 확인한다(M3 방식). 그때는 칸을 늘리는 쪽이 아니라
  **줄이고 순서를 바꾸는** 쪽을 본다
- **`합_불일치` 가 거의 모든 상품에서 뜨면** — 그 문장이 경고가 아니라 배경이 된다.
  저축은행은 상한에 걸린 상품이 297행 중 186행이므로 그럴 소지가 있다. 비율을 재서
  절반을 넘으면 표시 방식을 바꾼다(예: 상한은 계단에 녹이고 배타 그룹만 ※ 로)
- **`why` 때문에 `recommend_*.json` 이 커져 다루기 어려워지면** — 공시 문구 원문이
  행마다 들어간다. 지금은 gitignore 안이고 월 1회 산출이라 문제가 아니라고 본다
- **F4 에서 리포트 객체를 못 쓰고 다시 만들면** — 객체와 렌더를 가른 이유가 사라진다.
  그때는 객체 설계가 화면 요구와 안 맞았던 것이고, 계약을 객체 기준으로 다시 쓴다
- **리포트 검사(4상태)가 통과하는데 사람이 본 화면에서 계약이 깨지면** — 상태 네 개가
  대표성이 없는 것이다. 그러면 목록 검사처럼 전 세션으로 넓힌다(비용은 렌더 시간이다)
