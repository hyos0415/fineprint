# 0009 — 타깃을 검증기에서 추천기로 바꾼다

> 날짜: 2026-08-26 · 상태: 유효 · 사람이 결정
> 새 정의 `../spec/problem.md` · 옛 정의 `../spec/problem-v1-verifier.md` · 설계 `../spec/design.md`

## Decision

**만드는 것을 "AI 답변 검증기"에서 "내 상황·선호에 맞는 예적금 추천기"로 바꾼다.**

```
옛 정의   AI가 금리를 과대하게 말하는 것을 잡아내는 검증기
새 정의   내 상황과 선호에 맞는 예금·적금을 골라주는 시스템
```

함께 정한 것 다섯 가지.

1. **시스템은 선호를 추론하지 않는다.** 설문 → 고정 표 → 가중치, 사용자가 확인·수정
2. **정답은 "그 사용자 상태에서의 실수령 예상금리"다.** 취향이 아니라 계산이다
3. **계산 불가 상품은 버리지 않고 "근거 없음"으로 표시한다**
4. **편의성 축은 객관적인 것만 쓴다.** 주관적 점수(앱 사용성 등)는 우리가 매기지 않는다
5. **AI가 들어가는 자리를 넷으로 특정하고 각각 근거·측정을 붙인다** (R1~R4)

## Evidence

**(1) 검증기는 선행 프로젝트가 이미 한 일이다.** `finance_verifier`가
`verify(evidence, claim) → SUPPORTED/UNSUPPORTED/INSUFFICIENT`를 만들었다.
같은 것을 다시 만드는 것은 계보를 잇는 게 아니라 반복하는 것이다.

**(2) 사용자가 실제로 겪는 문제가 추천 쪽에 있다.** 같은 정책 저축상품이 은행마다
금리·혜택이 동일한데 인프라(비대면 개설 가능 여부·지점 위치)가 다르다.
그 비교를 하려고 전화하거나 방문하는 시간을 없애는 것이 동기다.

**(3) 전환해도 지금까지 만든 것이 대부분 살아남는다.**

| 기존 | 추천기에서의 역할 |
|---|---|
| 조건 유형 17종 (`0005`) | **사용자 상태 입력 필드**가 된다 |
| 닫힘률 (`prereg-03`) | **"이 상품을 계산해줄 수 있나" 판별기**가 된다 |
| 규칙 파서 v3 · 제한 스키마 LLM | 그대로 R1 |
| 검증기 개념 | R3 (분해가 원문과 맞나) |
| 사전등록 방법론 | 그대로 |

**(4) 추천의 정답이 계산 가능하다.** 사용자 상태 + 공시 구조 → 실수령 금리는
산수다. 그래서 "좋은 추천"에 검증 가능한 정답이 있다. 이것이 없으면 평가가 성립하지
않아 전환을 하지 않았을 것이다.

**(5) 데이터 실측이 전환을 지지한다.**

```
가입 채널(join_way)  은행 97건 · 저축은행 668건 전부 채워짐 — 편의성 축 1번이 이미 있다
비대면 전용 비율      은행 53% · 저축은행 53%           — 실제로 갈린다
계산 불가 상품        은행권 22.5% · 저축은행 36.8%      — 표시 기능이 필요한 규모다
```

## Alternative

- **(가) 검증기 유지** — `problem.md` 그대로 두고 추천은 하지 않는다
- **(나) 둘 다** — 검증기를 추천기의 부품으로 두고 두 산출물을 모두 평가한다
- **(다) 추천기 + 선호까지 추론** — 사용자 상황을 보고 가중치를 시스템이 정한다

## Why rejected

- **(가) 검증기 유지**: 선행 프로젝트와 같은 산출물이다. 그리고 사용자가 겪는 문제
  (은행 선택)를 다루지 못한다
- **(나) 둘 다**: 평가가 두 겹이 된다. 열린 결정(#2 정답 확정 규칙 · #3 판정 기준)이
  두 배로 늘어나고, 둘 다 미결인 상태에서 범위를 넓히면 어느 쪽도 못 끝낸다
- **(다) 선호 추론**: 평가 설계가 무너진다. 추천이 틀렸을 때 "선호를 잘못 읽었나,
  계산이 틀렸나"를 구분할 수 없다. 객관성·중립성도 확보되지 않는다.
  **사용자가 가중치를 주면 시스템은 "이 가중치면 이 순서"만 책임지면 되고, 그건
  검증 가능하다**

## 이 결정이 폐기하는 것

- **`0004`의 "주 타깃은 확인 불가 판정이다"** — 주 타깃에서 내려온다.
  단 같은 문서의 **"병목은 판정이 아니라 추출이다"는 그대로 유효**하고, 오히려
  추천기에서 더 중요해진다(실수령 금리 계산이 추출에 전부 달렸다)
- **이슈 #2(D3 정답 확정 규칙) · #3(D4 판정 기준)** — 검증기 기준으로 쓰여 있다. 재작성 필요
- **`0008`(본 실험 표본 B안)** — 판정 표본 기준이라 추천 평가에 맞는지 재검토 필요

## 이 결정이 폐기하지 않는 것

`0002`(사슬 순회 폐기) · `0005`(유형 17종·분석 단위) · `0006`(홀드아웃이 지표를 깨뜨림) ·
`0007`(규칙 깎기 종료). 전부 그대로다. `0002`는 오늘 API 조사로 근거가 더 강해졌다 —
카드 상품 엔드포인트가 없다는 것을 실측으로 확인했다.

## 반증 조건

- **실수령 금리를 계산할 수 있는 상품 비율이 50% 미만으로 떨어지면** → 추천할 수 있는
  상품이 절반도 안 된다는 뜻이고, 추천기로서 성립하지 않는다.
  현재 은행권 77.5% · 저축은행 63.2%
- **정책·정부 상품 데이터를 구할 수 없으면** → 전환 동기(§Evidence 2)의 핵심 사례를
  보여줄 수 없다. 편의성 축의 근거가 약한 채로 남고, 그때는 "금리 계산기"에 가까운
  범위로 축소해야 한다
- **사용자가 가중치를 조정하지 않고 기본값만 쓰면** → 설문·가중치 구조가 과설계였다는
  뜻이다. 고정 순위 하나로 충분했다는 신호다
- **설문 답이 조금 바뀔 때 1위 추천이 크게 흔들리면** → "시스템은 계산만 한다"가
  껍데기가 된다. 민감도를 측정해 가중치 구조를 다시 잡아야 한다
- **R1의 폴백 구조를 사전등록해 재측정했을 때 규칙 단독과 5%p 이내면** → AI가 R1에
  필요하다는 근거가 사라진다. `0004`의 첫 번째 반증 조건이 발동한다
