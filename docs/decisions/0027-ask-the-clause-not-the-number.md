# 0027 · 임계는 숫자로 받지 않고 문구로 묻는다

2026-08-28 · 사전등록 [`../spec/prereg-10-per-clause-questions.md`](../spec/prereg-10-per-clause-questions.md) ·
앞선 결정 `0015`(임계는 되묻는다) · `0016`(유형 하나에 질문 하나) · `0018`(예산·우선순위) ·
`0023`(계단식) · `0024`(P1 공시 문구 원문) · `0026`(질문 수 불가침) ·
이슈 [#13](https://github.com/hyos0415/fineprint/issues/13)

## Decision

**임계가 붙은 조건은 숫자를 묻지 않는다. 공시 문구를 그대로 질문 문장으로 쓰고
예/아니오/모름을 받는다.**

```
전   타상품_보유동시가입 — 금액이 얼마입니까? (상품별 기준 10만원 · 500만원 · 3,000만원)
후   "②적립식예금 잔액 10만원 이상 보유" — 충족하십니까?   [예][아니오][모름]
     "수익증권(펀드)을 3천만원 이상 보유 시" — 충족하십니까?  [예][아니오][모름]
```

**판정 단위가 (조건 유형)에서 (조건 유형 + 문구)로 내려간다.** 키는 문구 해시다
(`카드실적#a3f1c2d9`). 유형 게이트·계단식 처리·질문 예산 12개는 그대로다.

## Evidence

### 사람이 22개를 직접 답해 보고 나왔다

`0015`가 *"임계는 되묻는다"*로 정한 뒤 열 달 만에 처음으로 사람이 실제 루프를 답했다
(`prereg-09` §8). **수치 질문 두 개에서 답이 왜곡됐다.**

```
[15] 타상품_보유동시가입 — 금액이 얼마입니까?
       "예" 3번 거절 → 사실이 아닌 "아니오" 로 답했다
[17] 자동이체 — 몇 번 하십니까?
       4번 거절 → "모름" 으로 답했다. 모르는 게 아니었다
```

입력 처리 버그(거절 메시지가 `예`를 받는다고 거짓말했고, `6회` 같은 단위 표기를 못
읽었다)는 따로 고쳤다. **고쳐도 남는 문제가 이 결정의 이유다.**

> 입력 폼으로 받던가 해야할 거 같고 프로토 타입도 아닌 poc라서 그런 거 괜찮긴 한데
> 공시 문구 원문을 보여주는 게 약간 이해가 안 갈 거 같다고 느껴지는데?

### 한 유형 아래 대상이 서로 다른 문구가 묶여 있었다

```
"②적립식예금 잔액 10만원 이상 보유"          ← 적립식예금 잔액
"수익증권(펀드)을 3천만원 이상 보유 시"        ← 펀드 보유액
"정기예금 500만원이상(만기 1년이상) 가입하고…"   ← 정기예금 가입액
```

**"금액이 얼마입니까?" 에는 답이 존재하지 않는다.** 세 축이 다르기 때문이다.
`0016`의 *"유형 하나에 질문 하나"*가 유형 질문에서는 맞고 **임계 질문에서는 틀렸다** —
유형은 "카드를 쓰십니까" 처럼 하나의 사실이지만, 임계는 상품마다 **무엇의** 얼마인지가
다르다. 입력 폼으로 바꿔도 필드 하나로는 못 받는다.

### 사용자 부담이 줄고 P1이 강해진다

`0024` P1은 *"질문에 공시 문구를 그대로 붙인다"*였다. 이제 문구가 **질문 문장 자체**가
된다 — 사용자는 자기 상황을 그 문구에 대조하면 되고, 숫자를 계산해 입력할 일이 없다.

### 실측 — 사전등록 예측대로 나왔다 (`prereg-10` §7)

| | 예측 | 실측 |
|---|---|---|
| 은행권 질문 수 (전부 답) | 30~50 | **39** (유형 15 + 문구 24) |
| 저축은행 질문 수 | 35~60 | **45** (유형 13 + 문구 32) |
| 은행권 확정 (예산 12) | 40~56% | **55.2% (37/67)** — 변화 0 |
| 저축은행 확정 (예산 12) | 70~80% | **80.2% (85/106)** — 변화 0 |
| 폭 평균 (예산 12) | 올라간다 | 은행권 0.176 → **0.185** · 저축은행 0.277 → **0.386** |
| 전부 답했을 때 확정 | 같다 | 은행권 **50/67** · 저축은행 **93/106** — 둘 다 그대로 |
| 커버리지 | 안 변한다 | **84.8% · 35.7%** |
| 계단식 `단계불명` | 3 · 3종 | **3 · 3종** |

**예산 12개 안에서는 아무것도 안 변했다** — 문구 질문은 상품 커버리지가 작아
우선순위(`0018`)에서 12위 밖으로 밀린다. 예산 12개는 사실상 **유형 질문만 재고 있다.**
변한 것은 폭 평균이고, 저축은행이 0.277 → 0.386으로 크게 움직였다(문구 질문이 32개라
같은 12개 예산으로 덜 좁힌다). **`0026`이 "예산을 늘려 지우지 않는다"고 못 박았으므로
이 하락은 그대로 남긴다.**

## Alternative

| | 방법 | 왜 안 골랐나 |
|---|---|---|
| B | 수치 질문을 문구별로 쪼개고 답은 숫자 | 정확하지만 사용자가 펀드 보유액 같은 금액을 직접 계산해 넣어야 한다. 부담이 가장 크다 |
| C | 지금 상태로 두고 기록만 (PoC니까) | 실측에서 **틀린 답 두 개**가 나온 자리를 알면서 두는 것이다 |
| D | 유형 하나에 임계 하나만 남기고 나머지는 버린다 | 상품 판정이 조용히 틀어진다. 버린 조건이 `hi`에 남아 과대 진술이 된다 |
| E | 우리가 문구를 쉬운 말로 다시 쓴다 | `0016`·`CLAUDE.md` 5번이 막은 방향이다. 요약하면 사용자가 판단할 근거를 빼앗는다 |

## 반증 조건

- **문구 질문의 "모르겠다" 비율이 유형 질문보다 크게 높으면** — 문구가 질문 문장으로
  쓰기에 어려운 것이다. 그러면 E(우리 말로 다시 쓰기)를 다시 검토해야 한다.
  세션 로그의 `key`에 `#`가 있는지로 두 종류를 갈라 셀 수 있다
- **문구 질문 수가 유형 질문의 세 배를 넘으면** — 은행권 15:24 · 저축은행 13:32이다.
  세 배(1:3)를 넘으면 사용자가 같은 유형을 반복해서 답하는 느낌이 될 수 있다
- **폭 평균이 예산 12개에서 계속 나빠지면** — 지금은 문구 질문이 예산 밖으로 밀려서
  생긴 하락이다. `0018`의 예산 12개가 이 구조에서 여전히 옳은 값인지 다시 봐야 한다
  (**예산을 늘리는 것은 회피이므로** 지표 정의를 바꾸는 결정으로 다뤄야 한다)
- **긴 문구가 화면에서 잘리면** — 질문 문장이 잘리면 조건이 달라진다. 지금은 자르지
  않는다(은행권 최대 76자). 문구 길이 상한이 생기면 이 결정을 다시 본다
- **`--state`로 문구 키를 손으로 적는 것이 실제로 불가능하면** — 해시 키(`유형#a3f1c2d9`)를
  사람이 외울 수는 없다. 루프가 찍어 주므로 복사해 쓸 수 있지만, 측정 스크립트를
  손으로 돌릴 때 걸림돌이 되면 편의 문법이 필요하다
