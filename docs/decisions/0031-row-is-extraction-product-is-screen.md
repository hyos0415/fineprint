# 0031 · 행은 추출 품질의 단위, 상품은 화면의 단위다

> 날짜: 2026-08-31 · 상태: 유효
>
> **#61 이전 (2026-09-04 표시).** 이 문서의 저축은행 수(297행 · 상품 183개)는 옵션 행을 상품코드만으로
> 붙이던 때의 값이다 — 여기서 "상품은 기관코드+상품코드로 센다" 고 정하면서 **붙이는 자리는 안 고쳤다**.
> 고친 뒤는 196행 · 133개다(`0052` · `prereg-22`). 결정 자체(행/상품의 단위)는 그대로 유효하다.

사전등록 [`../spec/prereg-13-product-identity.md`](../spec/prereg-13-product-identity.md) ·
이슈 [#25](https://github.com/hyos0415/fineprint/issues/25) ·
앞선 결정 `0018`(질문 우선순위·예산 12개) · `0019`(기준선 재등록의 선례) ·
`0028`(스코프 축은 기관) · `0030`(선호 가중치 — 이 문제를 발견한 자리)

## Decision

**두 단위를 쓴다. 그리고 그 사실을 명시한다.**

```
행    (기관코드, 상품코드, 단리/복리, 적립방식)   -> **추출 품질**의 단위. 지표 분모
상품  (기관코드, 상품코드)                     -> **화면**의 단위. "상품 N개"
```

지금까지 코드가 **우연히** 그렇게 돼 있었고 **아무 데도 안 적혀 있었다.** 그리고
화면 쪽이 틀리게 계산되고 있었다 — 상품을 `상품코드만`으로 세서 저축은행 상품이
92개로 보였다(참값 183).

정한 것 넷.

1. **신원 계산은 `calculate.product_key()` · `row_key()` 두 함수에만 둔다.** 두 곳에서
   다르게 세면 이 버그가 그대로 재발한다
2. **`rank_questions()` 의 1순위는 `product_key()` 로 센다.** 규칙을 바꾼 것이 아니라
   규칙이 이미 *"상품 커버리지 내림차순"* 이라고 말하던 것을 그대로 계산되게 고쳤다
3. **지표 분모는 행 그대로다.** 커버리지 게이트(79.7% · 36.7%)와 이슈 #10 을 안 건드린다
4. **`rows` 에 `co_no`·`rate_type`·`rsrv_type` 를 담는다.** 원천에 있는데 안 담고
   있었다 — `kor_co_nm`(#15) · `join_way`(#22) 때와 **같은 자리 세 번째**다

## Evidence

### 상품코드는 상품의 신원이 아니다

```
저축은행 12개월   기관명 30종  ·  **기관코드(fin_co_no) 58개**
                하나저축은행 = 0010378 · 0010528 · 0010572 (세 법인)
                셋 다 상품코드 240001 "정기예금" 을 쓴다

상품 수   상품코드만 92   ·   기관코드+상품코드 **183**   (원천에서 독립 계산해 대조)
```

### 행의 정체가 원천으로 남김없이 설명된다

```
행 = (기관코드, 상품코드, 단리/복리, 적립방식)
     은행권 79 = 79 · 저축은행 297 = 297
     원천 optionList 에 완전 중복 레코드 0건 -> 수집 문제가 아니다
```

**그래서 "행이 무엇인지 모른다" 는 상태가 끝났다.** 남은 것은 무엇을 세는 단위로
쓸 것인가였고, 그 답이 위의 Decision 이다.

### 두 단위는 서로 다른 것을 잰다 — 그래서 하나로 합치지 않는다

```
행    같은 상품의 단리 행은 닫히고 복리 행은 안 닫힐 수 있다.
      닫힘률·확정률이 재는 것은 **추출이 그 줄을 읽어냈나** 이므로 행이 맞다
상품  사용자에게 "정기예금" 은 하나다. 8번 세면 화면이 이상해진다
```

### 화면이 참값을 말하게 됐다 (주 목적)

| | 원천 독립 계산 | `product_key()` |
|---|---|---|
| 은행권 | 73 | **73** |
| 저축은행 | 183 | **183** |

총수를 넘는 질문 0개 · 옛 값보다 줄어든 질문 0개(합치면 늘 수만 있다).

### 기준선이 움직였고, 그것을 미리 적었다

`rank_questions()` 가 화면 문구와 질문 순서를 **동시에** 만들어서, 화면을 고치면
순서가 바뀐다. `0019` 와 같은 절차로 사유·편향 방향·완화 조치를 **고치기 전에**
`prereg-13` §2 에 적었고 — **편향 방향은 "모른다" 라고 적었다.** 유리한 기준을
고를 수 없는 상태에서 예측을 커밋한 것이 이 재등록의 정당성이다.

**예측 일곱 중 다섯이 적중했고 하나(방향)는 예측하지 않았다.**

```
은행권      순서 동일 · 확정 37/67 (55.2%) · 폭 0.185%p · 커버리지 84.8%   **안 변함**
저축은행    1위가 고객군_자격 -> 비대면_채널가입(15상품 -> 67상품)
           확정 85/106 (80.2%) -> **75/106 (70.8%)** · 폭 0.386 -> **0.449%p**
           커버리지 35.7%  **안 변함**  <- 주 판정
```

**70.8% 는 후퇴가 아니다.** 같은 12개를 답한 것이 아니다 — 1위가 바뀌면 이후 그리디
경로가 갈라지고, 답한 질문 셋이 서로 다르다. 커버리지가 큰 질문을 먼저 묻는 것이
확정 상품 수를 더 늘리지는 않는다(확정은 그 상품의 **모든** 조건에 답해야 된다).
**`0018` 이 1순위로 고른 것은 커버리지이지 확정률이고, 확정률은 그 규칙의 부산물이다.**

## Alternative

- **A. 지표 분모도 상품(183)으로 바꾼다** — 화면과 지표가 같은 단위가 된다
- **B. 화면도 행(297)으로 센다** — "이 답 하나가 297행 중 N행을 엽니다"
- **C. `rank_questions()` 는 그대로 두고 화면 문구만 고친다** — 기준선이 안 움직인다
- **D. `rows` 를 상품 단위로 합친다** — 같은 상품의 여러 행을 하나로 접는다

## Why rejected

- **A** — `0018` 기준선과 이슈 #10 게이트를 통째로 재등록해야 한다. 그리고 **틀린
  방향이다** — 닫힘률·확정률이 재는 것은 추출이 그 **줄**을 읽어냈는가이지 상품이
  아니다. 단리 행은 닫히고 복리 행은 안 닫힐 수 있다
- **B** — 사용자에게 "행" 은 뜻이 없는 말이다. 같은 상품이 8번 세어지는 화면을
  설명할 방법이 없다
- **C** — 우선순위 1순위가 *"상품 커버리지"* 라고 적혀 있는데 상품을 틀리게 센 채로
  두는 것이다. **화면과 순서가 같은 함수에서 나오는데 한쪽만 참으로 만들면**, 화면은
  183 을 말하고 순서는 92 로 정해지는 상태가 문서화된 채 남는다. 기준선이 안 움직이는
  것은 이득이지만 그것을 위해 틀린 계산을 유지하는 것은 `0018` 이 막으려던 것과
  같은 종류의 도피다
- **D** — 합치려면 여러 행의 금리 중 무엇을 쓸지 정해야 한다. 그건 **사용자에게 보여줄
  금리를 우리가 고르는 것**이고 `0017`·`0022` 가 "고르지 않고 범위로 낸다" 로 답한
  자리다. 화면에서 묶는 것은 별도 문제로 남긴다(`prereg-13` §7-3)

## 반증 조건

- **화면의 "상품 N개" 가 또 틀리면** — 신원 계산이 `product_key()` 밖으로 새어 나간
  것이다. 이 결정의 1번(한 곳에만 둔다)이 지켜지지 않은 것이고, 그때는 assert 로
  박아야 한다(지금은 규율로만 막고 있다)
- **지표 분모가 움직이면** — `0031` 3번의 경계가 새어 나간 것이다. 커버리지 84.8% ·
  35.7% 가 기준이고, 움직이면 되돌린다
- **저축은행 확정률이 다음 측정에서 또 크게 흔들리면** — 예산 12개 시점의 확정률이
  질문 순서에 지나치게 민감한 것이다. 그러면 `0018` 의 "예산 12개" 가 재는 것이
  무엇인지를 다시 봐야 한다 (`0028` 반증 조건 4가 이미 같은 방향을 지목했다)
- **단리/복리가 사용자에게 필요한 정보로 드러나면** — `rows` 에 담기만 하고 화면에
  안 올린 판단이 틀린 것이다. 그때는 화면 계약을 하나 더 만들고(A9 가 `join_way` 에
  대해 한 것) 같은 상품이 8줄로 보이는 문제를 먼저 푼다
