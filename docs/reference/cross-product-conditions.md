# 조건이 다른 상품을 가리키는 경우 — 그래프가 필요해지는 지점

> 작성 2026-08-24 · 근거: `finance_verifier`의
> `data/normalized/deposit_products_canonical.json` 전수 집계
>
> **이 문서의 지위**: 발견 기록 + 재검증(§1.1).
> **2단계로 유지하기로 결정됐다** — `../decisions/0001-two-stage-scope.md`.
> 게이트 순서는 바뀌지 않는다.

## 0. 왜 이 문서가 생겼나

솔직한 배경부터 적어둔다. "예전 그래프 프로젝트를 살리고 싶다"는 동기가 먼저 있었고,
그 동기 자체는 **반증 게이트(v2 §3)가 막으려고 만들어진 것**이다. 그래서 동기를 근거로
쓰지 않고, **데이터에 그래프가 필요한 지점이 실제로 있는지** 따로 확인했다.

결과: 있었다. 다만 게이트를 건너뛰는 근거는 되지 않는다 — 아래 §4가 그 이유다.

## 1. 무엇을 확인했나

우대조건(`spcl_cnd`) 안에서 **다른 상품이나 서비스를 보유·가입하라고 요구하는지** 셌다.

```
우대조건이 있는 은행 정기예금                    32개
그중 조건이 '다른 상품/서비스 보유·가입'을 요구    11개
```

참조 대상별:

| 참조 대상 | 상품 수 |
|---|---:|
| 적금 | 4 |
| 카드 | 4 |
| 통장(입출금 등) | 3 |
| 주택청약 | 2 |
| 오픈뱅킹(다른 은행 계좌 등록) | 2 |
| 펀드·수익증권 | 1 |
| 연금 | 1 |

상품 이름을 **직접 지목한** 사례:

```
[p003 iM함께예금]     신규일 "iM함께적금" 동시 가입 및 만기(12회 불입) 보유
[p003 iM함께예금]     상품 가입 전 첫만남플러스통장 보유
[p029 NH내가Green]    NH내가Green초록세상적금 동시 보유 : 0.1%p
[p014 스마일드림]      김만덕나눔적금 보유 또는 만기 해지고객 0.2%
[p014 스마일드림]      예금가입시 탐나는전 체크카드 보유고객 0.1%
[p012 제주Dream]      탐나는 J연금통장 / 국민연금안심통장 / 공무원연금안심통장 가입고객
[p004 iM스마트예금]    당행 주택청약종합저축 보유
[p016 JB 123]        가입일직전 6개월 동안 당행 원화 정기예금 보유이력이 "없는" 경우 0.50%
```

마지막 `p016`은 **부정 조건**이다("보유이력이 없어야 함"). 지금 v2의 조건 표현에는
이 형태가 들어 있지 않다.

## 1.1 재검증 (2026-08-24, FINeprint 세션)

같은 파일을 다시 집계해서 위 숫자를 확인했다. **핵심 숫자는 그대로 재현됐고, 세부
세 곳을 조인다.**

| 항목 | 원래 기재 | 재검증 | 판정 |
|---|---|---|---|
| 우대조건 있는 정기예금 | 32개 | 32개 (`해당없음` 없음, 전체 38개 중) | ✅ 일치 |
| 다른 상품/서비스를 요구하는 상품 | 11개 | 11개 (`p002·p003·p004·p008·p012·p014·p016·p018·p020·p029·p034·p036` 중 키워드 합집합 11) | ✅ 일치 |
| 상품 이름을 직접 지목 | "9건" | **조건 문구 9개 · 상품 수로는 5개** | ⚠️ 단위 명확화 |
| 부정 조건 | 1건 (p016) | **2건** — p036도 같은 형태 | ⚠️ 누락 |
| 두 홉이 실제로 이어짐 | "4~5건" | **3건** | ⚠️ 하향 |

**(1) "9건"은 상품이 아니라 조건 문구의 수다.** 이름이 지목된 문구는 9개이고, 그 문구를
가진 상품은 5개다(`p003` 2개 · `p004` 1개 · `p012` 3개 · `p014` 2개 · `p029` 1개).
2단계 실험의 표본 단위는 상품이 아니라 claim이므로 문구 수가 더 쓸모 있는 숫자지만,
"11개 중 9개 상품"으로 읽히면 근거가 두 배로 부풀어 보인다.

기준도 적어둔다 — 이 9개는 **예적금·통장·청약 계열의 명시된 이름만** 세었다. `p034`의
"수협신용카드 / 수협체크카드"를 이름으로 인정하면 11개가 된다. 카드를 뺀 이유는 §3의
잎사귀 분류와 같다(카드 레코드가 없어 두 홉이 안 이어진다). **판단이며 측정이 아니다.**

**(2) 부정 조건은 두 건이다.**

```
[p016 JB 123]       가입일직전 6개월 동안 당행 원화 정기예금 보유이력이 "없는" 경우 0.50%
[p036 Sh첫만남우대]  최근 1년간 수협은행 예적금 활동계좌 "미보유" 고객
```

둘 다 "다른 상품을 보유하지 **않아야**" 우대를 받는 형태다. 방향이 반대인 조건을 한 건
더 찾았다는 건, 이게 예외가 아니라 **조건 표현이 반드시 다뤄야 하는 형태**라는 쪽에
가깝다.

**(3) 두 홉이 이어지는 건 3건이다 — 4~5건이 아니다.** 적금 API로 이름을 조회해 사슬을
이을 수 있는 건 아래 셋뿐이다.

```
p003 iM함께예금        →  iM함께적금
p014 스마일드림예금     →  김만덕나눔적금
p029 NH내가Green예금   →  NH내가Green초록세상적금
```

빠지는 것들과 이유:

- `p034` "당행 펀드 또는 적금" — 이름이 아니라 **상품군**이다. 한 홉의 대상이 하나로
  정해지지 않고 후보 집합 조회가 된다
- `p012` 연금통장 3종 · `p004` 주택청약종합저축 — 적금 API로 해결되지 않는다.
  각각 별도 API가 필요하다(v2 §5.1 범위 밖)
- `p036` "예적금 활동계좌" — 이름 없는 부정 조건이라 이을 대상이 없다

**이 3건이 D1의 검정력 기준에 미달한다.** `docs/decisions/README.md`의 D1 참고 자료는
"구조가 잡고 Verifier가 놓치는 건수가 **6건이면 유의**(p≈0.03)"라고 적어두었다. 3건은
그 절반이다. 즉 **2단계는 지금 데이터로는 측정이 성립하지 않고, 표본을 만드는 것이
첫 작업**이다 — 1단계의 `condition_omission` 3건과 정확히 같은 모양의 문제다.

## 2. 왜 이게 평면 구조로는 안 되나

`p003`의 조건을 검증하려면 `iM함께적금`이 무엇을 요구하는지 알아야 한다 —
그 적금에도 자기 조건이 있다. 즉 정보가 **상품 하나의 레코드 안에 없다.**

```
예금 A ─요구→ 조건 ─가리킴→ 적금 B ─요구→ 조건 ...
```

`condition_omission`과 같은 실패 유형인데, **빠진 정보가 다른 레코드에 있다.**
겨냥하는 질문은 한 홉 밖으로 나간다.

> AI가 "이 조건을 만족하면 우대금리를 받는다"고 답할 때,
> **그 조건이 또 다른 상품 가입을 요구한다는 사실**을 숨기지 않았는가?

이건 프롬프트를 고쳐서 해결되는 문제가 아니다. 프롬프트에 없는 레코드를 읽어올 수는 없다.

## 3. 정직하게 — 이 근거의 크기

| 참조 대상 | 상품 수 | 우리 데이터로 두 홉이 이어지나 |
|---|---:|---|
| 적금 | 4 | ✅ 적금 API로 해결 (v2 §5.1에서 이미 가져올 예정) |
| 연금 | 1 | ⚠️ 연금저축 API 별도 필요 |
| 통장 · 카드 · 청약 · 펀드 · 오픈뱅킹 | 나머지 | ❌ 레코드 없음 — 잎사귀로 끝남 |

**실제로 두 홉이 이어지는 건 3건이다**(§1.1 재검증 — 초판의 "4~5건"에서 하향).
나머지는 "외부 상품 요구"라는 라벨로 매달린다.
`condition_omission` 3건과 같은 표본 크기 문제를 그대로 안고 있다.

다만 ### 3.1 잎사귀는 수집으로 해결되지 않는다 — API 엔드포인트 확인 (2026-08-24)

위 표에서 "레코드 없음"으로 분류한 것들이 **더 모으면 채워지는 것인지** 확인했다.
금융감독원 금융상품한눈에 API에 실제로 요청을 보내 엔드포인트 존재 여부를 봤다
(은행권 `topFinGrpNo=020000`).

| 상품군 | 엔드포인트 | 결과 |
|---|---|---|
| 정기예금 | `depositProductsSearch` | 200 · 38건 (보유 중) |
| 적금 | `savingProductsSearch` | **미조회** — `../spec/prereg-01-savings-scope.md` 커밋 전이라 의도적으로 건드리지 않았다 |
| 연금저축 | `annuitySavingProductsSearch` | 200 · 은행권 **0건** |
| 주택담보·전세·신용대출 | `mortgageLoan` / `rentHouseLoan` / `creditLoan` | 200 · 34 / 41 / 44건 (범위 밖 — v2 §5.1) |
| **입출금통장** | `depositAccountSearch` | **404 — 엔드포인트 없음** |
| **주택청약** | `housingSubscriptionSearch` | **404 — 엔드포인트 없음** |
| **카드** | `cardProductsSearch` | **404 — 엔드포인트 없음** |

**따라서 잎사귀는 구조적으로 확정된다.** 통장·청약·카드를 요구하는 조건은 대상 레코드를
**원리적으로** 가져올 수 없다(이 API 기준). 참조가 해결되는 상품군은 실질적으로
**적금과 예금뿐**이다.

이 사실이 D6(2단계 설계)의 첫 항목을 바꾼다. "해결 안 되는 잎사귀를 노드로 둘지 속성
플래그로 둘지"는 선택의 문제가 아니라 **반드시 표현해야 하는 상태**다 — 검증기가
"이 조건은 확인 불가능한 외부 상품 보유를 요구한다"고 말할 수 있어야 한다.

(404는 추측한 엔드포인트 이름에 대한 응답이다. 이름이 다를 가능성을 배제하지는 못하지만,
금융상품한눈에가 공개하는 상품군 목록 자체에 입출금통장·청약·카드가 없다는 것과 일치한다.
카드는 여신금융협회 소관으로 별도 체계다.)

**매달린 참조도 검증에서는 의미가 있다** — "이 조건은 우리가 확인할 수 없는 외부
상품 보유를 요구한다"는 것 자체가 판정에 필요한 정보다(`INSUFFICIENT`에 가까운 신호이거나,
최소한 "완전히 검증할 수 없음" 플래그).

## 4. 제안 — 게이트는 그대로, 이건 2단계로

> **후속 (2026-08-24)**: 이 절의 제안대로 2단계 질문을 세우고 예측을 사전 등록한 뒤
> 적금 전수 59건을 수집해 측정했다. **사슬은 4건으로 임계(6건) 미달 → 2단계 폐기.**
> `../decisions/0002-drop-chain-traversal.md` · `../spec/prereg-01-savings-scope.md` §4.
> 아래 내용은 당시 판단의 기록으로 보존한다.

두 질문을 **분리**하면 둘 다 살아난다.

| | 질문 | 답하는 실험 |
|---|---|---|
| **1단계** (지금의 게이트) | 상품 **하나 안에서** 조건 누락을 잡는 데 구조가 필요한가? | G4 / G5 |
| **2단계** (이 문서) | 조건이 **다른 상품을 가리킬 때**, 사슬을 따라가야 잡히는 누락이 있는가? | 미설계 |

**1단계 결과가 2단계를 죽이지 않는다.** G5가 통과해서 "단일 상품은 정리해서 LLM에게
주면 된다"가 나와도 2단계는 열려 있다 — 레코드를 건너가는 건 별개 층이다.

반대로 이 문서가 **1단계를 건너뛰는 근거는 아니다.** 2단계 질문에 답하려면 애초에
"조건 구조를 어떻게 표현할지"가 정해져 있어야 하고, 그건 1단계 게이트가 결정한다.

### 2단계로 넘어갈 때 결정해야 할 것 (미정)

- 참조가 해결되지 않는 잎사귀(카드·통장 등)를 어떻게 표현할지 —
  노드로 둘지, 속성 플래그로 둘지
- 부정 조건(`p016`: "보유이력이 없어야 함")을 조건 표현에 넣을지
- 두 홉이 이어지는 **3건**으로는 측정이 성립하지 않는다(§1.1) — 표본을 어떻게 더 만들지
  → 적금 추가 시 얼마나 늘어날지 사전 등록: `../spec/prereg-01-savings-scope.md`
- 검증 대상 claim을 새로 만들어야 한다 — 지금 slice에는 "조건이 다른 상품을 요구하는데
  답변이 그걸 숨긴" 사례가 없다

## 5. 한 문단 요약

우대조건이 있는 정기예금 32개 중 **11개**의 조건이 다른 상품 보유를 요구하고,
**상품 이름을 직접 지목한 조건 문구가 9개**(상품 수로는 5개, §1.1)다. 이 정보는 상품 하나의 레코드 안에 없어서 평면 구조로
표현되지 않는다 — **그래프가 실제로 필요해지는 지점은 여기이며, 단일 상품 내부의
`condition_omission`이 아니다.** 다만 두 홉이 실제로 이어지는 건 **3건뿐**이고(D1 유의 기준 6건의 절반), 검증용
claim도 아직 없다. 따라서 이건 **1단계 게이트를 대체하지 않는 2단계 질문**으로 둔다.
