## 1. 문제

### 1.1 잡으려는 실패: `condition_omission`

```
Evidence(금융감독원 공시 원문):
  A · B 를 모두 충족해야 보너스금리 0.1%p

Claim:
  "A 를 충족하면 보너스금리를 받을 수 있다"      ← B 가 빠졌다

Gold:      UNSUPPORTED
Verifier:  SUPPORTED                          ← false accept
```

Claim에 적힌 A는 evidence에 실제로 있다. 문제는 **Claim에 적히지 않은 필수조건을
evidence 전체에서 능동적으로 찾는 일**이고, 이게 자연어 entailment 방식으로는 잘 안 된다.

### 1.2 확립된 것

> **정정 (2026-08-25)**: 아래 "체급으로 안 풀린다"는 선행 프로젝트의 자체 감사에서
> 뒤집혔다. 3B 로컬 모델(Kanana)이 같은 태스크를 4/4로 맞힌다. 실패는 체급이 아니라
> **모델별 특성**이다. 정정 요약은 `../reference/finance-verifier-findings.md` §0,
> 후속 결정은 `../decisions/0003-upstream-conclusions-corrected.md`.

- **재현된다** — Pilot 1건 관찰 → Test(unseen) 신규 2건 **모두** 실패
- **체급으로 안 풀린다** — Qwen3.5-4B `0/2`, Claude Haiku 4.5 `1/2`,
  Nemotron Ultra 550B(130배 큼) `0/2`
- **검색 리콜 문제가 아니다** ★ — finance_verifier에는 검색 단계가 없다. evidence는
  canonical record에서 직접 주입된다. 즉 **이미 oracle evidence 조건에서 실패했다.**
  감사가 요구한 oracle evidence 통제군은 **이미 통과된 것으로 기록**한다

### 1.3 확립되지 않은 것 ★★

`../reference/finance-verifier-findings.md` §2가 전체 목록. 요약:

| 항목 | 상태 |
|---|---|
| **표본 크기** | `condition_omission` 사례 **전체 3건** (Pilot 1 + Test 2), 크로스모델 체크는 **n=2** |
| `condition_omission`을 겨냥한 프롬프트 | **미측정** (v3·v4는 INSUFFICIENT를 겨냥했다) |
| claim 분해 단위 변경 | **미측정** (단, 분해 변경이 결과를 크게 바꾼 전례 있음) |
| 결정론적 체크리스트 | **미측정** ← 가장 싸고 가장 위험한 baseline |
| 조건 구조 추출 난이도 | **미지수** — 추출도 LLM이 한다(순환성) |
| gold 조건 집합의 상한 | 원문 자체가 모호한 사례가 **이미 확인됨** |

**함의**: 전제의 방향은 신뢰할 만하지만, **효과 크기를 논할 근거는 없다.**
"2건 중 2건을 잡았다"는 측정이 아니다. 따라서 첫 작업은 그래프도 게이트도 아니라
**평가 slice 구축**이다.

### 1.4 실제 조건 구조 — 3건 전수 확인 ★

`condition_omission` 3건의 evidence 원문을 직접 열어보면 **평면 AND가 아니다.**

```
p002 e-그린세이브예금 ─ 평면 ALL_OF (2개)
  "만기일에 아래의 조건을 모두 충족하는 경우 보너스이율 제공"
    - 6~12개월제 5천만원 이상 가입
    - 만기일 기준 전전월 말 수익증권(펀드) 3천만원 이상 보유
  claim: "5천만원 이상 가입 시 보너스이율 0.1%"        ← 펀드 조건 누락

p020 The파트너예금 ─ 최상위 독립/OR + 갈래 내부 AND
  ① 경남은행 거래기간 5년이상 + 마케팅동의  →  0.20%
  ② 급여·연금·가맹점대금 입금             →  0.10%
  ③ 카드 결제실적                        →  0.10%
  claim: "거래기간 5년 이상이면 0.20%"                 ← ① 내부의 마케팅동의 누락

p034 Sh해양플라스틱Zero!예금 ─ 항목 AND (하위 OR 제약)
  4. 자동이체 출금실적 : 0.1%
     - 수협신용카드 / 당행 펀드 또는 적금 / 수협체크카드
  claim: "자동이체 출금실적만 있으면 0.1%"              ← 하위 채널 제약 누락
```

**두 가지가 여기서 확정된다.**

**(1) 원문의 명시적 AND 표기만으로는 부족하다.** p002는 evidence에 "**모두 충족**"이라고
명시돼 있고 조건도 대시로 분리돼 있는데, 두 모델이 모두 놓쳤다. 따라서 "evidence를
읽기 좋게 정리해주면 LLM도 잘할 것"이라는 반대 가설(§3 G5)은 **텍스트 수준에서는
이미 반증에 가깝다.** (단, 형식 자료구조로 주고 명시 지시를 붙이는 것은 여전히 미측정 —
G5는 그것을 측정한다.)

**(2) 필수조건 집합은 "혜택 단위로 스코핑"해야 나온다.** p020에서 0.20%에 대한
`Required`는 ①의 조건들이고 ②③은 무관하다. 즉

```
Claim이 어느 혜택을 말하는가 → 그 혜택에 걸린 ConditionGroup → 그 안에서 비교
```

가 필요하다. 평면 리스트로는 표현되지 않으며, **이것이 v1 §6의
`Benefit ─REQUIRES→ ConditionGroup`이 실제로 필요한 이유다.**

## 2. 선행 프로젝트(KAG_LlamaIndex)의 한계

핵심은 "Knowledge Graph가 효과 없었다"가 아니다. **그래프를 만들기 전에 그래프 내부의
지식 단위와 관계 제약을 정의하지 않았다는 것**이다.

실측(감사):

```
Entity 타입 460종 / Relation 773종 · 단발성 엔티티 70.9%
리터럴 형태 엔티티 노드      152 / 925 = 16.4%
목적어가 리터럴인 트리플      183 / 773 = 23.7%   ← 트리플 1/4이 속성을 간선으로 표현
```

> **⚠️ v1 §2.1 정정 (Q2 결정 — 되돌리려면 이 절)**
> v1은 "같은 개념의 표기 변형을 정규화할 규칙이 없었다"를 **개선 가능한 결함**으로 나열했다.
> 실측은 다르다 — **선행 저장소는 정규화를 실제로 시도해서 기각했다.** 재등장 엔티티가
> 925개 중 42개(4.5%)뿐이라 완벽한 별칭 사전을 만들어도 상한이 이미 낮았다.
>
> 이 정정이 중요한 이유는 서사가 바뀌기 때문이다.
> - v1 서사: "정규화를 안 했다 → 이번엔 제대로 하자" → **이미 기각된 경로를 다시 걷는다**
> - v2 서사: "정규화를 시도했고 상한을 측정했다 → 해법은 다른 층(추출 시점 형식 제한)이다"
>
> 후자가 사실이고, 포트폴리오로도 더 강하다(측정해서 경로를 버린 기록).

그리고 감사가 밝힌 **v1이 다루지 않은 층 3개**:

- **응용 경로가 그래프를 아예 저장하지 않았다** (`app/**`에 `persist` 호출 0건).
  스키마를 완벽히 고정해도 이 층은 해결되지 않는다 → §10
- **LLM 생성 메타데이터가 추출 입력으로 재투입**되어 가짜 연결을 만든 실증 사례 → §5 불변식
- **파싱 실패 트리플이 조용히 버려지고 계측되지 않았다** → §8

### 2.1 순서를 뒤집는다

```
v1이 비판한 순서:   Graph → 탐색 → 나중에 평가
FINeprint의 순서:   Problem → Failure 정의 → 표본 확보 → 반증 게이트
                    → (필요하다고 확인되면) Schema → Constraint → Extraction → 평가
```

## 3. 반증 게이트 — Graph로 가기 전에 통과해야 하는 것 ★ 신설

**이 프로젝트의 가장 중요한 절이다.** v1에는 없었다.

목적: **"Graph가 필요한가"를 Graph를 만들기 전에 확인한다.** 감사의 Codex V1은
"`condition_omission`이 Graph로 풀 문제라는 전제가 미검증"을 치명 1순위로 지목했다.

### Phase 0 — 게이트

| # | 게이트 | 내용 | 통과 시 함의 |
|---|---|---|---|
| **G0** | **평가 slice 구축** | 목표치까지 사례 확보(D1). false reject용 negative + **상품군 층화**(§8.5) 포함 | 없으면 이하 전부 측정 불가 |
| **G1** | prompt-only | "언급되지 않은 필수조건이 있는지 evidence 전체와 대조하라"를 명시한 프롬프트 | **잡으면 → 프로젝트 전제 붕괴.** 구조 불필요 |
| **G2** | claim 분해 단위 | Decomposer가 "이 claim이 인용한 조건 집합"을 명시 산출 | 잡으면 → decomposer 개선으로 끝, 구조 불필요 |
| **G3** | oracle evidence | — | **이미 통과** (§1.2). 재실험 불필요 |
| **G4** | **결정론적 체크리스트** | 조건을 구조화한 뒤 **코드**가 비교 (혜택 스코핑 + 1단계 중첩, §7) | 잡으면 → 기여는 "결정론적 검사"에 있다 |
| **G5** | **구조화 evidence + LLM 판정** ★ | 같은 구조를 **형식 자료구조로 Verifier에게 주고** "conditions 전부를 claim이 언급했는지 확인하라"고 지시 | **잡으면 → 기여는 "구조화"에 있다. 그래프도 결정론적 checker도 불필요** |

### G4 / G5 — 왜 두 칸이 다 필요한가

실패의 원인이 두 층 중 어디인지 갈라야 한다.

- **Layer 1 · 구조화** — 자유서술 원문 → 명시적 조건 집합 + 논리 연산자
- **Layer 2 · 판정** — 그 집합과 claim을 비교

|  | 판정을 **LLM**이 | 판정을 **결정론적 코드**가 |
|---|---|---|
| **원문 evidence** (자유서술) | ① finance_verifier — **실패 확인됨** | 성립 불가 (구조가 없어 비교 자체가 안 됨) |
| **구조화된 evidence** | ② **G5** | ③ **G4** |

| 결과 | 결론 |
|---|---|
| G5 통과 | 기여는 **구조화(Layer 1)**. 그래프·결정론적 checker 불필요. 여기서 끝내고 그게 결론 |
| G5 실패 · G4 통과 | 기여는 **결정론적 검사(Layer 2)**. 구조화만으론 부족 |
| 둘 다 실패 | 병목은 **Layer 1 추출 자체**. 여기가 스키마 제약이 필요한 지점 |

**§1.4가 이미 부분적인 답을 준다** — p002는 원문에 "모두 충족"이 명시돼 있는데도 실패했다.
즉 **텍스트 수준의 명시성은 이미 반증됐고**, G5가 측정하는 것은 그보다 강한 조건
(형식 자료구조 + 명시 지시)이다.

### 실행 순서와 이유

```
G0 (표본)  →  G4 (체크리스트)  →  G5 (구조화+LLM)  →  G1 (프롬프트)  →  G2 (분해)
```

**G4를 가장 먼저 돌린다.** 가장 싸고, 통과하면 그래프가 불필요해지므로 가장 위험하다.
**G5는 G4 직후에 돌린다** — G4가 만든 구조를 그대로 재사용하므로 추가 비용이 거의 없고,
둘을 비교해야 위 2×2가 채워진다.

"비싼 것을 만들기 전에 싼 것이 되는지 본다"가 이 게이트의 전부다.

### 통과 판정

- 임계는 **측정 전에** 정한다 (D4, 미정)
- **게이트를 통과하지 못하는 것도 유효한 결과다.** G4가 잡으면 "그래프 없이 결정론적
  검사로 충분하다"가 이 프로젝트의 결론이 되고, 그건 실패가 아니라 발견이다
- 게이트 결과는 `../decisions/`에 기록하고, 통과 전에는 `spec/schema.md`에 손대지 않는다

### 3.1 이 게이트가 답하지 않는 질문 — 2단계 (참조 사슬) ★ 신설

> **후속 판정 (2026-08-24) — 2단계는 폐기됐다.** 적금 전수 59건 수집 후 이름 지목
> 사슬이 **4건**으로 사전등록 임계(6건) 미달. `../decisions/0002-drop-chain-traversal.md`.
> §12의 작업 순서 12~14는 실행하지 않는다. 아래 절은 판단 기록으로 보존한다.

위 게이트는 전부 **상품 하나 안에서** 조건 누락을 잡는 얘기다. 그런데 데이터에는
조건이 **다른 상품을 가리키는** 형태가 따로 있다.

```
[p003 iM함께예금]  신규일 "iM함께적금" 동시 가입 및 만기(12회 불입) 보유
```

이걸 검증하려면 `iM함께적금`이 무엇을 요구하는지 알아야 하고, 그 정보는 예금 하나의
레코드 안에 없다. **프롬프트로는 해결되지 않는다** — 프롬프트에 넣지 않은 레코드를
모델이 읽어올 수는 없다. 빈도도 예외가 아니다: 우대조건이 있는 정기예금 32개 중
**11개**가 이 형태다(전수 집계는 `../reference/cross-product-conditions.md`).

그래서 질문을 두 개로 **분리한다.**

| | 질문 | 답하는 실험 | 상태 |
|---|---|---|---|
| **1단계** | 상품 **하나 안에서** 조건 누락을 잡는 데 구조가 필요한가 | G4 / G5 / G1 / G2 | 위 §3 |
| **2단계** | 조건이 **다른 상품을 가리킬 때**, 사슬을 따라가야 잡히는 누락이 있는가 | 미설계 | 열림 |

**분리가 지키는 것은 두 방향이다.**

- G5가 통과해도(→ 1단계 종료) 2단계는 살아 있다. 레코드를 건너가는 것은 별개 층이다
- 반대로 **2단계의 존재가 1단계를 건너뛰는 근거는 아니다.** 두 홉이 실제로 이어지는
  사슬은 현재 **3건**뿐이고(D1 유의 기준 6건의 절반), 2단계용 claim은 **0건**이다.
  게다가 2단계 실험은 "조건을 어떤 형식으로 적을지"가 정해진 뒤에야 설계되고 그건
  1단계가 결정한다

기록: `../decisions/0001-two-stage-scope.md` (반증 조건 3개 포함).
**2단계에 착수하기 전에도 스키마 코드를 쓰지 않는다** — 순서는 §12 그대로다.

## 4. 핵심 가설 (게이트 통과 시)

> LLM Verifier가 자연어 의미 비교에는 강하지만 복합 조건의 누락 판단에 취약하다면,
> 조건 구조를 명시적으로 표현해 **결정론적 완전성 검사**로 상호 보완할 수 있는가?

구조는 Verifier를 대체하지 않는다.

```
                    Atomic Claim
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
        SLM Verifier          Condition Structure
             │                       │
      자연어 의미 비교             조건 완전성 검사
      숫자·문구·예외 비교          필수조건 누락 검사
             │                       │
             └───────────┬───────────┘
                         ▼
                    Final Verdict
```

**결합 규칙을 미리 정한다** — 감사 C5의 지적("선행 저장소의 문제는 Graph 출력이 최종
판정에 개입하는 **계약이 없었다**는 것"). 구조 검사가 발화했을 때 Verifier 판정을
어떻게 덮는지가 명시되지 않으면 같은 실패를 반복한다.

### 4.1 두 번째 타깃 — INSUFFICIENT ↔ UNSUPPORTED ★ 승격

v1 §3.3은 이 실패를 "Graph가 필요한 문제는 아니다"라며 사실상 스코프에서 뺐다.
**같은 구조를 쓰면 거의 공짜로 얻으므로 두 번째 타깃으로 승격한다.**

Test의 `p017_c02`가 정확한 사례다 — claim은 만기후이자(`mtrt_int`)를 묻는데 evidence는
우대조건(`spcl_cnd`)만 줬다. 정답은 INSUFFICIENT인데 UNSUPPORTED로 과대판정했다.

구조가 있으면 판정이 아니라 **조회**가 된다.

```
claim이 가리키는 필드/노드 타입이 evidence 구조에 존재하는가?
   없음  ->  INSUFFICIENT   (정보 부재)
   있음  ->  값을 비교해 SUPPORTED / UNSUPPORTED
```

승격하는 이유는 두 가지다.

1. **표본이 더 많다** — INSUFFICIENT 사례는 Pilot 4건 + Test 2건 = **6건**이고,
   `spcl_cnd`가 아예 없는 상품이 6개라 신규 생성도 쉽다. `condition_omission` 3건보다
   측정 여건이 낫다
2. **프롬프트로 안 고쳐진 것이 이미 확인됐다** — v3(절차+예시)·v4(부정 규칙) 양방향 실패,
   Nemotron Ultra 550B도 0/4

단, 이 검사는 **1홉 타입 조회**이므로 그래프 순회를 요구하지 않는다. "구조가 필요하다"의
근거는 되지만 "그래프가 필요하다"의 근거는 아니다 — 혼동하지 않는다.

## 5. Schema-first 원칙

### 5.1 데이터 범위 — 은행 정기예금 + **적금까지 확대** ★ 변경

v1 §5.1은 정기예금만으로 못박았다. **적금(`savingProductsSearch`, 은행권)까지 넓힌다.**

근거는 "많으면 좋다"가 아니라 **측정된 상한**이다.

```
은행 정기예금 전수                        38개  (total_count=38, 페이지 추가 없음)
그중 우대조건(spcl_cnd) 있음              32개
조건 항목 2개 이상 (복합조건 후보)         22개
"모두 충족"·"및"·"함께" 명시적 AND 표현     6개   ← 병목
```

**명시적 AND가 6개 상품뿐이다.** 나머지는 항목이 여러 개여도 AND인지 OR인지 원문에
안 적혀 있어(§1.4의 p020·p034가 그 예) gold 확정에 사람 판정이 들어간다. 정기예금만으로는
D1 목표치를 채우면 절반이 주관 판정이 된다.

적금을 고른 이유:

- **필드 스키마가 거의 같다** (`spcl_cnd`/`mtrt_int`/`etc_note` + 기간별 금리 옵션) —
  finance_verifier의 정규화 코드를 대부분 재사용
- 조건 구조가 더 풍부하다 (자동이체·적립방식 조건)

**대출·카드·보험은 계속 제외한다** — 필드 체계가 달라 정규화를 새로 써야 하고, 지금
필요한 건 "AND 복합조건 표본"이라 적금으로 해소된다.

> **선행 프로젝트를 다시 돌릴 필요는 없다.** finance_verifier는 "은행권 정기예금
> 단일 상품군"으로 주장을 한정해 마감했다(`report.md:38`, 상품군 확대는 `:157`에서
> 스코프 밖으로 선언). 한정된 주장은 다른 상품군을 안 봤다고 약해지지 않는다.
> 그리고 **적금에서의 Verifier 성능은 FINeprint가 통제군 A로 직접 측정하므로**
> "약점이 적금에도 일반화된다"는 가정 자체가 불필요하다. 단, §8.5의 층화 보고는 필수다.

### 5.2 최우선 산출물: 구분표 (D2)

두 독립 감사가 **1급 수렴**으로 요구한 단 하나의 문서.

```
어떤 필드를 노드로 / 리터럴 속성으로 / 논리식 내부 값으로 둘 것인가
```

v1 §6의 노드 후보 10종 중 `Rate`·`Term`·수치성 `Condition`을 노드로 두면,
**선행 저장소가 트리플 23.7%에서 겪은 실패를 스키마에 설계해 넣는 것**이 된다.
표 골격은 `../spec/schema.md`. **게이트 통과 후 착수.**

### 5.3 LLM의 역할 제한

```
자유로운 구조 생성        → 금지
사전 정의된 slot 채우기   → 허용
```

### 5.4 불변식 (차단 조건, "개선 항목"이 아니다)

- **원문 필드와 LLM 파생 필드를 강제 분리한다.** 선행 저장소에서 LLM이 생성한
  메타데이터가 추출 입력으로 재투입되어 가짜 연결을 만들고, 그것이 특정 실험 판정
  무효화 사유의 일부가 됐다(C4 + U2)
- **파싱/추출 실패는 버리지 않고 계측한다** (M3)

## 6. 조건 표현 — expression grammar (v1 operator enum 폐기)

v1 §7은 operator를 하나의 enum으로 뒀다.

```
ALL_OF · ANY_OF · NOT · MUTUALLY_EXCLUSIVE · THRESHOLD · TEMPORAL · EXCEPTION
```

**감사 Codex V4: 이 7종은 같은 층위가 아니다.** 논리 결합자(`ALL_OF`/`ANY_OF`/`NOT`),
비교 제약(`THRESHOLD`), scope override(`EXCEPTION`), consistency 제약
(`MUTUALLY_EXCLUSIVE`), 시점(`TEMPORAL`)이 한 enum에 섞였다.

따라서:

- **논리 결합자**만 expression tree의 노드로 둔다
- `THRESHOLD`·`TEMPORAL`은 **조건 술어의 속성**
- `MUTUALLY_EXCLUSIVE`는 operator가 아니라 **validation constraint**로 분리
- `EXCEPTION`은 별도 semantics — §7 참고

## 7. `Required − Claimed`는 ALL_OF MVP의 한 연산일 뿐이다

v1 §8은 집합 차분을 핵심 메커니즘으로 제시했다.

```
Required = {A, B, C}   Claimed = {A, C}   →   missing = {B}   →   UNSUPPORTED
```

**감사 Codex V3: 이게 깨지는 지점이 최소 7종이다.**

```
패러프레이즈       A 를 다른 표현으로 말했는데 매칭 실패
함의 조건          A 를 만족하면 자동으로 B 도 만족되는 경우
k-of-n            "4개 중 2개 이상" — 집합 차분이 성립하지 않음
threshold/range   "30만원 이상" vs "50만원" — 원소가 아니라 비교
예외              "단, X인 경우 제외" — 조건이 아니라 조건의 취소
중첩              조건 안의 조건
claim의 부정      "B 는 필요하지 않다"는 claim
```

**따라서 v1 §8의 평면 집합 차분은 핵심 메커니즘이 아니다.** 위 7종은 각각 별도
semantics와 truth table을 요구한다.

### 7.1 MVP 최소 요건 정정 — 평면 `ALL_OF`로는 부족하다 ★

이 문서의 초판은 "`ALL_OF` 단일 연산의 MVP로 격하"하고 "3건이 모두 순수 `ALL_OF`인지
확인"을 G0 과제로 남겼다. **확인해보니 아니었다** (§1.4).

| 사례 | 실제 구조 | 평면 `ALL_OF`로 커버되나 |
|---|---|---|
| p002 e-그린세이브예금 | 평면 ALL_OF (2개) | ✅ |
| p020 The파트너예금 | 최상위 독립/OR + **갈래 내부 AND** | ❌ |
| p034 Sh해양플라스틱Zero!예금 | 항목 AND + **하위 OR 제약** | ❌ |

**3건 중 2건이 중첩이다.** 평면 리스트 MVP는 1/3만 커버한다.

따라서 MVP 최소 요건을 다음 둘로 올린다.

1. **혜택 스코핑** — `Claim이 어느 혜택을 말하는가 → 그 혜택에 걸린 조건만 Required로`
   p020에서 0.20%의 `Required`는 ①의 조건들이고 ②③은 무관하다. 혜택 단위로 묶지 않으면
   `Required` 자체가 안 나온다. **이것이 v1 §6의 `Benefit ─REQUIRES→ ConditionGroup`이
   실제로 필요한 이유다**
2. **1단계 중첩** — `ALL_OF` 안의 `ANY_OF` (p034의 채널 제약)

**여전히 MVP 제외**: k-of-n, threshold/range 비교, 예외(취소), 2단계 이상 중첩,
claim의 부정. 이들은 별도 semantics를 요구하며, 게이트 이후 단계적으로 다룬다.
슬라이스에 섞여 들어오면 **유형 라벨을 붙여 분리 보고**한다 — "순수 ALL_OF는 잡고
k-of-n에서 깨진다"는 것 자체가 보고할 결과다.

## 8. 평가 설계

상세는 `../spec/evaluation.md`. 골자 셋:

### 8.1 factorial matrix — extractor와 checker 오류를 분리한다

|  | oracle checker | real checker |
|---|---|---|
| **gold 구조** | 상한 (설계가 맞는지) | checker 품질 |
| **추출된 구조** | extractor 품질 | 실제 성능 |

**Hybrid 성능 이전에 extractor recall ceiling을 먼저 보고한다** (Codex V2·V6).
감사 Codex V2의 순환성 지적: 구조를 채우는 것도 LLM이므로, verifier 실패가 extractor
앞단으로 **이동**할 수 있다. 이 표를 채우지 않으면 그 이동을 개선으로 오독한다.

### 8.2 Structure Only는 3-way classifier가 아니다

조건 누락이 감지될 때만 발화하는 **abstaining detector**다. 지표를 A/C와 같은 축으로
재지 않는다 — `trigger precision` / `coverage` / `false reject` (Codex V5).

### 8.3 사전 등록

지표 정의·임계·표본 크기를 **측정 전에 날짜와 함께 커밋한다.** 선행 저장소의 발견 16
("사전 등록은 오류를 막지 않고 드러낸다")이 근거이고, 같은 저장소의 재현성 실패 2건이
반례다.

### 8.4 ablation

```
A. Verifier Only        ← finance_verifier 코드 재사용, 새로 만들지 않음
B. Structure Only       ← abstaining detector
C. Verifier + Structure
```

측정 목적은 "구조를 붙였다"가 아니라 **"실제로 관찰된 failure를 얼마나 줄였는가"** 다.

### 8.5 층화 보고 (필수) ★ 신설

§5.1에서 적금까지 넓혔으므로, **집계값만 보고하면 안 된다.** 다음 축으로 나눠 보고한다.

```
상품군       정기예금 / 적금
조건 구조    평면 ALL_OF / 혜택스코핑 필요 / 1단계 중첩 / MVP 제외 유형(k-of-n 등)
실패 유형    condition_omission / INSUFFICIENT 경계
gold 출처    원문에 AND 명시 / 사람이 AND 판정 / 판정 불가(제외)
```

이유는 하나다. **원래 실패가 발견된 분포(정기예금)와 측정하는 분포가 달라질 수 있다.**
적금에서 Verifier가 잘하는데 slice가 적금 위주면, "구조가 필요하다"는 결론이 평균에
묻혀 성립해버린다. 나눠 보고하면 그 차이가 결과가 된다.

**알려진 정기예금 3건(`p002_c04_3`·`p020_c02`·`p034_c02`)은 slice에 반드시 유지한다** —
선행 프로젝트와 직접 대조 가능한 유일한 지점이다.

## 9. 스코프

### MVP 우선순위

1. `condition_omission` — **혜택 스코핑 + 1단계 중첩까지** (§7.1)
2. `INSUFFICIENT ↔ UNSUPPORTED` — 필드 커버리지 조회 (§4.1)
3. (통과 후) 예외조건, 상호배타, k-of-n, threshold, temporal

### MVP 제외

```
금융상품 추천 · 고객 개인화 · 대규모 graph traversal
PageRank 등 graph algorithm · 자유형 multi-hop reasoning
대출·카드·보험 확대 · 구조를 위한 구조
```

**graph algorithm은 문제에서 필요성이 확인될 때만 도입한다.**
"Graph 프로젝트"라는 이름값을 위해 그래프를 쓰지 않는다 — §3 게이트가 그 방어선이다.

---

## 10. 그래프 수명 정책 ★ 신설 (v1에 없던 층)

감사 Claude U1: 선행 저장소의 응용 경로는 **그래프를 아예 저장하지 않았다**
(`persist` 호출 0건). README가 KG 도입 근거로 내세운 "1월 기사 + 3월 기사 연결"은
코드 구조상 불가능했다. **스키마를 완벽히 고정해도 이 층은 해결되지 않는다.**

착수 전에 정한다.

- 구조를 요청마다 즉석 생성(JIT)하고 버리는가, 영속화하는가
- 영속화하면 재구축 트리거는 무엇인가 (공시 월 변경? 상품 추가?)
- 상품 스냅샷 버전과 구조 버전을 어떻게 대응시키는가

`condition_omission` 검사가 **단일 상품 내부**에서만 일어난다면 JIT + 폐기로 충분하고,
그러면 그래프 DB 자체가 불필요하다 — 이것도 §3 게이트가 답할 질문이다.

## 11. 저장소 정책

### 11.1 신규 저장소, history 미승계, **단 진단 산출물은 명시 이식**

v1 §13은 "기존 git history를 잇지 않는다"였다. 감사 C2(양쪽 1급 수렴)의 경고:
**이 저장소의 최대 이관 자산은 코드가 아니라 방법론이고, v1 §13이 그것을 버릴 위험이 있다.**

따라서 이식한다(완료):

```
docs/audit/00-comparison.md                     두 감사 비교 + 수정 17항
docs/audit/claude-architecture-audit.md         기존 구조 실측
docs/audit/codex-adversarial-review.md          가정 반증
docs/handoff/v1-original.md                     원본 보존
docs/reference/finance-verifier-findings.md     선행 실측의 확립/미확립 구분
```

방법론 자산(사전 등록 표 구조, fixture 검증, raw response logging, 실제 응답 모델 ID 기록)은
**패턴으로 승계하고 코드는 새로 쓴다** (Q1 조정안). 수용 기준은 Codex 안을 채택:
**"생성·strip·metric·fixture 검증이 하나의 재현 가능한 명령으로 고정되고 모든 지표가
baseline과 완전 일치"** — 이걸 eval harness의 완료 조건으로 쓴다.

### 11.2 이관 분류 정정 (v1 §12)

| v1 분류 | 정정 |

## 13. 여러 Agent 사용 시

v1 §14의 역할 분담(Cowork=spec / Orca=구현 / GPT=비판·조사)은 유지한다. v1 §16의 주의도
유지하되 감사 Codex V8을 반영해 **blind review 모드**를 추가한다.

> 여러 Agent가 같은 문서를 읽고 같은 결론을 냈다면 그건 독립 검증이 아니라
> 공통 입력의 결과다.

중요한 결정에 반증이 필요하면, **그 결론을 읽지 않은 reviewer에게** 원본 자료만 주고
따로 검토시킨다. 선행 저장소의 감사 2건이 실제로 이 방식으로 수행됐고, 그때
**원본 문서에 없던 판정 5건에 양쪽이 독립적으로 도달한 것**이 가장 강한 신호였다.

## 14. 핵심 질문

> **자연어 의미 비교에 강한 LLM Verifier와, 복합 조건의 완전성을 결정론적으로 검사하는
> 구조를 결합하면, 각각을 단독으로 쓸 때보다 금융 답변의 False Accept를 실제로 줄일 수 있는가?**

첫 번째로 답할 질문은 그보다 앞에 있고, 두 층으로 갈린다.

> **① `condition_omission`은 정말 구조가 필요한 문제인가?
> 프롬프트·분해단위로 이미 풀리지는 않는가?**
>
> **② 구조가 필요하다면, 기여는 "구조화"(Layer 1)인가 "결정론적 검사"(Layer 2)인가?**
> 구조화된 evidence를 그냥 LLM에게 줘도 되면(G5), 결정론적 checker도 그래프도 필요 없다.
