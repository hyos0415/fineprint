# prereg-14 · 사람이 웹에서 한 번 완주한다 — 막힌 자리를 센다

> 작성 2026-09-02 (**재기 전**) · 로드맵 F4-3 · 이슈
> [#42](https://github.com/hyos0415/fineprint/issues/42) · 화면 관찰은 이슈
> [#40](https://github.com/hyos0415/fineprint/issues/40) 코멘트

**이 문서는 재기 전에 쓴다.** 지표·임계·표본을 측정 **전에** 못 박는 것이 이 저장소의
규율이고(`CLAUDE.md` 3번), 실제로 `prereg-01` 은 예측 7개 중 6개가 맞았고 틀린 하나
때문에 방향 하나를 폐기했다(`0002`).

## 왜 재나 — 지금은 인상만 있다

F4-2 를 만들고 사람이 화면을 눌러 보다가 셋을 관찰했다. **셋 다 규모를 모른다.**

```
1. 공시 원문을 그대로 물으니 **만든 사람도 못 알아본다**
   "손하나로인증 서비스 등록" · "온실가스 줄이기 실천서약서 동의" · "통장미발급"
2. 화면 문구에 **내부 용어**가 그대로 나온다
   스코프 · 층 · 메인 · 사유 코드 · `급여_연금이체` 같은 밑줄 이름 · "판정을 엽니다" · %p
3. **계단식 조건**은 유형 질문에 답한 뒤 문구 질문이 또 와서, 같은 걸 두 번 묻는 것처럼 느껴진다
```

**고치기 전에 센다.** 재기 전에 고치면 무엇이 나아졌는지 알 수 없다.

## §1 무엇을 세나 — 정의 (재기 전 확정)

```
M1  답을 못 하겠는 질문 수 / 받은 질문 수
    "못 하겠다" 의 정의 — **공시 문구를 읽고도 예/아니오/모름 중 무엇을 골라야 할지
    모르겠어서 짐작으로 눌렀다.** 모름을 **의도적으로** 고른 것은 여기 안 센다
    (그건 시스템이 지원하는 답이다 · `0024` P5)

M2  뜻을 모르는 낱말 수 (중복 제외)
    화면에 나온 낱말 중 **처음 보거나 뜻이 확실하지 않은 것**. 낱말을 그때그때 적는다

M3  같은 걸 두 번 묻는 것처럼 느낀 자리 수
    유형 질문에 답한 뒤 같은 유형의 문구 질문이 와서 **왜 또 묻는지 몰랐던** 횟수

M4  완주했나 (예/아니오) · 걸린 시간 (분)
    **완주율은 지표가 아니다**(`0026` D2). 기록만 한다
```

## §2 표본 — 어떻게 도나

```
사람      1명 (만든 사람). **이것이 이 측정의 가장 큰 약점이다** — §4 에 적는다
세션      2회
  (가) 은행권 12개월 · 스코프 없음 · 선호 없음        ← 질문이 가장 많은 경로 (39개)
  (나) 은행권 6개월 · 스코프 `카카오` · 선호 2문항     ← 계단식 조건이 나오는 경로
기록      질문마다 (순서, 조건 유형, 고른 답, M1 해당 여부) 를 적는다
         낱말은 나올 때마다 적는다
```

**(나)를 넣는 이유** — 26주적금의 계단식 조건이 6개월에만 있다(실측: `주차` 문구가
`bank/6개월` 에만 2개). M3 를 재려면 그 경로를 반드시 지나야 한다.

## §3 예측 — 재기 전에 적는다

```
P1  M1 이 **받은 질문의 30% 이상**이다
    근거 — 조건 유형 17종 중 사용자 상태로 O/X 가 명확한 것(급여이체·자동이체·
    카드실적·비대면가입)은 절반이 안 된다. 나머지는 기관 고유 서비스명이나
    실천 미션이라 문구를 읽어도 판단이 어렵다

P2  M2 가 **8개 이상**이다
    근거 — 이슈 #40 에 뽑아 둔 내부 용어 표가 이미 8행이다(스코프·층·메인·사유 코드·
    밑줄 이름·판정을 엽니다·%p·공시)

P3  M3 이 **1회 이상** 나온다 — (나) 경로에서 26주적금을 만나면 반드시 나온다

P4  완주한다 (M4=예). 39개를 다 답할 수 있다
    근거 — 화면 계약 검사가 중간 상태 전수에서 통과하므로 막혀서 못 가는 자리는 없다

P5  M1 에 해당한 질문은 **꼬리에 몰린다** — 질문 순서가 커버리지 순(`0018`)이라
    앞쪽은 일반적인 조건(급여이체·자동이체)이고 뒤쪽이 기관 고유 조건이다
    관측 방법 — M1 해당 질문의 순서 번호 중앙값이 **전체의 후반부(50% 지점 이후)**인가
```

## §4 이 측정이 못 하는 것 — 미리 적는다

```
표본 1명이고 그 1명이 만든 사람이다
  → 문구를 이미 아는 사람이라 M1·M2 를 **과소 추정**한다. 편향 방향이 명확하다.
    그러므로 여기서 나온 수는 **하한**으로 읽는다
자기보고다
  → "못 하겠다" 의 판정을 스스로 한다. 그래서 M1 의 정의를 위에 못 박았다
학습 효과
  → (가)를 먼저 하면 (나)에서 낱말을 이미 안다. **M2 는 (가)에서만 센다**
```

## §5 이 결과로 무엇을 하나

```
P1 이 맞으면    문구 풀이가 필요하다. 다만 **근거가 있어야 한다** — A2(상품설명서)가
              선행이고, 우리가 용어 사전을 만드는 쪽은 안 간다(`0019` 위험)
P1 이 틀리면    (30% 미만) 문구 풀이는 급하지 않다. 내부 용어(M2)만 고친다
P2 가 맞으면    이슈 #40 의 표를 그대로 작업 지시서로 쓴다. 고칠 자리는 `view.display()`
P3 이 맞으면    계단식 안내 문구를 더한다 — "이 조건은 단계가 있습니다" 류
P5 가 맞으면    **후보를 좁힌 사용자가 더 많이 막힌다.** 스코프를 걸면 꼬리 조건만
              남으니까. 그러면 A7(스코프 밖 최고 금리)과 같은 자리에서 다뤄야 한다
```

**무엇을 고칠지는 위에 있고, 얼마나 고칠지는 재고 나서 정한다.**

# §6 개정 — M1 정의를 고친다 (1런 뒤 · 2런 **전에** 적는다)

**측정 전에 고친다.** 1런에서 관측된 실패를 원래 정의가 담지 못했다.
`CLAUDE.md` 3번대로 **사유·편향 방향·완화 조치**를 함께 적는다(`prereg-02` §2.1 선례).

## 무엇이 틀렸나

M1 을 *"짐작으로 눌렀나"* 로 정의했는데, 사람이 이렇게 보고했다.

> 일부러 모른다 한 거 아니야. **짐작도 전혀 없었거든.** 공시만 보고선 어떤 상품인지
> 알 수 없는 게 맥락이 전혀 없어서 **선택을 할 수 없다** 이게 가장 큰 문제네

실패 모드가 셋인데 정의가 둘만 봤다.

```
짐작으로 눌렀다          ← 원래 M1 이 잡으려던 것
의도적으로 모름을 골랐다   ← 원래 M1 에서 뺀 것 (시스템이 지원하는 답 · `0024` P5)
**고를 수가 없다**        ← **정의에 없었다.** 판단 자체가 불가능하다
```

**편향 방향** — 원래 정의로 세면 M1 = 0 이 나온다. 짐작을 안 했으니까. 그러면
**문제가 없는 것처럼 보인다.** 실패를 과소 추정하는 방향이다.

**완화 조치** — 1런 기록을 지우지 않고 그대로 남긴다. 2런과 나란히 둔다.

## 고친 정의 — M1 을 셋으로 가른다

```
M1a  **맥락이 없어서** 고를 수 없었다 — 어느 기관/상품의 문구인지 몰라서
M1b  **용어를 몰라서** 고를 수 없었다 — 기관은 알지만 그 기관 고유 용어를 모른다
     (예: 제주은행 "탑스" · 농협 "손하나로인증")
M1c  **짐작으로** 눌렀다 — 고를 수는 있었지만 근거가 없었다

안 센다   의도적으로 "모름" 을 고른 것. 그건 시스템이 지원하는 답이다
```

## 1런 결과 (고치기 전 · 2026-09-02)

```
세션        (가) 은행권 12개월 · 스코프 없음 · 선호 없음
M1a        관측됨 — "당행이 어디를 가리키는지 모른다"(질문 2 · 첫거래_신규고객)
M1b        관측됨 — "탑스가 무슨 말인지 모른다"(질문 8 · 주거래_장기거래_재예치)
M1c        **0건** ("짐작도 전혀 없었다")
결론        원래 M1 정의로는 0건 = 문제 없음. **실패를 못 담았다**
```

## 1런과 2런 사이에 **개입이 있었다** — 반복 측정이 아니다

1런 뒤에 고쳤다(같은 날).

```
고친 것   문구마다 **기관을 붙인다** — `rank_questions` 가 기관을 버리고 있었다
         "당행 원화 정기예금 보유이력이 없는 경우" → **"전북은행 — 당행 …"**
규모      유형 16개 중 15개가 문구를 2개 이상 기관에서 모아 왔다.
         문구 209개 중 "당행/본행/자행" 이 든 것 18개(8.6%)
안 고친 것  용어 자체(탑스·손하나로) — **공시에 정의가 없다**(실측: `spcl_cnd` 에만 나오고
         `etc_note`·`join_member`·`mtrt_int` 어디에도 없다). A2(설명서) 대기다
```

그러므로 2런은 1런의 반복이 아니라 **전/후**다. 두 런의 M1a 를 비교하는 것이
이 개입의 효과 측정이다.

## 2런 예측 (재기 전)

```
Q1  **M1a = 0** 이다 — 기관이 붙었으니 "어느 기관인지 몰라서" 는 사라져야 한다.
    하나라도 남으면 A 가 덜 고쳐진 것이다 (예: 기관이 빈 문구)
Q2  **M1b ≥ 3개** 다 — 맥락이 생겨 읽기 쉬워지면 **용어 문제가 더 눈에 띈다.**
    1런에서 이미 둘(탑스·손하나로 계열)이 나왔다
Q3  M1c 는 여전히 0에 가깝다 — 사람이 짐작으로 누르는 성향이 아니다(1런 관측)
Q4  M2(뜻 모르는 낱말)는 **§3 P2 의 8개 예측을 그대로 둔다.**
    다만 1런에서 세지 않았으므로 2런이 첫 측정이다
Q5  P5(꼬리에 몰린다)를 그대로 둔다 — 질문 순서가 커버리지 순이다(`0018`)
```

**Q2 가 맞으면** A2(상품설명서)와 G(검색·리랭커)의 수요가 측정으로 뒷받침된다 —
지금까지 로드맵이 *"구멍은 RAG 가 아니다"* 라고 적어 온 자리에 **첫 반례**가 생긴다.
그때도 우리가 용어 사전을 만드는 쪽은 안 간다(`0019` 위험).

# §7 2런 결과 (개입 뒤 · 2026-09-02)

세션 **(가) 은행권 12개월 · 스코프 없음 · 선호 없음** · 받은 질문 39개 · 완주.

```
M1a  0건   맥락이 없어서 못 고른 자리      ← Q1 적중  ("막힌 건 없었어")
M1b  2건   용어를 몰라서 못 고른 자리      ← Q2(3개 이상) **빗나감**
           탑스 · 소중한 날
M1c  0건   짐작으로 누른 자리            ← Q3 적중
M2   2개   뜻 모르는 낱말               ← Q4(8개 이상) **빗나감**
M4   완주함                          ← §3 P4 적중
Q5   **측정 불능** — M1 해당이 2건뿐이라 "꼬리에 몰리나"의 중앙값이 의미 없다
```

**예측 5개 중 2 적중 · 2 빗나감 · 1 측정 불능.**

## Q1 이 맞았다 — 기관을 붙인 개입이 들었다

1런에서 *"당행이 어디를 가리키는지 모른다"* 로 막혔던 자리가 **0건**이 됐다. 고친 것은
하나다 — `rank_questions` 가 버리던 기관을 문구마다 같이 담아서 `"전북은행 — 당행 …"`
으로 낸다. 1런과 2런은 반복이 아니라 **전/후**이므로(§ 위) 이 0건이 그 개입의 효과다.

## Q4 는 왜 빗나갔나 — §4 가 예측한 편향이 그대로 나왔다

Q4 의 근거는 이슈 #40 에 뽑아 둔 **내부 용어 표 8행**이었다(스코프 · 층 · 메인 ·
사유 코드 · 밑줄 이름 · "판정을 엽니다" · %p · 공시). 사람은 그중 **하나도 안 셌다.**
만든 사람이라 뜻을 이미 알기 때문이다.

§4 에 미리 적어 둔 문장이 있다 — *"문구를 이미 아는 사람이라 M1·M2 를 과소 추정한다."*
그 편향이 M2 에서 **그대로 실현됐다.** 결론은 하나다.

> **M2 는 만든 사람으로 잴 수 없다.** 다음에 M2 를 쓰려면 표본이 바뀌어야 한다.

다만 **내부 용어 문제 자체는 이 측정과 무관하게 남는다.** 화면에 `급여_연금이체` 라고
쓰여 있는 것은 **관측**이지 자기보고가 아니다. 이슈 #40 의 표는 M2 가 뒷받침하지
않아도 성립한다.

## Q2 는 왜 빗나갔나 — 예측 근거가 과했다

*"맥락이 생겨 읽기 쉬워지면 용어 문제가 더 눈에 띈다"* 로 3개 이상을 예측했는데 2개였다.
표본이 하한이므로 "3개 미만"이 확정된 것은 아니지만, **근거가 과했던 것으로 읽는다.**

**§5 의 판정은 바뀌지 않는다** — 2건도 공시에 뜻이 없는 낱말이고, A2(상품설명서) 없이는
못 푼다.

## M1b 2건의 공통점 — 공시 어디에도 뜻이 없다 (실측)

```
탑스      제주은행 · 제주Dream 정기예금    "③탑스, 주거래 고객"
소중한 날   국민은행 · KB내맘대로적금       "… 장기거래, 첫 거래, 주택청약종합저축, 소중한 날"
```

둘 다 **`spcl_cnd`(우대조건) 칸에만** 나오고 `etc_note` · `join_member` · `join_deny` ·
`mtrt_int` 어디에도 정의가 없다. 1런의 탑스와 같은 모양이고, 이제 **기관 2곳 · 사례 2건**이다.

이것이 로드맵 **G(검색·리랭커)** 의 첫 근거 있는 수요다 — 지금까지 로드맵은 *"구멍은
RAG 가 아니다"* 라고 적어 왔는데, **공시 안에 답이 없는 낱말**이 측정으로 나왔다.
선행은 A2(상품설명서 코퍼스)이고, 우리가 용어 사전을 만드는 쪽은 안 간다(`0019` 위험).

# §8 사전등록에 없던 관측 — 조건을 못 채우는 사용자에게는 화면이 틀린 순서로 보인다

**이것은 사전등록에 없다.** 2런 도중에 사람이 한 말에서 나왔으므로 예측이 없고,
따라서 **가설 검증이 아니라 관측**이다. 그래서 지표로 세지 않고 여기 따로 적는다.

> 사실상 내 기준에서 답하는 게 별 의미가 없는 게 **카드 안 쓰고 소득 없는 상황**이니깐

## 재 봤다 — 은행권 12개월 · 메인 67개

카드·급여·잔액·주거래·타상품에 걸린 조건은 "아니오", 돈이 안 드는 조건
(비대면가입 · 마케팅동의 · 첫거래 · 오픈뱅킹)은 "예" 로 9개를 답한 프로필이다.

```
                     확정 상품    확정 금리 최고    화면 맨 위(최대순)          확정순 1위
아무 답 없음             4개       3.64%        카카오뱅크 우리아이적금        Only One 주거래 우대적금
                                              2.54~5.92%               3.64~4.06%
카드X·소득X (답 9개)     23개       3.64%        (같음)                    (같음)
전부 예 (대조군)        39개       5.92%        카카오뱅크 우리아이적금 5.92%    (같은 상품)
```

## 세 가지가 나온다

**1. 말이 맞다 — 금리는 안 움직인다.** 답을 9개 해도 **확정 금리 최고값이 3.64% 그대로**다.
이 사람이 못 채우는 조건에 걸린 우대는 답해도 열리지 않는다. 반면 전부 채우는 프로필은
5.92% 까지 간다. **격차 2.28%p 가 조건을 채울 수 있는지에서 온다.**

**2. 그런데 확정 상품 수는 4개 → 23개다.** 답해서 얻는 것이 *"더 높은 금리"* 가 아니라
**"이 값이 맞다는 확신"** 이다. 답하기 전에는 67개 중 4개만 값이 확정이었다.
이것이 `problem.md` 가 말한 것과 정확히 같다 — 우리가 파는 것은 높은 숫자가 아니라
**믿을 수 있는 숫자**다.

**3. 화면이 그걸 안 보여준다.** 이 사람에게 화면 맨 위는 `2.54~5.92%` 인데, 실제로
확실히 받는 것은 `3.64~4.06%` 인 다른 상품이다. `0017` 이 기본 정렬을 최대순으로 정하면서
**`--sort lo`(확정된 값 순)를 남겼는데, 웹 폼에 그 선택지가 없다** — CLI 에만 있다
(`view.build()` 가 정렬 인자를 안 받는다).

`0017` 의 Evidence 에 이 문장이 있다.

> **조건을 못 채우는 사용자에게만 크게 움직인다.** 그 사람이 정확히 알아야 할 사람이므로
> 방향이 맞다.

**그 사용자가 나타났고, 그 사람이 봐야 할 정렬이 화면에 없었다.** `0017` 이 옳게 예측한
자리에서 구현이 반만 따라간 것이다.

## 무엇을 하나 — 아직 정하지 않는다

관측 1건이고 사전등록이 없다. 후보는 둘이다.

```
A  웹 폼에 정렬 선택지를 낸다 (`0017` 이 이미 남겨 둔 `--sort lo` 를 노출)
   장점 — 결정 하나로 끝난다. 이미 있는 기능이다
   위험 — 사용자가 무엇을 고를지 모르는 선택지를 하나 더 준다
B  조건을 못 채우는 것이 관측되면 **화면이 알아서 확정순을 같이 보여준다**
   장점 — 고르게 하지 않는다
   위험 — "못 채운다" 를 시스템이 판정하는 것이다. 이 프로젝트는 선호를 추측하지 않는다
        (`CLAUDE.md` 한 줄 요약) — 그 선을 넘는지 따져야 한다
```

**B 는 선을 넘을 소지가 있으므로 사람이 정한다.** 결정 전에 재야 할 것은 하나다 —
*최대순 1위와 확정순 1위가 갈리는 사용자가 얼마나 되나* (페르소나 전수로 잴 수 있다).

## 재 봤다 — 5명 중 1명이 갈린다 (사후 측정 · 예측 없음)

무작위로 답한 사용자 200명을 만들어 **전부 답한 끝 상태**에서 둘을 비교했다.
끝 상태로 재는 이유 — 다 답한 뒤에도 갈리면 그때는 사용자가 무엇을 놓치는지가 확정이다.

```
최대순 1위 ≠ 확정순 1위      39명 / 200명 (19.5%)
갈릴 때 확정 금리 차이        중앙값 +0.38%p · 최대 +1.44%p
0.5%p 이상 놓치는 사람        19명 (9.5%)
```

**5명 중 1명이 화면 맨 위 상품보다 확실히 더 주는 상품을 옆에 두고 있다.** 그중 절반은
0.5%p 이상이다. 1천만원 1년이면 5만원이고, `problem.md` 가 인용한 피해 사례와 방향이
같다 — **보이는 숫자와 받는 숫자가 다르다.**

이 측정은 **사후**다(예측을 안 적고 쟀다). 그래서 "19.5%" 를 검증된 수로 쓰지 않고,
**A/B 중 무엇을 할지 사람이 정하는 데 쓰는 참고값**으로만 쓴다. 무작위 답 사용자가
실제 사용자 분포를 대표하지도 않는다.

## 정했다 — A (2026-09-02)

사람이 **A** 를 골랐다. 기록은 `decisions/0044` 다. 요약하면 이렇다.

```
시작 폼에 정렬 선택지를 낸다      "조건을 다 채웠을 때…" · "지금 확실히 받는 금리 순"
화면 안에서도 버튼으로 바꾼다      답한 것은 그대로 유지된다 (무상태 · `0040`)
성과 줄 낱말도 같이 바꾼다        확정순에서 `최고` 는 거짓이다 → `확실히 받는 것 중 최고`
A8 에 그 낱말 검사를 **더한다**   원래 있던 `최고` 검사는 그대로 둔다
정렬 규칙을 한 곳에 모은다        `prefs.sorter()` — 흩어져 있으면 노출하는 순간 갈라진다
```

**B 는 기각했다** — *"이 사람은 조건을 못 채운다"* 를 시스템이 판정하는 것이고,
그건 답을 대신 정하는 쪽으로 가는 첫 걸음이다.

검사는 이제 **두 정렬을 다 돈다**(`check_screen_contract.py` 가 인자 없이 hi·lo 를
차례로 돈다). 두 정렬 모두 페르소나 3 + 시드 30 · 중간 상태 전수에서 위반 0건이고,
정렬만 최대순으로 되돌리고 라벨은 확정순으로 두는 고장을 심으면 세션 하나에서
**A8 이 30건** 잡는다.
