# 1부 · 조건 매칭 (이슈 #2)

## 1.1 애매함의 규모 — 실측

추출된 조건 항목 **1,051개**(은행권 711 · 저축은행 340) 기준.

| | 건수 | 비율 | 무엇이 문제인가 |
|---|---:|---:|---|
| **금액·횟수 임계가 붙어 있다** | **143** | **13.6%** | 되물어서 판정한다 (§1.3) |
| 사용자가 답할 수 없는 층 2 유형 | 131 | 12.5% | 실천·미션 66 · 무조건·특판 46 · 쿠폰·코드 19 |
| `기타`로 분류됨 | 40 | 3.8% | 어느 상태 변수에도 대응하지 않는다 |
| 부정 조건 (`must_not_have`) | 6 | 0.6% | 예상보다 적다 (§1.4) |

> **[정정 2026-08-26]** 처음 적은 270건(25.7%)은 **부풀려진 값이었다.** 정규식이
> `12개월` 같은 **가입기간 표기까지 임계로 오인**했다. 기간은 `applies_to_term` 이 이미
> 처리하므로 임계가 아니다.
>
> ```
> 느슨한 정규식        270  25.7%   ← 기간 표기 149건이 섞였다
> 엄격한 정규식        121  11.5%   ← 실제 임계
>    금액 (3천만원 등)   58   5.5%
>    횟수·인원 (6회 이상) 64   6.1%
> ```
>
> **A안의 대가가 절반 이하로 줄었다.** 11.5%만 범위로 빠진다.
>
> **[재정정 2026-08-26]** 11.5%도 **낮게 잡힌 값이었다.** 단위 목록에 `천만원`이 없어서
> `"5천만원 이상 가입"`을 임계로 세지 못했다. 단위를 고친 뒤 **143건(13.6%)**이다.
>
> 이 버그는 방향이 나쁘다 — **임계인 줄 모르면 사용자 답을 그대로 충족으로 세어
> 과대 진술이 된다.** 그리고 값을 읽을 때 `천만원`을 `만원`으로 읽으면 5천만원이
> 5만원이 되어 **1,000배 오차**가 난다. 그래서 검사 정규식과 파싱 정규식이 **같은 단위
> 목록**을 쓰게 묶었다(`calculate.py` 의 `THRESHOLD_MONEY` · `MONEY_VALUE`).

**임계값이 가장 큰 문제다.** 예시:

```
"6~12개월제(만기일시지급식) 5천만원 이상 가입"
"만기일 기준 전전월 마지막 영업일에 수익증권(펀드)을 3천만원 이상 보유 시"
"급여이체 실적(월 50만원 이상) 6개월 이상"
```

## 1.2 지금 구현된 규칙 — 사람 승인이 필요하다

`src/analysis/calculate.py`의 `condition_met()`에 이미 들어간 규칙이다.
**사전등록 없이 내가 정한 것이므로 여기서 명시하고 승인을 받는다.**

```python
층 2 중 "무조건_특판_이벤트"   →  항상 충족  (가입고객 모두에게 적용된다)
층 2 중 "판정불가_불특정"      →  판정 불가 (None)
polarity == "must_not_have"  →  사용자 상태를 반대로 읽는다
사용자가 답하지 않은 유형       →  판정 불가 (None)
판정 불가가 있으면            →  하나의 값이 아니라 범위를 낸다
```

**범위를 내는 것이 이 설계의 핵심이다.** 모르는 것을 추측하지 않는다.

## 1.3 정해야 할 것 — 임계값 처리 (270건, 25.7%)

**후보 넷.** 각각 무엇을 얻고 잃는지 적는다.

| | 방법 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A** | **임계가 붙은 조건은 "판정 불가"로 둔다** | 정직하다. 틀린 숫자를 안 낸다 | 25.7%가 범위로 빠져 추천이 흐려진다 |
| **B** | **임계를 추출해 사용자에게 금액·횟수를 묻는다** | 정확해진다 | 재추출 $1 + 입력 항목이 늘어난다 |
| **C** | 사용자가 "O"라고 하면 임계도 충족으로 본다 | 추천이 선명하다 | **과대 추정.** 이 프로젝트가 잡으려던 실패다 |
| **D** | 금액은 이미 묻는다(가입금액). 그것과 비교한다 | 일부는 정확해진다 | "펀드 보유액"처럼 안 묻는 항목은 여전히 모른다 |

**C는 배제한다.** 사용자가 "카드 씀"이라고 답했는데 조건이 "월 100만원 이상"이면
충족이 아닐 수 있고, 그걸 충족으로 계산하면 실제보다 높은 금리를 보여준다.
`problem.md` §1이 금지한 방향이다.

### 결정 — B를 채택했다. 수치가 필요하면 **되묻는다** (2026-08-26)

A(판정 불가로 두기)를 먼저 구현했고, 같은 날 **B로 옮겼다.** 사람 결정이다 —
*"급여이체 실적에 대한 수치가 필요한 경우 그냥 다시금 물어보게 하자."*

**재추출은 필요 없었다.** $1이 든다고 적었는데 **근거 문구에 숫자가 이미 있었다.**
임계 항목 143개 중 **132개(92.3%)**를 정규식으로 읽어낸다.

```
"급여이체 실적(월 50만원 이상) 6개월 이상"   →  (금액, 500,000, 최소)
"펀드를 3천만원 이상 보유 시"                →  (금액, 30,000,000, 최소)
"자동이체 6회 이상"                         →  (횟수, 6, 최소)
```

사용자 답은 **단위를 붙인 키**로 받는다. 유형만 O/X로 받으면 금액인지 횟수인지 몰라
엉뚱한 비교를 하게 된다.

```
--state 자동이체                         "자동이체 하십니까"      → 예
--state 자동이체_횟수=6                   "월 몇 회 하십니까"      → 6회
--state 잔액_평잔_가입금액_금액=5000만원     "평잔이 얼마입니까"      → 5천만원
```

**질문은 유형 하나에 하나다.** 상품마다 임계가 달라도 "월 몇 회 하십니까"는 한 번
물으면 되고, 비교는 상품별로 각자 한다. 계산기가 물어야 할 질문을 **답 하나가 상품
몇 개를 확정으로 옮기는지** 순으로 보여준다.

```
잔액_평잔_가입금액_금액   상품 6개   임계 30만원 · 50만원 · 2,000만원 · 5,000만원
카드실적_금액            상품 4개   임계 10만원 · 100만원
급여_연금이체_금액         상품 3개   임계 10만원 · 50만원
자동이체_횟수             상품 2개   임계 3회 · 6회
```

### 얼마나 확정이 늘어났나 — 실측

12개월 상품 기준이다. "답할 수 있는 것만"은 실천·미션과 쿠폰을 안 묻는 경우다(§1.5).

| | | A 확정 | A 범위 | **B 확정** | **B 범위** |
|---|---|---:|---:|---:|---:|
| 은행권 79개 | 전부 답함 | 51 | 13 | **64** | **0** |
| | 답할 수 있는 것만 | 40 | 24 | **51** | 13 |
| 저축은행 297개 | 전부 답함 | 86 | 23 | **105** | **4** |
| | 답할 수 있는 것만 | 82 | 27 | **100** | 9 |

**확정이 25% 늘고, 은행권은 범위가 0이 된다.** 남는 범위의 원인은 임계가 아니라
**답할 수 없는 유형**(실천·미션 등 §1.5)과 **계단식 우대**(§1.6)다 — 둘 다 다음 결정이다.

**폴백 83.9%는 그대로다.** 임계 처리는 추출이 아니라 판정 단계라서 닫힘률과 무관하다.

### 남긴 것 — A 경로는 코드에 그대로 있다

수치를 아직 안 물어봤으면 **A와 똑같이 동작한다**(판정 불가 → 범위). 사용자가 설문을
끝까지 안 채워도 시스템이 멈추지 않고, 그때 보여주는 값이 과대 진술이 아니다.

```
금액   \d[\d,]*(천만원|백만원|십만원|억원|만원|천원|억|원)
횟수   \d+(회|건|명|개|일|주차|좌)\s*(이상|이내|초과|미만|까지)
기간   제외 — applies_to_term 이 처리한다
방향   이상·초과·부터 → 최소 / 이내·미만·이하·까지 → 최대
```

### 부수 수정 — 금리 상한을 넣었다

A를 구현하다 **AI가 금액을 금리 칸에 넣은 사례 2건**을 발견했다.

```
"6~12개월제(만기일시지급식) 5천만원 이상 가입"
  → rate = 5000 · rate = 5000000     (은행권 711개 항목 중 2건 · 0.3%)
```

스키마에 금리 상한이 없어 통과했다. **한 항목이 20%p 를 넘으면 금리가 아니라고
본다**(`MAX_ITEM_RATE`). 관측된 정상 최댓값은 9.0%p("31일 저금 성공 시 연 9.0%")다.

이 2건은 이미 실패로 세고 있었으므로 **폴백 83.9% 판정에는 영향이 없다.**
표시 문자열만 `-5000000.10%p` → `-0.10%p` 로 정상화됐다.

## 1.4 부수 관측 — 부정 조건이 6건뿐이다

`must_not_have`가 1,051개 중 **6건(0.6%)**이다. 전부 같은 문구다.

```
"신규가입일 포함 14일 이내 타기관 공인인증서 미등록시 우대금리 적용해제"
```

**금융위원회 소비자 경보가 지목한 유형인데 데이터에는 거의 없다.**

> "A씨는 최고금리 10%를 보고 적금에 가입했으나 **가입 이전 6개월간 카드 사용실적이
> 있어** 우대금리를 적용받지 못했다" (2023-04-05)

`problem-v1-verifier.md` §2-(나)가 이 유형을 두 번째 타깃으로 삼았는데,
**우리 데이터(은행·저축은행 예적금)에는 사실상 없다.** 두 가지 가능성이 있다.

1. 그 사례가 다른 상품군(카드 연계 적금 등)의 것이다
2. B가 부정 조건을 `required`로 잘못 읽고 있다

**2번을 확인해야 한다** — `기타` 40건과 함께 사람이 표본 검토할 항목이다.

## 1.6 새로 열린 결정 — 계단식 우대 (11건, 1.0%)

되물어도 판정할 수 없는 조건이 **11건** 남는다. 하나의 조건에 임계가 여러 개이고
**금리도 단계별로 다르다.**

```
"자동이체 입금횟수 우대금리 : 최고 0.5%p - 5회이상 : 0.2%p, 10회이상 : 0.3%p, 15회이상 0.5%p"
"목표달성 축하 우대이율: 최고 연 1.0%p, 50만원 이하: 연 0.5%p, 50만원 초과: 연 1.0%p"
```

**추출기가 이걸 항목 하나로 접었다** — 스키마에 단계를 담을 자리가 없어서 가장 높은
금리만 남았다. 사용자가 "10회"라고 답하면 실제로는 0.3%p인데 우리가 아는 값은 0.5%p다.
**추측하면 과대 진술이므로 판정 불가로 남긴다.**

| | 방법 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A** | 지금처럼 판정 불가 (범위) | 공짜. 과대 진술 없음 | 상품 4개가 범위에 남는다 |
| **B** | 스키마에 `tiers: [{임계, 금리}]` 를 넣고 재추출 | 정확해진다 | 재추출 $1 + 스키마 복잡도. **1.0%를 위해** |
| **C** | 계단식은 가장 낮은 단계 금리로 본다 | 공짜. 과소로 기운다 | 근거 없는 값을 확정으로 보여준다 |

**미정.** 규모가 1.0%라 B의 값어치가 의심스럽다 — `0013`(추출 개선 중단)과 같은 판단이
적용될 자리로 보인다. 다만 **이건 추출기가 정보를 버린 사례**라서 성격이 다르다.

## 1.5 층 2 유형을 어떻게 물을 것인가 (131건, 12.5%)

| 유형 | 건수 | 사용자에게 물을 수 있나 |
|---|---:|---|
| `실천_미션_인증` | 66 | **애매하다.** "대중교통 이용하겠습니까"는 물을 수 있지만 "ESG 서약"은? |
| `무조건_특판_이벤트` | 46 | 물을 필요 없다 — 모두에게 적용 |
| `쿠폰_코드_추천인` | 19 | **애매하다.** "쿠폰 있습니까"는 물을 수 있다 |

### 결정 — 유형을 가리지 않고 되묻는다 (2026-08-26 · `decisions/0016`)

**"물을 수 있나"를 따지는 것 자체를 그만뒀다.** 문구 20개를 훑어 넷으로 나눠 봤더니,
못 묻는다고 판정할 이유가 없었다.

| 군 | 성격 | 건수 | 예 |
|---|---|---:|---|
| 1 | 가입할 때 클릭 한 번 | 25 (37.9%) | `"온실가스 줄이기 실천서약서 동의"` · `"통장미발급"` |
| 2 | 가입 후 계속 해야 한다 | 19 (28.8%) | `"대중교통 미션: 1년제 연 0.4%p"` · `"계약기간의 1/2이상 매월 로그인"` |
| 3 | 이미 갖고 있는지 묻는 사실 | 11 (16.7%) | `"손하나로인증 서비스 등록"` · `"자원봉사자, 헌혈자"` |
| 4 | **공시가 무엇을 하라는지 안 말한다** | 11 (16.7%) | `"ESG 실천 우대금리 1.00%"` · `"봉사활동 또는 상품홍보"` |

4군도 **문구를 그대로 보여주고 되묻는다.** 우리가 요약하면 사용자가 판단할 근거를
빼앗는다 — 사용자는 자기가 그 은행에서 ESG 우대를 받는지 알 수도 있다.

2군은 물어서 받은 답이 **사실이 아니라 약속**이므로, 충족으로 계산하되
`이행필요` 사유를 붙여 보여준다(§1.7).

**쿠폰 19건은 문구 6개가 전부 같은 질문이다** — `"금리우대 쿠폰이나 코드가 있습니까"`
하나로 끝난다(쿠폰·코드 17건, 추천인 2건).

## 1.7 못 채웠을 때 무엇을 보여주는가 (`decisions/0016`)

**조용히 빼지 않는다.** 판정하지 못한 조건이 있으면 사유를 문장으로 보여준다.

| 사유 | 보여줄 문장 | 되물어서 없앨 수 있나 |
|---|---|---|
| `미응답` | 답하지 않은 조건이 있습니다. 답하면 금리가 확정됩니다 | 그렇다 |
| `수치필요` | 금액·횟수를 답하면 금리가 확정됩니다 | 그렇다 (§1.3) |
| `모름` | 사용자가 모른다고 답한 조건이 있어 금리를 확정할 수 없습니다 | 물었고 답이 "모름"이다 |
| `이행필요` | 가입 후 계속 실천해야 받는 우대금리가 포함돼 있습니다. 중단하면 그만큼 낮아집니다 | 아니다 — 미래의 일이다 |
| `단계불명` | 충족 정도에 따라 금리가 달라지는 조건이 있는데 공시에 단계가 다 나와 있지 않습니다 | 아니다 (§1.6) |
| `추첨` | 추첨·랜덤으로 주는 우대금리가 포함돼 있어 실제 금리는 더 낮을 수 있습니다 | 아니다 — **지금 데이터에 0건** |

### 전부 되물었을 때 — 실측

```
                 확정   범위          되물은 뒤 남는 사유
은행권 79개         64      0          이행필요 46
저축은행 297개      105      4          이행필요 15 · 단계불명 4
```

**은행권은 범위가 사라진다.** 남는 것은 "약속을 지켜야 받는다"는 주의뿐이다.

## 1.8 표본을 직접 읽고 나온 것 — 조건이 아닌 문구 (2026-08-27 · `decisions/0019`)

`기타` 40건과 부정 조건 6건을 사람이 원문과 나란히 놓고 읽었다
(`src/analysis/review_sample.py`). **둘 다 결론이 났고, 하나는 예상과 방향이 반대였다.**

### 부정 조건 6건 — 정말 없는 게 맞다. 그 6건마저 오탐이다

6건은 **상품 하나**다(KB저축은행 정기예금 × 기간 6개). 문구도 하나뿐이다.

```
인터넷뱅킹 신규가입하여 출금계좌를 등록한 후 당일 창구 신규시 우대금리 연 0.1%p적용.
단, 신규가입일 포함 14일 이내 타기관 공인인증서 미등록시 우대금리 적용해제
```

**등록해야 받는다**(`required`)인데 AI가 `must_not_have`로 읽었다. "미등록시 해제"라는
**이중 부정을 한 번만 푼 것**이다. `must_not_have`는 사용자 답을 뒤집으므로, 지금은
*"타행계좌를 등록하지 **않은** 사람이 0.1%p를 받는다"*로 계산된다.

§1.4가 세운 가설 둘 중 **2번(AI가 부정 조건을 required로 잘못 읽는다)의 정반대**다.
`required`를 `must_not_have`로 읽고 있었다. 그러므로 **1번이 맞다** — 이 유형은
우리 상품군(은행·저축은행 예적금)에 사실상 **0건**이고, 금융위 경보 사례는 다른
상품군의 것이다. 영향은 작고 방향은 안전하다(과소 진술).

### (1) 추천기판 회피 방지 제약 ★ 가장 중요

**검증기에서 배운 것**: `"UNSUPPORTED"`만 반환하는 상수 스텁이 1·2·3순위 지표를
전부 이겼다(`reference/finance-verifier-findings.md` §0.4).

**추천기에도 같은 구멍이 있다.**

```
계산 불가 상품을 많이 만들수록 "틀린 금리를 안 보여준다" 는 점에서 안전해 보인다
  → 극단으로 가면 전부 "근거 없음" 으로 표시하는 시스템이 가장 안전하다
  → 그게 스텁과 같은 모양이다
```

**제약식 후보** (등록 시점에 적었던 것)

```
후보 1   메인 층(확정+범위) 비율이 기준선 아래로 떨어지면 개선으로 인정하지 않는다
후보 2   "범위 폭"의 평균이 늘면 인정하지 않는다
후보 3   둘 다 본다
```

### 재 봤다 — 후보 1·2는 두 번째 구멍을 못 막는다 (2026-08-27)

**구멍이 둘인데 후보는 하나만 보고 있었다.**

```
구멍 A   전부 "근거 없음" 으로 표시하면 틀린 금리를 절대 안 보여준다   ← 상수 스텁과 같은 모양
구멍 B   답할 리 없는 질문을 잔뜩 만들면 "되물으면 확정된다" 로 확정률이 오른다
```

질문을 하나씩 늘려가며 층과 범위 폭을 실측했다(다 충족 페르소나, 상품 커버리지가 큰
질문부터). 재현: `python src/analysis/ask_budget.py 20260826 --group bank --tolerance`.
**두 가지가 나왔고 둘 다 후보 설계를 바꾼다.**

| 답한 질문 | 은행권 메인 | 확정 | 폭 평균 | | 저축은행 메인 | 확정 | 폭 평균 |
|---:|---:|---:|---:|---|---:|---:|---:|
| 0 | **64** | 4 | 0.696 | | **109** | 52 | 0.624 |
| 6 | **64** | 21 | 0.306 | | **109** | 75 | 0.383 |
| 12 | **64** | 47 | 0.096 | | **109** | 91 | 0.239 |
| 전부(23·26) | **64** | 64 | 0.000 | | **109** | 105 | 0.058 |

**첫째 — 메인 층 수는 되묻기와 무관하다.** 은행권 64, 저축은행 109가 질문 0개에서
전부 답할 때까지 **한 번도 안 변한다.** 되묻기는 `범위`를 `확정`으로 옮길 뿐 메인
안팎으로 상품을 옮기지 않는다(층은 닫힘률이 정하고, 닫힘률은 추출이 정한다).

> **후보 1은 구멍 A를 막지만 구멍 B에는 완전히 무감각하다.** 질문을 25개 더 만들어도
> 이 지표는 소수점 한 자리도 안 움직인다.

**둘째 — 범위 폭 평균은 질문 수의 함수다.** 단조 감소한다. 질문을 늘리면 무조건 좋아진다.

> **후보 2는 구멍 B를 막기는커녕 정확히 보상한다.** 단독으로 쓰면 안 된다.
> 후보 3(둘 다)도 마찬가지다 — 둘을 더해도 구멍 B는 여전히 열려 있다.

### 그래서 후보를 하나 추가한다 — 질문 예산

**질문 개수를 사전에 못 박고, 그 예산 안에서만 지표를 잰다.** 예산을 고정하면
질문을 늘리는 것으로는 지표가 오르지 않는다.

```
후보 4   상위 K개 질문까지만 답한 상태에서 확정률과 폭 평균을 잰다
         K 를 측정 전에 커밋한다. K 를 넘는 질문은 지표에 안 들어간다
```

**K 후보 12** — 수확 체감이 거기서 꺾인다.

```
은행권      질문 12개    확정 47/64 (73.4%) · 폭 0.696 → 0.096 (-86%)
            남은 11개    확정 +17 · 폭 -0.096
저축은행    질문 12개    확정 91/109 (83.5%) · 폭 0.624 → 0.239 (-62%)
            남은 14개    확정 +14 · 폭 -0.181
```

### 부수 확인 — 허용 오차로는 메인을 부풀릴 수 없다

메인 층 판정이 `TOLERANCE`(산수 일치 허용 오차 0.06%p)에 걸려 있으므로,
**오차를 넓혀서 메인을 늘리는 우회로가 있는지** 확인했다. 없다.

```
허용 오차 %p    0.06    0.10    0.20    0.50    1.00    5.00
은행권 메인     81.0%   77.2%   68.4%   51.9%   31.6%    7.6%
저축은행 메인    36.7%   31.3%   29.3%   26.6%   24.2%   20.2%
```

넓힐수록 **줄어든다.** 오차를 넓히면 `공시 최고금리 = 기본금리`인 행이 `공시미반영`
층으로 빠지기 때문이다. 이 방향은 막을 필요가 없다.

### 결정 — 커버리지 게이트 + 질문 예산 12개 (2026-08-27 · `decisions/0018`)

사람 결정이다. **후보 1과 후보 4를 함께 쓴다.**

```
게이트   메인 층(확정+범위) 비율이 기준선 아래로 떨어지면 개선으로 인정하지 않는다
         기준선 — 은행권 12개월 81.0% (64/79) · 저축은행 12개월 36.7% (109/297)

예산     상위 12개 질문까지만 답한 상태에서 확정률과 범위 폭을 잰다
         13번째부터는 물어도 되지만 **평가 지표에 안 들어간다**
```

**커버리지는 점수에 더하지 않는다 — 게이트로만 쓴다.** 가중 합산하면 "커버리지를 조금
깎고 확정률을 크게 올리는" 거래가 가능해지고, 그게 막으려던 도피다. 게이트는 거래를
허용하지 않는다.

**질문 우선순위와 동점 처리를 지금 못 박는다.** 안 그러면 상위 12개를 **사후에 고르는
우회**가 생긴다 — 결과를 보고 유리한 질문을 상위로 올리면 예산이 무력해진다.

```
1순위   상품 커버리지 내림차순 — 그 질문 하나가 판정을 여는 상품 수
2순위   질문 키 사전순 — 내용에 무관한 기준을 일부러 골랐다
```

2순위를 금리 크기처럼 **의미 있는 값으로 두지 않았다.** 그런 값은 시스템이 만드는
값이라 추출 금리를 키우면 순위를 밀어올릴 수 있다. 사전순은 조작할 수 없다.

**동점은 실제로 예산 경계에 걸린다** — 은행권 11·12위가 둘 다 7상품(`고객군_자격`·
`기타`), 저축은행 11·12위가 둘 다 4상품이다. 누가 예산 안에 드는지를 2순위가 정한다.

질문 하나의 단위는 **조건 유형 하나**다(`0016`). 유형을 합쳐 예산을 아끼는 우회를
막는다. 수치 후속 질문(`_금액`·`_횟수`)은 별도로 센다 — 비싸게 세는 쪽이다.

**예산 시점의 값이 앞으로 비교 기준이다.**

```
은행권      확정 47/64 (73.4%) · 폭 평균 0.096%p · 커버리지 81.0%
저축은행    확정 91/109 (83.5%) · 폭 평균 0.239%p · 커버리지 36.7%

사전순 규칙을 넣기 전후로 예산 시점 값은 바뀌지 않았다.

### 기준선 재등록 예고 — 고치기 **전에** 적는다 (2026-08-27)

위 기준선(은행권 81.0% · 저축은행 36.7%)은 **버그가 있는 코드에서 나온 값**이다.
표본 검토(START-HERE 1번) 중에 셋을 찾았고, 셋 다 고치면 기준선이 움직인다.

`CLAUDE.md` 3번은 "기준을 고쳐야 하면 **측정 전에** 고치고 사유·편향 방향·완화 조치를
함께 적는다"고 정했다(`prereg-02` §2.1이 선례다). 그래서 여기 먼저 적는다.

**무엇을 고치나**

| | 무엇 | 규모 | 지금 무슨 일이 벌어지나 |
|---|---|---:|---|
| 1 | 조건이 아닌 문구를 조건으로 뽑았다 | 13건 | `"우대이율 6개월 이상 2.20%"`를 조건 항목으로 세어 합산한다 |
| 2 | 그중 일부가 `무조건_특판_이벤트`(항상 충족)로 분류됐다 | 4건 | **사용자가 아무것도 안 해도 2.20%p를 받는 것으로 보여준다** |
| 3 | 금액 임계를 띄어쓰기 없으면 못 잡는다 | 36건 | `"1천만원이상"`을 임계로 못 읽어 사용자 "예" 답을 그대로 충족으로 센다 |

**편향 방향 — 셋 다 확정률을 낮추는 쪽이다**

이게 이 재등록의 핵심 논거다. 세 수정은 **지표를 좋게 만들지 않는다.**

```
1  조건 아닌 항목을 빼거나 판정 불가로 → 확정이 줄고 범위가 는다
2  항상 충족이던 것이 판정 불가로     → 확정이 줄어든다
3  임계를 제대로 잡으면 되물어야 판정  → 안 물으면 판정 불가. 확정이 줄어든다
```

**결과를 보고 유리한 기준을 고르는 것이 아니다.** 유리한 쪽으로 고칠 셈이었다면
이 셋을 고치지 않고 두는 것이 이득이다. 지금 값이 더 높게 나오기 때문이다.

**정직하게 적어 둘 것** — 후보안을 고르는 과정에서 **C안·D안의 예산 시점 값을 이미
봤다**(D: 은행권 커버리지 81.0% · 확정 71.9% / 저축은행 38.0% · 82.3%). 임계 수정(3번)은
반영되지 않은 값이라 최종 숫자는 아니지만, "전혀 안 보고 등록했다"고 쓰지 않는다.

**완화 조치**

- 옛 기준선(81.0% · 36.7%)을 지우지 않고 **버그가 있던 값으로 기록에 남긴다**
- 새 기준선은 세 수정을 **전부 반영한 뒤 한 번 재고 그 값으로 못 박는다.**
  이후 변경은 새 기준으로 잰다
- **질문 예산 K=12와 우선순위 규칙은 건드리지 않는다.** 이번에 바뀌는 것은
  기준선 숫자 하나뿐이고, 제약식의 구조는 그대로다

셋을 고치고 한 번 쟀다. **예고대로 전부 나빠졌다.**

### 두 번째 기준선 재등록 예고 — 배타 그룹을 범위로 처리한다 (2026-08-27)

**무엇을 고치나** — 층 판정이 배타 그룹을 무시하고 다 더한다. 같은 파일의
`bonus_range()`와 공식 닫힘률(`compare_extractors.declared_llm`)은 그룹 최댓값을 쓴다.
**같은 항목이 두 값을 낸다.**

어느 쪽이 맞는지 재봤더니 **어느 쪽도 아니었다.**

```
배타 그룹이 붙은 행에서 공시 폭에 맞는 쪽
  은행권 93행    최댓값 35 · 합산 32 · 둘 다 틀림 26
  저축은행 46행   최댓값 18 · 합산 16 · 둘 다 틀림 12
```

`iM함께예금`은 `g1`에 `[0.1 × 5]`가 들어 있는데 공시 폭이 0.45라 **다섯 개가 다
더해져야** 맞는다. 중복 적용 불가가 아니라 별개 조건 다섯을 한 그룹으로 묶은 것이다.
**공식이 틀린 게 아니라 라벨을 못 믿는다.**

**그래서 어느 쪽도 고르지 않는다.** 배타 그룹이 진짜인지 모르면 **그것도 모르는 것**이고,
이 프로젝트는 모르는 것을 범위로 낸다(`0015`·`0016`·`0017`이 전부 같은 답을 했다).

```
lo = 그룹 최댓값   중복 적용 불가가 맞다면
hi = 합산         중복 적용 가능하다면 (공시 최고금리 상한에 걸린다)
층 판정 = 공시 폭이 [lo, hi] 안에 들어오면 "설명됨"
사유    = `중복우대불명` — 조건들이 중복 적용되는지 공시가 분명하지 않습니다
```

**편향 방향 — 이번에는 지표가 좋아지는 쪽이다. 그래서 더 조심해야 한다**

`0019`의 재등록은 셋 다 확정률을 낮추는 방향이라 "유리하게 고친 게 아니다"가 논거였다.
**이번은 반대다.** 밴드는 두 점보다 넓으므로 **커버리지가 오를 수밖에 없다.**
결과를 보고 유리한 쪽을 고른 것처럼 보일 수 있고, 그 의심이 정당하다.

**그래서 완화 조치를 세 개 건다.**

1. **밴드 덕분에만 메인에 들어온 행의 수를 주 지표와 함께 보고한다.**
   두 점 규칙 어느 쪽으로도 설명 안 되는데 밴드로만 들어온 행이 많으면,
   그건 판정이 느슨해진 것이지 정확해진 것이 아니다
2. **`중복우대불명` 사유를 반드시 화면에 내보낸다.** 층 라벨만 후해지고 사용자가
   모르면 그게 과대 진술이다. `조건불명`(`0019`)과 같은 취급이다
3. **새 기준선은 이 변경을 반영해 한 번 재고 못 박는다.** 옛 값(79.7% · 36.7%)은
   지우지 않고 남긴다

**예측 — 재기 전에 적는다**

```
커버리지        은행권 82.3% -> 85% 이상 · 저축은행 35.4% -> 40% 이상
밴드 전용 행     메인의 20% 미만이어야 한다. 넘으면 판정이 느슨해진 것으로 본다
폭 평균         늘어난다 (hi 가 합산으로 올라간다). 늘어나는 것 자체는 정상이다
```

> **열어 둔 것** — 은행권은 지금 84.8%로 기준선(79.7%)을 크게 넘는다. 기준선을 실측치로
> **올려 못 박을지**는 정하지 않았다. 올리면 이후 회귀를 더 촘촘히 잡고, 안 올리면
> 84.8 → 80% 하락이 게이트를 통과한다.
