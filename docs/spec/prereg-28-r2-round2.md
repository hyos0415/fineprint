# prereg-28 · R2 2차 — 개발/평가 표본을 가르고, 근거 대조 필터를 넣고, 좁힌 R2 와 조건 답을 같이 잰다

> 작성 2026-09-07 (**평가 표본을 재기 전**) · 이슈 [#73](https://github.com/hyos0415/fineprint/issues/73) · 앞선 실험 `prereg-27`(기각 · `0058`) ·
> 사람 결정 *"우선 커밋을 하고 쭉 진행"* — 1차의 관측 위에서 방법을 바꿔 다시 잰다

## §1 1차에서 배운 것 → 이번에 바꾸는 것

```
1차 관측                                        이번 대응
같은 20문장으로 프롬프트를 고칠 수밖에 없어 두 판으로 잘랐다   표본을 DEV(40 · 1차 20 포함) / TEST(30 · 새 문장) 로 가른다. 프롬프트는 DEV 로 몇 번이든
                                               고치고, TEST 는 **마지막에 한 번** 잰다. TEST 를 본 뒤 프롬프트·라벨을 고치면 무효
없는 조건을 채우는 오답(v2 · 4B 4 → 12)                모델이 답마다 낸 근거 조각이 **원문에 글자 그대로 없으면 그 답을 버린다**(근거 대조 필터 ·
                                               띄어쓰기만 무시 · 코드). 모델을 바꾸지 않고 코드로 막는다
규칙을 늘리자 작은 모델이 나빠졌다                       v3 은 규칙 대신 **예시 4개**(DEV·TEST 에 없는 문장)를 보인다
값의 대부분이 거래 은행 목록에 있었다                    지표를 둘로 가른다 — **좁힌 R2**(스코프 + 거래 은행 · 은행 enum) 와 **조건 답**. 어느 쪽이
                                               통과하는지를 따로 본다
20문장에서 1개 = 5%                              TEST 30 · 조건 답 라벨 ≈ 25개 · 은행 언급 ≈ 20개
```

## §2 관문 — 재기 전에 정한다 (TEST 기준)

```
좁힌 R2   (가) 스코프 다섯 칸 정확도 ≥ 90%   (나) 거래 은행 목록 일치 ≥ 90% (30문장 중 27)   (다) **없는 은행·틀린 은행을 목록에 넣은 것 0**
조건 답   (가) 화면 오답 0 (필터 뒤)   (나) 빠뜨림 ≤ 30%   — 1차와 같은 관문
```

좁힌 R2 가 통과하고 조건 답이 안 되면 → **좁힌 R2 만 화면으로**(스코프·거래 은행을 자연어로 채우고 조건은 질문 루프). 둘 다 통과하면 조건 답 후보도
확인 화면으로. 둘 다 안 되면 R2 는 `0058` 로 닫힌다. **TEST 는 모델·프롬프트 하나(DEV 에서 고른 것)로 한 번만 잰다.** 두 모델을 TEST 에 돌려
좋은 쪽을 고르는 것도 하지 않는다 — 그러면 TEST 가 DEV 가 된다.

## §3 예측 — DEV 를 재기 전에 적는다

```
P1  필터    DEV 에서 근거 대조 필터가 원출력 오답의 **절반 이상**을 걸러 낸다 · 억울하게 걸리는 정답은 오답보다 적다
P2  v3     예시 프롬프트(v3)가 4B 에서 v1 보다 화면 오답이 **같거나 적고** 빠뜨림은 적다 (v2 처럼 나빠지지 않는다)
P3  DEV→TEST  DEV 에서 고른 판의 TEST 화면 오답은 DEV 비율의 ±1개 안 — 크게 벌어지면 DEV 에 맞춘 것이다
P4  좁힌 R2  TEST 에서 (가)(나)(다) 통과 — 스코프 ≥ 90% · 거래 은행 ≥ 27/30 · 틀린 은행 0. **이건 통과한다고 본다**(1차 93% · 18/20 · enum)
P5  조건 답  TEST 화면 오답 **0~1** · 빠뜨림 ≤ 30%. 0 이면 통과인데 **반반**보다 조금 못하다고 본다 — 1차 최고 판이 1 이었고 필터가 그 1(보수적
            "모름")은 못 거른다(근거가 원문에 있다)
P6  지연    4B 문장 하나 < 8초 (v3 은 프롬프트가 길어 1차보다 늦다)
```

### §2 관문 판정 — 예측과 반대로 갈렸다

- **조건 답**: (가)(나) 통과. 단, 안전은 모델이 아니라 **후보 집합 필터**가 만들었다(원출력 6 → 화면 0). 그리고 TEST 30문장은 0 과 1 을
  가를 크기가 아니다(§4 P3)
- **좁힌 R2**: (다) 불통과 2건. 두 건 다 **거래 은행 목록**에서 났고, 거래 은행 목록은 F6 이 그것으로 첫거래·주거래를 **유도**하기 때문에
  틀리면 조건 답 하나보다 파급이 크다(우리은행을 거래로 넣으면 우리은행 첫거래가 아니오로 유도된다)

**§4 는 이 조합(좁힌 R2 ✗ · 조건 답 ✓)을 예상하지 않았다.** P4 조항은 "R2 전체를 닫는다", P5 조항은 "확인 화면으로" 라서 서로 부딪힌다.
정하지 않고 사람에게 넘긴다 — 결정 [`0059`](../decisions/0059-r2-round2-result.md).

## §7 덧붙임 — 거래 은행 오답을 구조로 막을 수 있나 (2026-09-07 · 같은 날 · 사람 요청 *"부정문 잘 거를 방안이 없음?"*)

TEST 의 (다) 오답 2건은 은행을 **두 목록**(보고 싶은 · 거래하는)에 나눠 담는 스키마에서 섞인 것이다. 두 방안을 DEV 에서 재 봤다.

```
① 은행 역할 스키마 (v5)    문장에 나온 은행 **전부**를 나열하고 각각 거래함·거래없음·보고싶음 중 하나를 붙이게 한다. 두 목록이 없다
② 재확인 호출             뽑힌 거래 은행마다 "이 은행과 거래한다고 말했나? 예/아니오" 를 따로 묻고 아니오면 뺀다
```

DEV 결과 (Qwen3.5-4B · 40문장)

```
                     화면 오답  원출력  빠뜨림(26)  스코프  스코프-은행  거래 일치  틀린 은행  지연
v3 (기준)                2        5      8%       94%     35/40     37/40       3        4.3s
v5 (역할 스키마)          4        6     27%       94%     28/40     40/40       0        4.2s
v5 + 재확인 호출          4        6     27%       93%     28/40     35/40       0        4.9s   재확인이 뺀 것: 오답 0 · 정답 6
hybrid (답은 v3 · 은행은 v5 · 호출 2회)   2   5     8%       90%     27/40     40/40       0       10.5s
```

- **①은 거래 은행 문제를 풀었다** — 틀린 은행 3 → 0, 일치 40/40. 그러나 프롬프트가 길어지자 4B 의 **조건 답이 나빠졌다**(2 → 4 · 빠뜨림 8 → 27%).
  1차 v2 때와 같은 모양이다 — 작은 모델에 일이 늘면 다른 칸이 흐려진다
- **②는 해롭다** — 오답은 0개 빼고 정답 6개를 뺐다. 짧은 문장에 은행 하나를 대조하는 두 번째 물음에 모델이 "아니오" 로 기운다. 버린다
- **hybrid** — 조건 답·스코프는 v3 로, 은행은 v5 로 두 번 부른다. 조건 답 2/8% 와 거래 은행 40/40·틀린 은행 0 이 **같이** 나온다.
  값은 지연이다 — 문장 하나 10.5초. 그리고 **스코프 은행(좁히기) 칸이 27/40 으로 약해졌다** — v5 가 "보고싶음" 을 덜 붙인다. 좁히기를 놓치는
  것은 질문이 줄지 않는 쪽의 오답이라 위험하지는 않다

**TEST(30)의 0 은 표본이 쉬웠던 것이다.** TEST2 는 부정문·"보고 싶은 은행 ≠ 거래 은행"·여러 은행을 일부러 섞었고, 거기서 4B 는 30문장 중
8문장에서 화면까지 갈 오답을 냈다. 오답의 모양은 셋으로 모인다.

```
뒤집힘     "국민은행 거래는 없어" → 첫거래_신규고객@국민은행 **아니오** (#201) · "부산은행 거래 없고 경남만 써" → 주거래@경남 **아니오** (#217)
지어낸 추론  "적금은 국민은행 걸로 보고 싶어" → 첫거래@국민 **예** (#211 · 보고 싶다는 말에서 첫거래를 만들었다) · "농협 조합원" → 고객군_자격 예 (#209)
권역 혼동   "하나은행은 처음이고 신한은 주거래" → 하나**저축**은행 · 신한**저축**은행 (#214 · 은행권 문장인데 저축은행 이름을 골랐다)
```

셋 다 1차·2차에서 이미 본 모양이고, **후보 집합 필터가 막아 주던 것이 이번엔 그 키가 후보 집합 안에 있어서 화면까지 갔다.** 즉 지금까지의
"화면 0" 은 모델이 맞아서가 아니라 오답 키가 우연히 후보 밖이었던 덕이 컸다.

### 이 실험이 말하는 것

1. **조건 답 제안은 4B 로컬 모델로는 안 된다** — 부정과 추론이 섞인 문장에서 30% 오답. 확인 화면을 붙여도 셋 중 하나가 틀린 제안을
   들고 오는 셈이라 확인이 형식이 되기 쉽다(`0057` 반증 조건 2). 1차 `0058` 의 기각을 **더 강한 근거로 재확인**한다
2. **은행 역할 스키마는 방향이 맞다** — 두 목록(v3)의 틀린 은행 3 → 역할(v5) 0(DEV) · 1(TEST2 · 부정문 많음). 구조로 막는 것이 프롬프트로 막는
   것보다 낫다는 것이 이번에도 확인됐다. 다만 0 은 아니다
3. **거의 틀리지 않는 칸이 있다** — 권역 97% · 상품군 100% · 기간 100% · 금액 80~100%. 이것은 `0042` 원안의 화이트리스트 넷이다
4. 재확인 호출(②)은 해롭고, 근거 대조 필터는 무력하다 — 둘 다 "작은 모델에 한 번 더 묻기 · 베낀 조각 검사" 로는 뜻 오류를 못 잡는다
5. 하이브리드는 12초 — 화면에 붙이기엔 길다
