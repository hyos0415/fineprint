# 사전 등록 13 — "상품 하나" 의 신원을 고친다

2026-08-31 작성 · **재기 전에 커밋한다** · 이슈 [#25](https://github.com/hyos0415/fineprint/issues/25)

앞선 기록: `decisions/0018`(질문 우선순위·예산 12개를 못 박았다) · `0019`(기준선 재등록의
선례) · `prereg-06` §2.3(1)(재등록 사유·편향 방향을 **고치기 전에** 적은 예) ·
`0028`(스코프 축은 기관) · `0030`(선호 가중치) · `prereg-12` §9(이 문제를 발견한 자리)

## 0. 무엇이 틀렸나

**화면이 상품 수를 틀리게 센다.** 질문 루프가 *"이 답 하나가 상품 N개의 판정을 엽니다"*
라고 쓰는데, 그 N 이 `fin_prdt_cd`(상품코드) 만으로 세어진다. 상품코드는 **기관을 넘어
유일하지 않다.**

```
저축은행 12개월   기관명 30종  ·  **기관코드(fin_co_no) 58개**
                하나저축은행 = 0010378 · 0010528 · 0010572  (세 법인)
                셋 다 상품코드 240001 "정기예금" 을 쓴다 -> 지금은 하나로 합쳐 센다

상품 수         상품코드만  92        (지금 화면이 말하는 값)
               기관코드+상품코드  **183**   (참값)
```

**행의 정체는 조사로 확정됐다** (이슈 #25 코멘트).

```
행 = (기관코드, 상품코드, 단리/복리, 적립방식)
     은행권 79 = 79 · 저축은행 297 = 297 — 원천 필드로 **남김없이** 설명된다
     원천 optionList 에 완전 중복 레코드 0건. 수집 페이징 문제도 아니다
```

그런데 `rows` 에 **세 필드가 안 담겨 있다** — `fin_co_no` · `intr_rate_type_nm`(단리/복리) ·
`rsrv_type_nm`(정액/자유적립식). `kor_co_nm`(#15) · `join_way`(#22) 때와 **같은 자리
세 번째**다.

## 1. 무엇을 고치고 무엇을 안 고치나

```
고친다    rows 에 세 필드를 담는다                        순수 추가. 소비자 없음
         상품 신원 = (기관코드, 상품코드)                  헬퍼 하나로 통일한다
         rank_questions() 의 "상품 몇 개" 를 그 신원으로   -> **질문 우선순위가 바뀐다**
         product_line() 의 이동 화살표도 같은 신원으로     지금 같은 코드끼리 섞인다

안 고친다  지표의 분모는 **행 그대로**다 (은행권 79 · 저축은행 297)
         커버리지 게이트 분모도 그대로다 (`0018` · 이슈 #10 을 안 건드린다)
```

**분모를 안 고치는 것이 이 사전등록의 경계다.** 두 단위는 서로 **다른 것을 잰다.**

```
행    같은 상품의 단리 행은 닫히고 복리 행은 안 닫힐 수 있다
      -> **추출 품질**을 재는 단위다. 지표 분모로 맞다
상품  사용자에게 "정기예금" 은 하나다. 8번 세면 화면이 이상해진다
      -> **화면**의 단위로 맞다
```

지금 코드는 **우연히** 그렇게 돼 있고 **아무 데도 안 적혀 있다.** 이 사전등록이 그것을
명시하고, 화면 쪽 신원만 참값으로 고친다. 분모를 상품으로 바꾸는 것은 `0018` 기준선과
이슈 #10 게이트를 통째로 재등록하는 일이라 **여기서 하지 않는다.**

## 2. 기준선이 움직인다 — 고치기 **전에** 사유·편향 방향을 적는다

`rank_questions()` 는 두 곳에 쓰인다.

```
화면    "이 답 하나가 상품 N개를 엽니다" — 지금 거짓이다
순서    질문 우선순위 (`0018` 1순위 = 상품 커버리지 내림차순)
```

**둘이 같은 함수라, 화면을 고치면 순서도 바뀐다.** 순서가 바뀌면 예산 12개 안에 드는
질문이 달라지고, 예산 12개 시점의 **확정률·폭 평균이 움직인다.**

**그래서 `0019` 와 같은 절차를 밟는다** — 재등록 사유·편향 방향·완화 조치를 측정 전에
적는다(`prereg-06` §2.3(1) 이 그 선례다).

| | |
|---|---|
| **사유** | 우선순위 1순위가 "상품 커버리지" 라고 적혀 있는데 **상품을 틀리게 세고 있었다.** 규칙을 바꾸는 것이 아니라 규칙이 말하는 대로 계산되게 고치는 것이다 |
| **편향 방향** | **모른다.** 저축은행에서 기관코드를 보면 상품 수가 92 → 183 으로 **늘어나므로** 질문마다 커버리지가 커지는데, 어느 질문이 더 커지는지는 안 재 봤다. 확정률이 오를 수도 내릴 수도 있다 |
| **완화 조치** | 방향을 모르므로 **유리한 방향을 고를 수가 없다.** 예측을 §4 에 먼저 적고, 새 기준선은 실측값을 그대로 등록한다. `0021` 때처럼 게이트가 걸리면 넘기지 않고 신호로 남긴다 |
| **안 건드리는 것** | 커버리지 게이트 분모·기준선(79.7% · 36.7%)·예산 크기 12·2순위(사전순) |

**유리한 기준을 고른 재등록이 아니라는 근거가 "방향을 모른다" 는 것이다.** 방향을 알고
고쳤다면 그 사실을 여기 적어야 했다.

## 3. 무엇을 주장하지 않는가

1. **"추천이 좋아졌다"** — 이 변경은 질문 순서와 화면 문구를 고칠 뿐이다. 정렬 품질에
   정답이 없는 것은 `prereg-12` §1 그대로다
2. **새 확정률이 옛 확정률보다 낫다** — 분자·분모의 정의가 아니라 **질문 순서**가 바뀌는
   것이다. 두 숫자는 같은 것을 재지만 **다른 12개 질문**을 답한 상태에서 잰 값이다.
   높아져도 개선이 아니고 낮아져도 후퇴가 아니다
3. **상품 183 이 "옳은 단위" 라는 것** — 화면에는 맞고 지표에는 안 맞다(§1). 어느 하나가
   보편적으로 옳다고 주장하지 않는다

## 4. 예측 — 재기 전에 적는다

**상품 기준 우선순위를 아직 한 번도 계산하지 않았다.** 아래는 전부 사전 예측이다.

| | 예측 | 근거 |
|---|---|---|
| 1 | **은행권 질문 순서는 안 바뀐다** | 기관명 17 = 기관코드 17 이고 상품코드 73 vs 행 79 다. 합쳐지는 상품이 거의 없다 |
| 2 | **저축은행 질문 순서는 바뀐다** | 상품 92 → 183 이다. 두 배다 |
| 3 | 은행권 확정률·폭 평균 **안 변한다** (37/67 · 0.185%p) | 1번의 따름 결과. 순서가 같으면 예산 12개 집합도 같다 |
| 4 | 저축은행 확정률·폭 평균 **변한다**. **방향은 예측하지 않는다** | §2 대로 방향을 모른다. 방향을 적으면 그건 사후 합리화가 된다 |
| 5 | **커버리지는 두 권역 다 안 변한다** (84.8% · 35.7%) | 분모를 안 건드린다. 움직이면 §1 의 경계가 새어 나간 것이다 |
| 6 | 화면 계약 **A1~A11 전부 통과** | 화면 신원이 바뀌지만 계약은 그대로다 |
| 7 | `--prefs` 정렬 결과 **안 변한다** | 선호 조정은 상품 신원을 안 쓴다(`0030`). 움직이면 결합이 샌 것이다 |

**예측 5 가 주 판정이다.** 화면 쪽 신원만 고치기로 한 §1 의 경계가 지켜졌는지를 본다.

**예측 1·2 는 방향이 반대인 쌍이라 둘 다 맞기 어렵다** — 하나만 맞으면 신원 변경의
효과를 내가 잘못 짚은 것이다.

## 5. 회피 방지

| 가드 | 기준 |
|---|---|
| 분모를 안 바꾼다 | `ask_budget.stats()` 의 `len(main)`·`len(scored)` 는 행 그대로 |
| 새 기준선을 유리하게 고르지 않는다 | 방향을 모르는 상태에서 예측을 커밋했다(§2·§4-4) |
| 게이트를 안 만진다 | `COVERAGE_FLOOR` 는 79.7 · 36.7 그대로. 걸리면 신호로 남긴다 |
| 2순위를 안 만진다 | 사전순 그대로. `0018` 이 "내용 무관" 을 일부러 골랐다 |
| 예산 크기를 안 만진다 | `ASK_BUDGET = 12` 그대로 (`0026`) |
| 신원 계산을 한 곳에만 둔다 | `calculate.product_key()` 하나. 두 곳에서 다르게 세면 이 버그가 재발한다 |

```
M12  지표 — 확정률·폭 평균·커버리지를 두 권역에서. 옛 값과 나란히 적는다
M13  질문 순서 — 옛 순서 vs 새 순서. 예산 12개 안에 들고 난 질문을 이름으로 적는다

     독립으로 세어 대조한다. **이게 이 작업의 목적이다**
```

전부 코드가 한다. 돈은 안 든다.

## 7. 이 사전등록이 정하지 않는 것

1. **지표 분모를 상품으로 바꿀 것인가** — `0018` 기준선과 이슈 #10 게이트를 통째로
   재등록하는 일이다. §1 이 "행은 추출 품질, 상품은 화면" 이라고 명시하는 것으로
   이번 회차를 닫고, 바꾸려면 별도 사전등록을 쓴다
2. **단리/복리·적립방식을 화면에 보여줄 것인가** — `rows` 에 담기는 하지만 화면에는
   안 올린다. 올리면 화면 계약이 하나 더 필요하고(A9 가 `join_way` 에 대해 한 것),
   같은 상품이 8줄로 보이는 문제를 먼저 풀어야 한다. **별도 이슈다**
3. **같은 상품의 행을 화면에서 묶을 것인가** — 위와 같은 문제다. 지금은 안 묶는다
