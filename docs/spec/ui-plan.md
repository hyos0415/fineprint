# F4 · UI 계획 — 웹으로 옮길 때 무엇이 깨질 수 있나

> 작성 2026-08-31 (착수 전 계획) · 상태는 [`roadmap.md`](./roadmap.md) F 절 ·
> 결정 [`0038`](../decisions/0038-fastapi-for-the-ui-server.md)(서버·의존성)

**이 문서는 착수 전에 쓴 계획이다.** 크리티컬 패스에 F4(UI)만 남은 상태에서, 다음
세션이 무엇부터 보고 무엇을 정해야 하는지를 적는다.

## 끝의 정의

```
지금 동작하는 것   수집 · 추출 · 계산 · 되묻기 · 후보 집합 · 선호 정렬 · 비교 리포트
                 화면 계약 A1~A13 · 세율/광고 조문 감시
없는 것           화면 — 저장소에 .html · .js · .css · .ts 가 0개다
```

**끝 = 사람이 브라우저에서 처음부터 끝까지 한 번 완주할 수 있고, 그 화면이 계약을
지키는 것.** 나머지는 "안 하기로 적어 둔 것" 으로 닫는다(아래 §안 하는 것).

## 왜 이 순서인가 — 화면이 이 저장소의 상습 실패 자리다

지금까지 찾은 실패가 거의 다 화면에서 나왔다.

```
0019   조건이 한 글자도 없는데 4.80% 가 확정처럼 보였다
0026   중단 지점의 화면이 범위를 단일 숫자로 줄이거나 `확정` 라벨을 붙이는 것
0029   후보 4개짜리 스코프에서 확정 카운터가 6개 질문 동안 0으로 고정돼 있었다
0035   `세후` 라벨이 calculate.py 목록에는 있고 질문 루프 화면에는 없었다
```

**화면을 새로 만드는 것은 이 실패들이 한 번에 되살아날 수 있는 자리다.** 그래서
UI 를 쓰기 전에 계약을 옮긴다(F4-0).

## 단계

### F4-0 · 뷰 모델 — UI 없이 하는 일 (중간)

지금 화면 계약 검사는 **렌더된 CLI 문자열을 grep** 한다 — `"세후" in screen` ·
`C.CAVEAT[code] in screen`. HTML 로 옮기면 그 검사가 전부 무의미해진다.

```
할 일   화면이 내놓을 것을 뷰 모델 하나로 정의한다
          products[] · status · questions · notices · report
        CLI 렌더러와 웹 렌더러가 **같은 뷰 모델**을 소비한다
        계약은 뷰 모델에서 검사하고, 렌더러별로는 "필수 칸을 실제로 출력했나"
        한 겹만 문자열로 본다
산출    src/analysis/view.py + check_screen_contract.py 개편
회귀    **CLI 출력이 안 바뀌고 A1~A13 이 그대로 통과** — 이것이 완료 조건이다
위험    ask_loop · report 를 건드린다. 방어선은 이미 있는 계약 검사다
```

`report.build()`(F1 · `0036`)가 이미 렌더와 분리된 객체를 내므로 발판은 있다.

### F4-1 · 서버 — 얇게 (작다)

```
엔드포인트 둘
  POST /api/session   스코프 · 기간 · 금액 · 선호        → 뷰 모델
  POST /api/answer    질문 하나에 대한 답(예/아니오/모름) → 갱신된 뷰 모델
```

**계산은 파이썬 그대로 재사용하고 JS 로 다시 쓰지 않는다** — 계산이 두 군데 있으면
두 답이 나온다(`problem.md` §7). 서버는 `evaluate()`·`report.build()` 를 부르는
얇은 껍데기다.

**여기서 D9(이어하기)가 거의 무료로 풀린다** — `ask_session_*.json` 에 질문마다
답·경과시간·남은 수·확정 수가 이미 남는다. `0026` D3 가 *"피로는 이어하기·질문 순서·
문구로만 다룬다"* 고 지목한 자리다.

### F4-2 · 화면 셋 (크다 — 작업의 절반)

```
0단계 폼     기관 · 상품군 · 기간 · 월 납입액 · 선호(5문항)     `0028` · `0030`
질문 루프    질문 하나씩 · [예][아니오][모름] · 답할 때마다 목록·범위·순위 갱신
결과        목록 + 비교 리포트(F1)
```

렌더에 박아야 하는 것 — 범위 표기 · 세후 라벨 · 성격 고지 · 사유 문장 · 남은 조건 수 ·
스코프 밖 최고 금리 · 진행 카운터 · 성과 줄 · 선호 조정(정렬만).

### F4-3 · 검증 (작다. 다만 사람이 필요하다)

```
1. 웹 렌더러에 계약 검사를 건다 (뷰 모델 → HTML 한 겹 확인)
2. **사람이 웹에서 한 번 완주한다** (M3 방식 · 자기보고)
```

**발견이 나올 것을 예상하고 들어간다** — `0026` D3 가 지목한 피로·문구·순서다.
그때 답은 **질문 축소가 아니다**(`0026` D1·D4).

## 정한 것 · 정할 것

| | 상태 |
|---|---|
| 질문 루프까지 웹으로 (결과 화면만이 아니라) | ✅ 정했다 — 되묻기가 이 시스템의 존재 이유다(`0026`) |
| 서버 = **FastAPI + Uvicorn** | ✅ 정했다 — `0038` |
| `requirements.txt` 에 예외를 사유와 함께 적는다 | ⏳ F4-1 에서 |
| **답을 서버에 저장하나** | 🙋 **정할 것.** 저장하면 `0026` 의 반증 조건이 발동한다 — *"저장·계정 기능을 만드는 순간 이 결정을 다시 본다"*. **로컬 전용 · 세션 메모리 · 로그는 지금처럼 `data/`(gitignore)** 로 두면 발동하지 않고 이어하기도 그 안에서 된다 |
| 배포 | 🙋 **정할 것.** `0037` 이 *"공개는 깃 단위에서 끝날 가능성이 높다"* 를 전제로 서 있다. 공개 형태가 바뀌면 `0037` 을 다시 읽는다 |
