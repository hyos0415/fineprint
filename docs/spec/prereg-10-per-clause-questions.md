# 사전 등록 10 — 임계는 숫자로 받지 않고 문구로 묻는다

2026-08-28 작성 · **재기 전에 커밋한다** · 이슈 [#13](https://github.com/hyos0415/fineprint/issues/13)

앞선 기록: `decisions/0015`(임계는 되묻는다) · `0016`(유형 하나에 질문 하나) ·
`0018`(질문 예산·우선순위) · `0023`(계단식) · `0024`(되묻기 흐름 P1) · `0026`(질문 수
불가침) · `prereg-09` §8(사람 세션 실측)

## 0. 사람이 정한 방향 — 문구별 예/아니오

**사람이 실제로 22개를 답해 보고 나온 결정이다.** 수치 질문 두 개에서 답이 왜곡됐다.

```
[15] 타상품_보유동시가입 — 금액이 얼마입니까? (상품별 기준 10만원 · 500만원 · 3,000만원)
       공시 문구  "②적립식예금 잔액 10만원 이상 보유"
       공시 문구  "수익증권(펀드)을 3천만원 이상 보유 시"
       공시 문구  "정기예금 500만원이상(만기 1년이상) 가입하고 만기일 전일까지 유지"
       → "예" 3번 거절 → 사실이 아닌 "아니오" 로 답했다

[17] 자동이체 — 몇 번 하십니까?
       → 4번 거절 → "모름" 으로 답했다. 모르는 게 아니었다
```

거절 자체는 입력 처리 버그였고 고쳤다. **그런데 고쳐도 남는 문제가 있다.**

> 입력 폼으로 받던가 해야할 거 같고 프로토 타입도 아닌 poc라서 그런 거 괜찮긴 한데
> 공시 문구 원문을 보여주는 게 약간 이해가 안 갈 거 같다고 느껴지는데?

**적립식예금 잔액 · 펀드 보유액 · 정기예금 가입액은 같은 축이 아니다.** "금액이
얼마입니까?" 에는 답이 존재하지 않는다 — 입력 폼으로 바꿔도 필드 하나로는 못 받는다.
`0016` 의 "유형 하나에 질문 하나" 가 임계 질문에서 깨지는 자리다.

## 1. 무엇을 바꾸나

**임계가 붙은 조건은 숫자를 받지 않고, 공시 문구를 그대로 질문 문장으로 쓴다.**

```
전   타상품_보유동시가입 — 금액이 얼마입니까? (상품별 기준 10만원 · 500만원 · 3,000만원)
     금액을 숫자로 — 500만원 · 5000000 · [모름] · [아니오]

후   "②적립식예금 잔액 10만원 이상 보유" — 이 조건을 충족하십니까?   [예][아니오][모름]
     "수익증권(펀드)을 3천만원 이상 보유 시" — 이 조건을 충족하십니까?  [예][아니오][모름]
```

**판정 단위가 유형에서 (유형 + 문구)로 내려간다.** `condition_met()` 은 임계 비교를
하지 않고 그 문구에 대한 답을 그대로 쓴다.

**`0024` P1이 강해진다** — 공시 문구가 질문 옆의 참고 자료가 아니라 **질문 문장 자체**가
된다. 사용자는 자기 상황을 그 문구에 바로 대조하고, 숫자 계산이 사라진다.

## 2. 질문 키 — 문구 해시로 만든다

```
key = f"{조건유형}#{blake2s(문구, 4바이트)}"      예) 카드실적#a3f1c2d9
```

**왜 해시인가** — `0018` 이 정렬 2순위를 *"질문 키 사전순 — 내용에 무관한 기준을 일부러
골랐다"* 로 못 박았다. 문구 텍스트를 그대로 키로 쓰면 정렬이 문구 내용을 따르게 된다.
해시는 결정론적이고 내용과 무관하며, 같은 문구는 항상 같은 키가 된다(`0020` 의 자기
일관성과 같은 성질).

**1순위는 그대로 상품 커버리지 내림차순이다.** 우선순위 규칙을 건드리지 않는다.

## 3. 무엇이 안 바뀌나 — 셋을 못 박는다

| | 유지 | 근거 |
|---|---|---|
| 유형 게이트 | 유형 질문을 먼저 묻고, "아니오"·"모름" 이면 그 유형의 문구 질문을 **전부 지운다** | `0024` P4 (남은 수는 줄어들기만 한다) |
| 계단식 | 문구에 단계가 둘 이상이면 여전히 `단계불명` 이다. 예/아니오로도 못 판정한다 | `0023` (진짜 계단 3문구) |
| 질문 예산 | **12개 그대로.** 질문이 늘었으니 예산도 늘리는 것은 회피다 | `0018` |

## 4. 예측 — 재기 전에 적는다

**질문 수가 늘고 예산 12개 안의 확정률은 내려간다.** 유리한 방향이 아니다.

| | 지금 | 예측 |
|---|---|---|
| 은행권 질문 수 (전부 답) | 22 | **늘어난다 · 30~50** |
| 저축은행 질문 수 (전부 답) | 27 | **늘어난다 · 35~60** |
| 은행권 확정 (예산 12) | 37/67 (55.2%) | **내려간다 · 40~56%** |
| 저축은행 확정 (예산 12) | 85/106 (80.2%) | **내려가거나 같다 · 70~80%** |
| 폭 평균 (예산 12) | 0.176 · 0.277%p | **올라간다** (덜 좁혀진다) |
| 전부 답했을 때 확정 (은행권) | 50/67 | **같다 · 50/67** ← 같은 항목을 전부 판정하므로 |
| 커버리지 | 84.8% · 35.7% | **안 변한다** (층 판정은 사용자 상태와 무관) |
| 화면 계약 A1~A5 | 통과 | **통과해야 한다** (`prereg-09` 재실행) |
| 계단식 `단계불명` 문구 | 은행권 3 · 저축은행 3종 | **그대로 3 · 3** |

**"전부 답했을 때 확정" 이 50/67 에서 움직이면 예상 밖이다** — 임계를 숫자로 비교하던
것을 문구 답으로 바꿨을 뿐이므로, 다 답하면 같은 결론이 나와야 한다. 움직이면 판정
경로에 다른 변화가 섞인 것이고 그 사실을 먼저 적는다.

**커버리지가 움직이면 이 사전등록의 전제가 틀린 것이다.**

## 5. 회피 방지

| 가드 | 기준 |
|---|---|
| 예산을 늘리지 않는다 | 12개 고정. 질문이 늘었다고 예산을 늘리면 확정률 하락을 지표에서 지우는 것이다 |
| 우선순위 규칙을 안 건드린다 | 커버리지 내림차순 → 키 사전순. 키만 해시로 바뀐다(§2) |
| 커버리지 게이트 그대로 | 은행권 79.7% · 저축은행 36.7%. 이 변경으로 게이트를 넘으려 하지 않는다 |
| 화면 계약을 다시 돌린다 | `check_screen_contract.py` A1~A5. 질문 단위가 바뀌면 A4(단조 비증가)가 가장 위험하다 |
| 계단식을 예/아니오로 밀어넣지 않는다 | 단계가 둘 이상인 문구는 `단계불명` 이다. 3 · 3 이 유지되는지 센다 |
| 문구를 우리가 다시 쓰지 않는다 | 공시 문구 원문 그대로 질문에 쓴다. 요약·의역 금지(`0016` · `CLAUDE.md` 5번) |

## 6. 이 사전등록이 정하지 않는 것

1. **긴 문구를 화면에서 어떻게 자를 것인가.** 지금은 74자에서 자른다. 질문 문장이 되면
   자르는 것이 위험할 수 있다 — 결과를 보고 사람에게 묻는다
2. **`--state` 인터페이스.** 해시 키를 사람이 손으로 적기는 어렵다. 루프가 키를 찍어
   주므로 복사해 쓸 수 있지만, 편의 문법이 필요한지는 미정
3. **M3 재측정.** 입력 버그와 이 변경 뒤에 사람 세션을 한 번 더 돌릴지는 `prereg-09` §6
   ("첫 세션이 기록") 과 맞물린다. 돌리면 **두 세션을 다 남기고 사유를 적는다**
