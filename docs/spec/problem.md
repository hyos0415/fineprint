# 이 프로젝트가 푸는 문제

> 작성 2026-08-26 · 이 문서가 **현재 유효한 정의**다
> 옛 정의(검증기 시절)는 [`problem-v1-verifier.md`](./problem-v1-verifier.md)에 보존했다.
> 왜 바꿨는지는 [`../decisions/0009-pivot-to-recommender.md`](../decisions/0009-pivot-to-recommender.md).

## 1. 한 문장

**내 상황과 내가 중요하게 여기는 것에 맞는 예금·적금을 골라주는 시스템을 만든다.**

여기서 "내 상황"은 급여이체를 하는지, 카드를 쓰는지 같은 **사실**이고,
"중요하게 여기는 것"은 금리가 우선인지 비대면 가입이 우선인지 같은 **선호**다.

**시스템은 선호를 추측하지 않는다.** 사용자가 알려주고, 시스템은 계산만 책임진다.

## 2. 왜 필요한가 — 실제로 겪는 일

### (가) 광고 금리와 내가 받을 금리가 다르다

은행이 "최고 연 3.85%"라고 붙여놓은 상품이 있다. 그런데 그 3.85%를 받으려면
조건 여러 개를 다 채워야 한다. 내가 못 채우는 조건이 있으면 실제로는 2.35%다.

지금은 이걸 알려면 상품마다 우대조건을 읽고 직접 계산해야 한다.
상품이 765개다.

### (나) 같은 상품인데 은행마다 다르다

청년 대상 저축 상품처럼 **금리와 혜택이 은행마다 똑같은** 상품이 있다.
그러면 무엇으로 고르나? 은행이 다르다.

```
A은행    앱이 편하고 비대면으로 개설된다. 은행에 갈 일이 없다
B은행    비대면이 안 되지만, 직장 근처에 지점이 있다
```

**집이 은행과 먼 사람에게는 A가 맞고, 직장 근처에 B 지점이 있는 사람에게는 B가 맞다.**
누가 맞다고 정해줄 수 없다. 사람마다 다르다.

지금은 이 비교를 하려고 은행에 전화하거나 방문한다. 그 시간을 없애는 게 목표다.

### (다) 광고 금리에 도달하는 방법이 공시에 없는 상품이 있다

실제 사례다.

```
제주은행 J정기예금 · 36개월
  기본금리 1.85%    광고 최고금리 3.85%    차이 2.0%p

  그런데 공시된 우대조건을 다 더해도 0.5%p 밖에 안 된다.
  나머지 1.5%p 는 어디서 오는지 공시에 적혀 있지 않다.

  조건문에 이렇게 적혀 있다:
  "(단, 이벤트시 디지털 채널에 고시한 우대금리를 추가 적용할 수 있음)"
```

**최고금리만 보고 줄을 세우면 이런 상품이 1등으로 올라온다.**
그런데 그 금리를 어떻게 받는지는 아무도 모른다.

## 3. 무엇을 받고 무엇을 내놓나

### 기준 시나리오 — 이 한 줄이 무엇을 요구하는지 (2026-08-28 추가)

**시나리오가 모호했던 것이 실제로 설계 결함을 만들었다.** 0단계 축에 기관이 없어서
질문이 카탈로그 17개 기관 전체에서 생성됐고, 우리·농협을 보려는 사용자가 제주·광주
상품 때문에 답하다가 중단했다(`decisions/0028`). 그래서 기준 시나리오를 여기 박아둔다.

```
"우리은행을 주거래 은행으로 쓰고 있는데, 목돈을 모으고 싶어. 적절한 상품 추천해줘"
```

이 한 줄에서 나오는 것과 **나오지 않는 것**을 가른다.

| 말 | 무엇이 되나 | 무엇이 안 되나 |
|---|---|---|
| "우리은행을 주거래로" | **스코프 = 기관 우리은행** | 급여이체·자동이체를 한다는 답은 **아니다** — 그 4개 상품에 `주거래` 조건은 아예 없고, 있는 것은 급여이체·자동이체·카드실적이다. 추측하면 `0024` P2 위반 |
| "목돈을 모으고 싶어" | **스코프 = 적금** | 금액·기간은 아니다. 폼으로 받는다 |
| (안 말한 것) | — | 기간·납입액은 물어야 한다 |

**결과**: 카탈로그 79개 · 질문 39개 → **상품 4개 · 질문 7개**, 그리고 그 7개가 전부
우리은행 고객이 답할 수 있는 문구다. 동시에 **좁힌 대가**를 같이 보여준다 —
"스코프 밖에 5.92%가 있습니다 (+2.67%p)". 기관별 격차 중앙값이 2.41%p라
안 보여주면 그게 곧 정보 은폐다.


### 받는 것 두 가지

**첫째, 내 상황 (사실)**

```
급여이체를 하는가 · 자동이체가 있는가 · 카드를 쓰는가 · 청약이 있는가
나이 · 넣을 금액 · 넣을 기간 · 집과 직장 위치 · 주로 쓰는 은행
```

이 항목들은 우리가 만든 **조건 유형 17종**과 짝이 맞는다
([`../decisions/0005-condition-type-enum-and-analysis-unit.md`](../decisions/0005-condition-type-enum-and-analysis-unit.md)).
공시가 요구하는 조건이 그 17종이니, 사용자에게 물을 것도 그 17종이다.

**둘째, 내 선호 (가중치)**

설문으로 받는다. 답을 **고정된 표**로 가중치에 옮긴다.

```
"금리가 얼마나 중요한가?"     매우 그렇다 → 금리 가중치 0.8
"비대면 가입이 필요한가?"     필수다      → 영업점 필수 상품 제외
```

**그리고 옮긴 결과를 사용자에게 보여주고 고칠 수 있게 한다.**
이게 있어야 "시스템이 마음대로 정했다"가 안 된다.

### 내놓는 것

```
1위  A은행 청년적금      내가 받을 금리 4.2%   (기본 3.0 + 우대 1.2)
       채운 조건    급여이체 +0.5 · 카드실적 +0.7
       못 채운 조건  없음
       가입 채널    비대면 가능

2위  B은행 청년적금      내가 받을 금리 3.5%   (기본 3.0 + 우대 0.5)
       채운 조건    급여이체 +0.5
       못 채운 조건  카드실적 (이 은행 카드를 써야 함)
       가입 채널    영업점 방문 필요
       ⚠ 광고 최고금리 3.8% 중 0.3%p 는 근거가 공시에 없음
```

**"왜 이 순서인지"가 같이 나온다.** 금리 숫자만 던지지 않는다.

## 4. "좋은 추천"이란 무엇인가 — 정답의 정의

이게 이 문서에서 제일 중요한 부분이다. **정답이 없으면 잘 만들었는지 알 수 없다.**

### 정답은 취향이 아니라 계산이다

```
사용자 상태 { 급여이체 O, 자동이체 O, 카드실적 X, 12개월, 월 50만원 }
        +
상품 공시  { 기본 3.0%, 급여이체 +0.5, 자동이체 +0.3, 카드실적 +0.4, 상한 1.0 }
        ↓
세전 금리 = 3.0 + min(0.5 + 0.3, 1.0) = 3.8%
        ↓ 세금
세후 금리 = 3.8 × (1 − 0.154) = 3.21%      ← 실제로 손에 쥐는 금리
```

**이건 사람마다 다르지 않다. 산수다.** 그래서 맞았는지 틀렸는지 확인할 수 있다.

**줄은 세후 금리로 세운다.** 세전으로 세우면 사용자가 실제로 받는 순서와 달라진다.

정렬도 마찬가지다. 사용자가 가중치를 줬으면 그 가중치로 계산한 순서는 하나뿐이다.

### 그래서 틀릴 수 있는 곳이 어디인지가 분명해진다

```
틀릴 수 없는 것                틀릴 수 있는 것  ← 여기를 측정한다
──────────────                ─────────────────────────────────
가중합 정렬                    1. 공시에서 조건을 제대로 뽑았나
                              2. 계산 불가 상품을 제대로 걸러냈나
                              3. 편의 속성이 정확한가 (채널·거리)
```

**1번이 이 프로젝트가 지금까지 만든 것 전부다.** 조건 유형 17종, 규칙 파서,
제한 스키마 LLM, 닫힘률이 다 1번의 부품이다.

### 세금이 순위를 뒤집는다

세전 금리가 낮아도 비과세면 세후로 이긴다. 사용자가 직접 하기 어려운 계산이다.

```
A상품   세전 3.85%  →  세후 3.26%    일반과세
B상품   세전 3.50%  →  세후 3.50%    비과세 대상자

세전으로는 A, 세후로는 B가 이긴다
```

세금은 세 층으로 나눠 다룬다. **확실성이 층마다 다르기 때문이다.**

| 층 | 무엇 | 언제 보여주나 |
|---|---|---|
| 1 | 원천징수 세후금리 | **항상.** 추가 질문 없이 계산된다 |
| 2 | 비과세·세금우대 자격 | **항상.** 나이·자격은 이미 묻는 항목이다 |
| 3 | 금융소득종합과세 | **선을 넘을 때만.** 그때 사용자에게 물어본다 |

**3층은 미리 묻지 않는다.** 계산해보고 연 2,000만원 선을 넘을 때만
소득을 물어본다 — 대부분의 사용자에게는 그 질문이 아예 뜨지 않는다.

그리고 물어봐도 **최종 세액은 약속하지 않는다.** 공제 항목까지는 우리가 모른다.
할 수 있는 것은 세율 구간을 좁히는 것과, **"이 상품에 얼마까지 넣으면 선을 안 넘는가"**를
역산해주는 것이다. 뒤쪽은 정확히 계산된다.

**세율은 매년 바뀐다.** 그래서 세율표를 코드에 박지 않고 별도 파일에 두고
적용 시점을 적는다 — 공시 스냅샷을 날짜로 고정한 것과 같은 방식이다.

## 5. 계산이 안 되는 상품은 어떻게 하나

**버리지 않는다. "근거 없음"으로 표시한다.**

공시된 우대조건을 다 더해도 광고 최고금리에 안 닿는 상품이 있다(§2-다).
이걸 조용히 빼면 사용자는 그 상품이 있는 줄도 모르고,
그대로 두면 광고 금리로 1등이 된다.

```
표시 예시
  광고 최고금리 3.85%
  공시된 조건으로 설명되는 금리 2.35%
  ⚠ 나머지 1.5%p 는 어떻게 받는지 공시에 없습니다
```

### 계산값은 공시 최고금리를 넘지 않는다

**우리가 뽑은 조건 합계가 공시 최고금리보다 클 때가 있다.** 그러면 공시 값으로 자른다.
사용자가 공시보다 많이 받을 수는 없으므로 이 상한은 항상 참이다.

```
저축은행 12개월 297개 기준
  우리 계산이 공시 최고금리를 넘던 상품   182개
  가장 심한 예    처음만난적금  11.50% → 8.00%   (공시 최고가 8.0%)
```

**상한이 없으면 공시에 없는 금리를 사용자에게 보여준다.** 이 프로젝트가 잡으려던
실패를 우리가 만드는 셈이다.

**그런데 이 상한은 증상만 막는다는 것을 적어둔다.** 넘치는 182개는 상품 문제가 아니라
**우리가 잘못 읽은 것**이고, 상한은 그걸 사용자 화면에서만 가린다. 그래서 원값을 함께
남긴다 — 추출이 나아졌는지 계속 재야 한다.

### 상품을 버리지 않고 층으로 나눈다

문제 있는 상품을 목록에서 빼는 방법도 있었다. **버리지 않기로 했다.**

| 층 | 무엇 | 화면 | 사용자에게 하는 말 |
|---|---|---|---|
| **확정** | 합계가 공시와 맞고 모든 조건에 답했다 | **메인** | — |
| **범위** | 맞지만 답하지 않은 조건이 있다 | **메인** | — |
| **공시미반영** | 조건문에 우대가 있는데 공시 최고금리에 없다 | 아래 | "은행에 확인이 필요합니다" |
| 설명부족 | 공시 최고금리 일부가 설명되지 않는다 | 아래 | "광고 금리의 근거가 공시에 없습니다" |
| 추출불확실 | 우리가 공시보다 많이 뽑았다 | 아래 | "조건 해석에 확신이 없습니다" |
| 계산불가 | 조건 항목을 못 뽑았다 | 아래 | "금리를 계산할 수 없습니다" |

```
저축은행 12개월 297개
  메인 109   ·   공시미반영 176   ·   설명부족 6   ·   추출불확실 5   ·   계산불가 1
```

**`공시미반영`을 따로 둔 것이 중요하다.** 처음에는 넘치는 181개를 전부 "우리가 잘못
읽었다"로 묶었는데, 세어 보니 **176개는 공시 문제**였다. 조건문에 "비대면 가입시 0.1%"가
적혀 있고 우리는 정확히 뽑았는데, 공시가 그 값을 최고금리 칸에 넣지 않은 것이다.

이 층은 **사용자에게 실제로 유용하다** — "이 상품은 조건문에 우대가 있는데 공시에
반영이 안 돼 있으니 은행에 물어보세요"라고 알려줄 수 있다.

**버리지 않는 이유 세 가지.**

1. 사용자가 그 상품이 있는 줄도 모르게 된다
2. 176개는 상품 공시의 문제다. 버리면 **사용자가 알아야 할 정보를 지우는 것**이다
3. **닫히는 것만 남기면 닫힘률이 자동으로 100%가 되어 개선을 측정할 수 없다.**
   선행 프로젝트에서 `"UNSUPPORTED"` 상수 스텁이 지표를 이긴 것과 같은 구조다

**이걸 판별하는 장치가 "닫힘률"이다.** 뽑아낸 우대금리를 다 더한 값이
공시의 (최고금리 − 기본금리)와 맞으면 그 상품은 계산할 수 있다는 뜻이다.

실측하면 이렇다.

```
은행권      조건 있는 253행 중 계산 가능 77.5%
저축은행     조건 있는 182행 중 계산 가능 63.2%   (처음 보는 데이터 기준)
```

## 6. 편의성은 어떻게 다루나

§2-(나)의 "은행마다 다르다"를 다루려면 금리 말고 다른 축이 필요하다.
그런데 축마다 성질이 달라서 셋으로 나눈다.

| 축 | 예 | 확인 가능한가 | 데이터 |
|---|---|---|---|
| **1. 공시에 있는 사실** | 비대면 개설 가능 여부 · 가입 채널 · 최소금액 | **된다** | **이미 있다** |
| **2. 밖에 있는 사실** | 지점 위치 · 영업시간 | **된다** (좌표는 사실) | 수집 필요 |
| **3. 주관적 평가** | "앱이 편하다" | **안 된다** | **만들지 않는다** |

**3번을 우리가 점수 매기면 안 된다.** 추천이 틀렸을 때
"점수를 잘못 줬나, 계산이 틀렸나"를 구분할 수 없게 된다.
대신 사용자에게 가중치로 물어본다.

1번은 이미 데이터에 있다.

```
join_way (가입 채널)   은행 97건 · 저축은행 668건 전부 채워져 있음
  비대면 전용(영업점 불가)   은행 53% · 저축은행 53%
  영업점 전용(비대면 불가)   0건
```

## 7. AI가 들어가는 자리 — 그리고 안 들어가는 자리

**"AI 프로젝트니까 AI를 쓴다"로 가지 않는다.** 자리마다 왜 필요한지와
없으면 어떻게 되는지를 적는다.

| | 하는 일 | AI가 꼭 필요한가 | 지금까지 잰 것 |
|---|---|---|---|
| **R1** | 공시 조건문을 구조로 바꾼다 | **규칙과 경쟁 중** | 규칙 62.6% · LLM 71.4% · **둘을 합치면 80.2%** |
| **R2** | 사용자 자연어를 상태로 바꾼다 | **그렇다** (폼만 쓸 거면 불필요) | 아직 안 쟀다 |
| **R3** | 뽑아낸 분해가 원문과 맞나 판정 | **그렇다** — 의미 판단이다 | 규칙과 LLM이 **9%**에서 갈린다 |
| R4 | 리포트 서술 문장을 쓴다 | 아니다 | **편의 기능.** 잴 품질 지표가 없다 |

### R1을 왜 아직 "경쟁 중"이라고 하나

규칙(정규식)을 세 라운드 깎아봤다. 결과가 이랬다.

```
규칙을 만들 때 본 데이터에서    68.4% → 77.5%   (+9.1%p)
처음 보는 기관에서             62.6% → 63.2%   (+0.5%p)
```

**규칙이 배운 건 특정 은행들의 글쓰기 습관이었다.** 처음 보는 곳에서는 안 올랐다.
그래서 LLM이 필요할 수 있다. 다만 LLM 단독(71.4%)도 아직 규칙보다 통계적으로
확실히 낫다고 말할 수 없다(p = 0.0987).

**가장 좋은 건 둘을 합치는 것이다.**

```
1. 규칙 파서를 먼저 돌린다               (싸고 빠르다)
2. 닫힘률로 검사한다                     (산수가 맞나)
3. 안 닫힌 것만 LLM에 보낸다             (전체의 39%)
   → 80.2%.  둘 중 어느 하나보다 낫다
```

### R4를 편의 기능이라고 부르는 이유

리포트 문장을 LLM이 쓰면 **읽기 좋아지는지는 주관적이라 잴 수 없다.**
잴 수 없는 걸 성과라고 하면 나머지 주장까지 의심받는다. 그래서 정직하게 적는다.

**대신 위험은 구조로 막는다.**

```
숫자 칸    코드가 채운다. LLM 출력 스키마에 아예 없다   ← 만질 수가 없다
서술 칸    LLM이 채운다. 여기에 숫자를 쓰는 것은 금지
```

이렇게 하면 LLM이 "최고 3.85%까지 받을 수 있습니다" 같은 과장을 할 수가 없다.
검사 장치를 따로 만들 필요도 없다.

## 8. 안 하는 것

- **선호를 추측하지 않는다.** 사용자가 준다
- **주관적 편의 점수를 우리가 매기지 않는다.** 앱 사용성 같은 것
- **AI가 숫자를 만들지 못하게 한다.** 계산은 전부 코드다
- **상품을 광고하지 않는다.** 근거 없는 금리는 근거 없다고 표시한다

## 9. 지금 가진 데이터와 없는 데이터

### 가진 것

```
금융감독원 '금융상품한눈에' API
  은행 예금 38 · 적금 59        상품 97   · 조건 있는 행 253
  저축은행 예금 391 · 적금 277   상품 668  · 조건 있는 행 1,090

  서로 다른 우대조건 문구  177개 · 총 17,358자 (A4 9장)
  가입 채널 · 가입대상 · 가입한도 · 기타사항 — 전부 채워져 있음
  회사 홈페이지 URL · 대표전화 — 전부 있음
```

### 없는 것 — 그리고 그게 왜 중요한가

**정책·정부 상품이 이 API에 하나도 없다.**

```
청년도약 · 청년희망 · 재형저축 · 내일채움 · 청년우대 …  검색 결과 0건 / 765개 상품
```

§2-(나)에서 말한 "같은 상품, 다른 은행" 상황이 **바로 이 상품군에서 일어난다.**
금리가 같으니 편의성이 결정적인 유일한 경우인데, 그 데이터가 없다.

**상품설명서 원문도 없다.** API가 주는 우대조건은 요약본이다.

```
실제 사용자 질문   "급여이체 우대 조건은 무엇으로 급여를 인식하나요?"
실제 답            6회 이상 · 월 50만원 · 적요 문구

이 답은 API 데이터에 없다. 상품설명서에 있다.
```

**카드 상품도 없다.** 회사 목록에는 카드사 48곳이 있지만, 상품은 개인신용대출
29건뿐이다. 그래서 "카드 이용실적 조건"을 데이터로 확인할 방법이 없다.

### 수집 우선순위

| 순위 | 무엇 | 이게 있으면 풀리는 것 |
|---|---|---|
| **1** | **상품설명서 원문** | (1) 설명 안 되는 금리가 진짜 없는 건지 확인 (2) 문서 검색(RAG)의 대상 (3) 리랭커 학습 데이터 — **셋을 동시에 푼다** |
| **2** | 정책·정부 상품 | §2-(나)를 실제로 보여줄 수 있는 유일한 상품군 |
| **3** | 지점 위치 | 편의성 축 2번 |
| 4 | 상품별 딥링크 | 없어도 시스템은 돈다. 회사 홈페이지까지는 연결됨 |

## 10. 앞 버전(검증기)에서 무엇이 바뀌고 무엇이 남았나

| 앞 버전 | 지금 |
|---|---|
| AI 답변이 공시로 뒷받침되는지 **검사**한다 | 내게 맞는 상품을 **골라준다** |
| 정답 = 공시 원문 | 정답 = 내 상황에서의 **실수령 예상금리** |
| 주 타깃 = "확인 불가 판정" | 계산 불가 상품을 **표시하는 기능**으로 남음 |

**남는 것이 생각보다 많다.**

```
조건 유형 17종      → 사용자 상태 입력 필드가 된다
닫힘률              → "이 상품을 계산해줄 수 있나" 판별기가 된다
규칙 파서 · LLM 추출  → 그대로 R1
검증기 개념          → R3 (분해가 원문과 맞나)
사전등록 방법론       → 그대로
```

버려지는 것은 "무엇을 최종 산출물로 삼는가"뿐이다.
