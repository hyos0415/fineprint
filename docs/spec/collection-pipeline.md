# 데이터는 어떻게 들어오나 — 수집과 자동화

> 작성 2026-08-31 · 결정 기록 [`0010`](../decisions/0010-disclosure-updates-monthly.md)(공시는 월 1회) ·
> [`0032`](../decisions/0032-tax-rates-are-pinned-to-statute.md)(세율은 조문에 핀) ·
> 상태는 [`roadmap.md`](./roadmap.md) A·H 절

**이 문서는 밖에서 읽는 사람을 위한 것이다.** *"공시 어떻게 자동화했어요?"* 라는 질문에
답하려고 쓴다. 부품별 계약은 [`design.md`](./design.md), 왜 이렇게 정했는지는
`decisions/` 에 있다.

## 한 문장으로

**들어오는 데이터가 두 종류다.** 상품 공시(금융감독원)와 **우리 숫자·화면의 근거
법조문**(법제처). 둘 다 공개 API 로 받고, **둘 다 월 1회만 받는다.**

```
공시   금융감독원 '금융상품한눈에' API      765상품  · 월 1회 (매월 20일 전후)
법령   법제처 국가법령정보 API             조문 11개 · 월 1회 (공시 수집에 붙여서)
         세율 5개      바뀌면 → config/tax-2026.json 의 값      (`0032` · #28)
         광고 규제 6개  바뀌면 → **화면이 무엇을 강제하나**       (`0034` · #30)
```

**스케줄러는 아직 안 세웠다.** 지금은 손으로 부른다. 왜 안 세웠는지가 이 문서의 절반이다.

## 1. 공시 — 상품 데이터

### 무엇을 받나

```
python src/ingest/fetch_finlife.py deposit                        은행 정기예금
python src/ingest/fetch_finlife.py saving  --group savingsbank    저축은행 적금
```

| | 상품 | 조건 있는 행 |
|---|---|---|
| 은행 | 예금 38 · 적금 59 = **97** | 253 |
| 저축은행 | 예금 391 · 적금 277 = **668** | 1,090 |

응답은 두 덩이로 온다. **이 구분이 뒤에서 계속 중요하다.**

```
baseList     상품 하나당 한 줄   상품명 · 기관명 · 가입채널 · **우대조건 문구(spcl_cnd)**
optionList   금리 한 줄당 한 줄   기간 · 기본금리 · 최고금리 · 단리/복리 · 적립방식
```

한 상품이 `optionList` 에 여러 줄로 나온다 — 기간 6개 × 단리/복리 × 적립방식이 각각
다른 금리를 갖기 때문이다. **저축은행은 12개월 한 기간만 봐도 297줄인데 상품은 183개다**
(`0031`).

### 하는 일은 페이지 순회뿐이다

첫 페이지를 받아 `max_page_no` 를 읽고, 2페이지부터 끝까지 돌면서 두 리스트를 이어
붙인다. 페이지 사이에 0.3초 쉰다. 받은 것을 **손대지 않고** 날짜 붙인 파일로 저장한다.

```
data/raw/deposit_20260826.json
data/raw/saving_savingsbank_20260825.json
```

정직하게 적어 둘 것 셋.

- **재시도가 없다.** `err_cd != "000"` 이면 그 자리에서 죽는다. 월 1회짜리라 사람이
  다시 부르면 되고, 조용히 재시도해서 반쯤 받은 스냅샷을 만드는 것이 더 나쁘다
- **개수가 안 맞으면 경고만 하고 저장한다** — `수집 N건 != total_count` 를 찍고 그대로
  남긴다. 스냅샷은 "그때 API 가 뭐라고 했는지" 의 기록이므로 우리가 고치면 안 된다
- **API 키는 로그에 `auth=***` 로 마스킹한다.** 키는 `.env` 에만 있다

### 원본을 git 에 안 올린다

`data/` 는 `.gitignore` 에 있다. **금융감독원이 API 로 공개하는 데이터를 GitHub 에
재배포하면 검색·크롤링에 그대로 잡혀서 API 로 배포하는 의미가 퇴색된다.** 커밋하는 것은
수집 스크립트와 문서에 적은 집계 결과다.

### 왜 월 1회인가 — 재 봤다

```
8/24 스냅샷과 8/26 스냅샷을 전수 비교   변경 0건
```

**공시는 매월 20일 전후에 한 번 갱신되고 같은 달 안에서는 안 움직인다.**
`0010` 이 그 실측으로 정했다. 매일 긁으면 같은 파일을 30번 받는다.

## 2. 법령 — 세율의 근거

### 왜 이게 수집 대상인가

우리가 화면에 내는 금리는 **전부 세후**다. `15.4%` 를 떼고 나온 숫자이고, 선호 가중치의
`-0.50%p` 같은 값도 세후 %p 다. 그런데 그 `15.4%` 가 `"확인_상태": "미확인"` 이었다.

**첫 확인에서 틀린 값이 나왔다.**

```
조특법 §89의3   조합등예탁금
  우리가 적어 둔 값   "세율 1.4% (농특세만 부과)"
  조문의 실제 값      2025-12-31 까지 가입분은 비과세
                    **2026-01-01 ~ 12-31 가입분 100분의 5** · 2027년 이후 9%
```

누군가 2025년에 맞게 적어 뒀고 아무도 다시 안 봤다. **세법은 매년 바뀌고 특례에는
일몰이 있다** — 그래서 값이 아니라 **출처**를 관리하기로 했다(`0032`).

### 어디서 받나 — 호출 두 개

**1단 · 목록 조회.** 법령명으로 현행 버전의 메타데이터만 받는다. **2.5KB.**

```
GET https://www.law.go.kr/DRF/lawSearch.do?OC=<키>&target=law&query=소득세법&type=JSON

받는 것   법령ID       001565     ← 법이 바뀌어도 안 변한다. **여기에 핀을 박는다**
         법령일련번호   280405     ← MST. **개정될 때마다 새로 생긴다**
         시행일자      20260701
         공포일자/번호  20251223 / 21221
```

**2단 · 본문 조회.** 1단에서 받은 `MST` 로 법 전체를 받는다. **1.3MB.**

```
GET https://www.law.go.kr/DRF/lawService.do?OC=<키>&target=law&MST=280405&type=JSON

받는 것   조문단위[] = 조문번호 + 조문가지번호 + 조문여부 + 조문시행일자 + 항/호/목 내용
```

### 조문 하나를 집는 좌표는 셋이다

```
조문번호     "103"
조문가지번호  "13"     ← 제103조의13 의 "13". 없으면 None
조문여부     "조문"    ← **이걸 안 보면 틀린 것을 집는다**
```

`조문여부='전문'` 은 편·장 헤더인데 **같은 조문번호로** 목록에 섞여 있다. 안 걸렀다가
소득세법 제14조와 지방세법 제103조의13 을 못 찾았다.

집은 뒤에 `...내용` 으로 끝나는 필드를 재귀로 모아 한 문자열로 만들고, 공백을
정규화해서 **sha256 앞 16자**를 뜬다. 그게 "이 조문이 바뀌었나" 의 기준이다.

지금 보는 조문은 **열하나**다. 먼저 세율 다섯.

| 법령 | 법령ID | 조문 | 무엇 |
|---|---|---|---|
| 소득세법 | `001565` | 제129조 | 이자소득 원천징수세율 14% |
| 소득세법 | `001565` | 제14조 | 금융소득종합과세 기준 2천만원 |
| 지방세법 | `001649` | 제103조의13 | 개인지방소득세 = 소득세의 10% |
| 조세특례제한법 | `001584` | 제88조의2 | 비과세종합저축 5천만원 · 일몰 2028-12-31 |
| 조세특례제한법 | `001584` | 제89조의3 | 조합등예탁금 3천만원 · 5%/9% |

그리고 광고 규제 여섯. **여기는 값이 아니라 화면이 걸려 있다.**

| 규범 | ID | 조문 | 무엇 |
|---|---|---|---|
| 금융소비자보호법 | `013704` | 제22조 | 예금성 상품 광고 금지행위 — *"이자율의 범위ㆍ산정방법 (…) 을 명확히 표시하지 아니하여 (…) 오인하게 하는 행위"* |
| 같은 법 시행령 | `014044` | 제18조 | 광고에 넣을 '금융상품의 내용' + 고시 위임 |
| 같은 법 시행령 | `014044` | 제20조 | 광고 금지행위 + 고시 위임 |
| 금융소비자보호 감독규정 | `77048` | 제17조 | **예금성 상품은 "이자율ㆍ수익률 각각의 범위 및 산출기준"** 을 광고에 포함해야 한다 |
| 같은 감독규정 | `77048` | 제19조 | **"소비자에 따라 달라질 수 있는 거래조건을 누구에게나 적용될 수 있는 것처럼 오인하게 만드는 행위"** 금지 |
| 공정위 「금융상품 등의 표시·광고에 관한 심사지침」 | `55352` | 전문 | Ⅴ.1.마 — **'세전'인지 '세후'인지를 누락하면 부당한 표시·광고** |

**이게 `0017` 이 화면에 강제한 것의 근거다** — 최고금리를 단독으로 쓰지 않고 항상
범위로 쓰는 것. 자세한 것은 [`0034`](../decisions/0034-ad-rules-exist-but-bind-the-seller.md)
에 있고, **의무 주체가 판매업자라 우리에게 직접 적용되는지는 아직 열린 결정**이다(#31).

### 행정규칙은 응답 구조가 다르다 — 같은 코드가 안 붙었다

감독규정은 금융위원회 **고시**이고 심사지침은 공정위 **예규**다. 법률·대통령령이
아니므로 `target=law` 가 아니라 **`target=admrul`** 로 부르고, 그러면 필드 이름과
본문 모양이 통째로 바뀐다.

```
법령 (target=law)                     행정규칙 (target=admrul)
법령ID           ← 핀 →               행정규칙ID
법령일련번호(MST)  ← 매번 새로 →        행정규칙일련번호
공포일자/공포번호   ← 대응 →            발령일자/발령번호
조문단위[] = dict 리스트               조문내용[] = **문자열 리스트**
  조문번호·조문가지번호·조문여부           "제17조(광고의 내용) ① …" 처럼 좌표가
  ·조문시행일자가 필드로 있다              본문 앞머리에 붙어 있을 뿐이다
본문 조회 = MST 파라미터                본문 조회 = **ID 파라미터**
                                      그 ID 는 행정규칙ID(77048)가 아니라
                                      **행정규칙일련번호**(2100000276850) 다
```

**같은 `target` 안에서도 갈린다** — 공정위 예규는 `조문내용` 이 **문자열 하나**로
온다(장·절이 로마숫자라 조문 단위가 아니다). 그 행만 좌표 없이 전문을 해시한다.

법령 쪽에서 겪은 함정(`조문여부='전문'` 인 편·장 헤더가 **같은 조문번호로** 섞여
있어서 조문 두 개를 못 찾았다)에 대응하는 것이 있는지 찾아봤는데 **감독규정에는
없었다** — 원소 36개가 전부 `제N조` 로 시작하고 좌표 중복이 0이었다.

### 확인은 2단으로 한다 — 크기 차이가 이유다

```
lawSearch    2,505 bytes      <- 이것만으로 "바뀌었나" 가 판정된다
lawService   1,288,895 bytes  <- 바뀐 법령만 긁는다              ~515배
```

```
python src/ingest/fetch_law.py --check
  │
  ├─ 1단  법령 3개에 목록 조회 (2.5KB × 3 = 7.5KB)
  │       시행일자·공포번호가 커밋된 스냅샷과 같은가?
  │
  ├─ 같다 ─────────► 끝. 종료코드 0. **본문을 안 긁는다**
  │
  └─ 다르다 ─► 2단  **그 법령만** 본문 조회 (1.3MB)
                   조문별 해시 대조 → 바뀐 조문을 이름으로 찍고 종료코드 1
```

**핀을 `법령ID` 에 박고 `MST` 는 매번 새로 얻는 것이 핵심이다.** `MST` 를 고정하면
개정된 뒤에도 옛 버전을 계속 읽어서 영원히 "안 바뀌었다" 가 나온다.

근거 스냅샷은 커밋한다 — `config/tax-sources.json` · `config/ad-sources.json`.
**둘로 나눈 이유는 바뀔 때 고칠 곳이 다르기 때문이다** — 세율은 `tax-2026.json` 의
숫자를 고치면 되지만, 광고 조문이 바뀌면 **화면이 무엇을 강제해야 하는지**를 다시
봐야 한다. 파일에 들어가는 것은 같다 — 좌표 · 시행일자 · 공포번호 ·
해시 · **인용 원문**이 들어 있다.

## 3. 자동화하지 않은 것 — 그리고 그 이유

### 조문에서 세율을 자동으로 읽지 않는다

```
기계가 한다   "바뀌었다" 까지
사람이 한다   "무엇으로 바뀌었나" 를 읽고 config/tax-2026.json 에 반영한다
```

**조특법 §89의3 이 그 근거다.** 한 조문 안에서 가입 시기별로 5%/9% 로 갈리고 대상자
조건으로 또 갈린다. 정규식이 어느 숫자를 집을지 알 수 없고, **틀려도 조용하다.**
오늘 찾은 오류가 정확히 그 모양이다.

이 프로젝트가 *"LLM 이 숫자를 만들지 못하게 한다 — 숫자 칸은 코드가 채운다"* 로 막은
자리에, 이번엔 정규식이 있을 뻔했다.

**감시하는 문구도 조문이 말하는 쪽으로 잡았다.** 지방소득세 1.4% 는 조문에 없다 —
조문은 *"원천징수하는 소득세의 100분의 10"* 이고 1.4% 는 14×10% 로 우리가 유도한
값이다. 그래서 `"1.4%"` 가 아니라 `"100분의 10에 해당하는 금액"` 을 본다.
**우리가 계산한 것을 감시하면 안 된다.**

### Airflow 를 아직 안 세웠다

**저장소에 `dags/` 가 0개다.** 이유가 둘이다.

**첫째, 부를 일이 아직 하나뿐이다.** 월 1회 공시 수집이 전부다. 세율 조문 대조도
별도 스케줄이 필요 없다 — **세율이 쓰이는 자리가 월 1회 계산 하나뿐**이라 같은
파이프라인의 첫 태스크로 들어간다. 별도 DAG 를 만들 명분이 없다.

**둘째, 아직 안 잰 것이 있다.** *"월 갱신 때 사람 손이 몇 건 필요한가"* 를 9월 공시로
재고 나서 파이프라인을 짜기로 했다(로드맵 B6). **월 5건이면 AI 없이 가고 월 60건이면
필요하다** — 그 답이 파이프라인 모양을 정한다.

그래서 **스크립트를 먼저 만들고 스케줄러는 쓸 곳이 둘이 됐을 때 붙인다.** `--check` 가
그대로 DAG task 의 몸통이고, cron·GitHub Actions·Airflow 어디에나 붙는다.

이 순서를 지키는 이유는 선행 프로젝트가 반대로 해서 실패했기 때문이다 —
**구조를 먼저 세우고 쓸 곳은 나중에** 찾는 순서였고, `CLAUDE.md` 1번이 그것을 막는다.

### 개정 20일 지연을 받아들인다

세법은 **12월 말 공포 → 1월 1일 시행**이 기본형이다(실제로 소득세법 2025-12-23 공포 ·
지방세법 2025-12-31 공포). 1월 1일 시행인데 1월 공시 수집(1/20 전후)에서 잡으면
**최대 20일 늦게 안다.**

12월~1월만 조밀하게 보는 안을 검토했고 **안 만들었다.** 지연을 며칠로 줄이는 대신
지킬 규칙이 하나 늘어난다. **지연이 실제로 문제가 됐을 때 만든다** — 그때는 근거가
생긴다. 지금은 근거 없는 최적화다.

## 4. 자주 받을 질문

**Q. 공시 어떻게 자동화했어요?**
스크립트로 받아서 날짜 붙인 스냅샷으로 저장한다. **스케줄러는 아직 안 붙였다** —
부를 일이 하나뿐이고, 파이프라인 모양을 정할 측정(B6)이 9월 공시를 기다리는 중이다.

**Q. 왜 매일 안 긁어요?**
공시가 월 1회만 갱신된다. 8/24 ↔ 8/26 스냅샷 전수 비교로 **변경 0건**을 확인했다.
매일 긁으면 같은 파일을 30번 받는다.

**Q. 이번 달 데이터가 다 들어왔는지 어떻게 알아요?**
**아직 못 안다.** 저축은행은 기관마다 며칠에 걸쳐 들어오는데, `dcls_strt_day`(공시
시작일)로 세면 판정할 수 있다. 로드맵 H2 이고 **착수 가능 상태로 열려 있다.**

**Q. 법이 바뀌면 어떻게 알아요?**
`fetch_law.py --check` 가 목록 조회 2.5KB 로 판정하고, 바뀐 법령만 본문을 긁어
조문 해시를 대조한다. 스냅샷의 공포번호를 개정된 것처럼 바꿔 놓고 돌려 **이 경로가
실제로 발동하는 것을 확인했다.**

**Q. 세율을 왜 자동으로 안 읽어요?**
한 조문 안에서 가입 시기·대상자별로 세율이 갈린다(조특법 §89의3). 정규식이 어느 숫자를
집을지 알 수 없고 틀려도 조용하다. **실제로 그 조문에서 우리 값이 1년 묵어 있던 것을
찾았다.**

**Q. 실패하면 어떻게 돼요?**
그 자리에서 죽는다. 재시도가 없다. 월 1회짜리라 사람이 다시 부르면 되고, **반쯤 받은
스냅샷을 만드는 것이 더 나쁘다.**

**Q. 원본 데이터는 왜 저장소에 없어요?**
금융감독원이 API 로 공개하는 데이터를 GitHub 에 재배포하면 검색·크롤링에 잡혀서 API 로
배포하는 의미가 퇴색된다. 커밋하는 것은 수집 스크립트와 집계 결과다.

**Q. API 키는요?**
`.env` 에만 둔다(`.gitignore` 포함). 로그에는 `auth=***` 로 마스킹한다.
`.env.example` 에는 키 이름만 있다.

## 5. 명령어 모음

```
공시     python src/ingest/fetch_finlife.py deposit
        python src/ingest/fetch_finlife.py saving --group savingsbank

법령     python src/ingest/fetch_law.py --check       바뀌었는지 본다 (종료코드로 답한다)
        python src/ingest/fetch_law.py --show 129    조문 원문을 읽는다 (사람이)
        python src/ingest/fetch_law.py --snapshot    스냅샷을 다시 뜬다 (확인 뒤)
```

| 필요한 키 | 어디 | 없으면 |
|---|---|---|
| `FINLIFE_API_KEY` | `.env` | 공시 수집이 죽는다 |
| `LAW_OC` | `.env` | `OC=test` 로 떨어진다 (지금은 동작하지만 실사용은 발급받는다) |
