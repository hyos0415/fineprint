## §A 부하 시험 — 10명이 같은 순간에 "칸 채우기" 를 누르면

### A1 무엇을 재나

```
서빙       llama-server -np 8 -c 32768 --log-disable (슬롯 8 · 총 컨텍스트 32k · 프롬프트 로그 없음) · uvicorn 단일 프로세스 (지금 그대로)
도구       k6 v2.2.0 · 스크립트 tools/k6/prefill_burst.js (저장소에 둔다 · 문장은 합성 10개 · 개인정보 없음)
시나리오    browse  — 0~70초 동안 초당 5건 POST /screen (은행권 12개월 · 답 없음) — "다른 사람들이 목록을 본다"
          burst   — 20초 시점에 10 VU 가 **동시에** POST /prefill 한 번씩 (서로 다른 문장) — "10명이 같은 순간에 칸 채우기"
읽는 값    /screen p50·p95 (burst 전 20초 vs burst 중) · /prefill 10건의 완료 시간 분포 · 실패(타임아웃 30초 → 안내 문구) 건수 · GPU 메모리 최대
두 번 잰다   ① 지금 코드 (async 핸들러 안에서 동기 urllib) ② 모델 호출을 스레드풀로 보낸 뒤. 같은 스크립트 · 같은 서빙
```

### A2 예측 — 시험 전에 적는다

```
P1  켜짐       -np 8 -c 32768 이 8GB 에 올라간다 — 가중치 2.9 + KV 1.0(f16) + 버퍼 · 기동 뒤 사용 VRAM 4.5~5.5 GB
P2  ① 차단     고치기 전: burst 중 /screen p95 가 **1초를 넘는다**(혼자일 때 수십 ms). 핸들러가 이벤트 루프를 잡고 있어 목록 보기가 모델을 기다린다.
             10건의 /prefill 은 **한 번에 하나씩** 서버에 닿아 사실상 직렬 — 마지막 사람은 30초 타임아웃에 걸릴 수 있다 (실패 1건 이상)
P3  ② 해소     고친 뒤: burst 중 /screen p95 < 200 ms (burst 전과 같은 자릿수). /prefill 10건이 슬롯 8개에 같이 들어가 **8건은 병렬 · 2건 대기**.
             완료 시간 — 병렬 8건 15~30초(혼자 4초의 4~7배 · GPU 를 나눠 쓴다) · 대기 2건 +5~15초. 타임아웃 30초에 걸리는 건 0~2건
P4  처리량     슬롯을 늘려도 GPU 하나의 총 처리량은 그대로 — 10건 전부 끝나는 시각은 ①과 ② 가 크게 다르지 않다(±20%). 달라지는 것은 **다른 사람의 화면**이다
P5  안내 문구   타임아웃에 걸린 건은 지금 "모델 서버가 꺼져 있습니다" 를 받는다 — 붐빔인데 꺼짐이라고 말한다 → 문구를 갈라야 한다 (시험이 이 건수를 센다)
```

### A3 판정 조항

```
P1 이 틀리면(안 켜짐)      -np 6 -c 24576 로 낮춘다 · KV q8 은 그 다음
P2 가 맞으면              스레드풀 수정은 파일럿 **전제 조건**이다 — 고치고 ② 를 잰다 (수정은 한 함수 · /screen 은 건드리지 않는다 · A1~A19 재확인)
P3 의 p95 가 200 ms 넘으면  uvicorn 워커 수(--workers 2)를 본다 — 계산 16 ms 라 한 프로세스로 충분해야 한다. 넘으면 원인을 적는다
P3 의 타임아웃 3건 이상     np 8 로 부족 — 문장 수를 줄이는 게 아니라 **타임아웃 문구를 갈라 폼이 그대로 동작함을 확인**하고, np 12 를 한 번 더 잰다
어느 쪽이든              결과는 §A4 에 · 서빙 설정은 START-HERE "다음 시작점" 명령에 반영
```

```

P2  ① 차단   맞음 — p95 1초 예측이었는데 **40초**. 직렬화도 맞음(10건이 25초 중앙값 · 마지막 44초). 타임아웃 1건 이상 예측은 틀림 —
           대기는 uvicorn 소켓 앞에서 일어나 urllib 의 30초 시계가 돌지 않았다 (사용자는 그냥 44초를 기다렸다)
P3  ② 해소   맞음 — p95 33 ms < 200 ms. 8병렬+2대기 예측 · 완료 15~30초 예측 → 18.6~23.2초. 타임아웃 0~2 예측 → 0

           "슬롯을 늘려도 처리량은 같다" 는 직렬 대기가 있을 때는 틀린 말이었다
P5  문구     시간 초과가 0건이라 이번 시험에서는 안 보였다. 문구는 갈라 두었다(`PREFILL_BUSY`) — 다음에 걸리면 그때 센다
```

### §A 판정

- **스레드풀 수정은 파일럿 전제 조건이었고 고쳤다.** `/screen` 코드는 안 건드렸다(diff 0) · A1~A19 은행권 통과 재확인
- **np 8 · c 32768 로 간다.** 10명 동시 최악이 23초, 다른 사람 화면은 영향 0. np 12·16 은 재지 않는다 — 필요가 관측되면 그때
- vLLM 은 후보에서 내린다 — 동시성은 이걸로 충분하고, 엔진을 바꾸면 R2 측정(`prereg-27~29`)을 다시 해야 한다
- 이 시험은 **교육장 20명 중 10명이 같은 초에 누르는** 경우다. 실제로는 어긋나서 5~10초일 것이다. 남은 위험은 사람 세션에서 본다
